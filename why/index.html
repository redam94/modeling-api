    Why modeling-api?¶

    Most statistical models that are important to a business start in a notebook. Someone explains them in a slide deck, and then the work stops. To make the models useful, a second project is necessary, and most of it is plumbing. The project must put the models in front of the persons who make decisions. It must keep the models honest after the data changes. It must prove that they learned something real, and let other tools use them.

    modeling-api is that second project, done one time, for a specific type of model: Bayesian and classical models of labelled, multi-dimensional data (panels, time series, hierarchies). The preprocessing and uncertainty of these models must stay correct in production. Their analysis must be repeatable and defensible.

    The problems it solves¶

    The problem What usually happens What modeling-api does
    The preprocessing at score time is not the preprocessing at fit time Someone writes the scaling, lags and currency conversion again in the service. Or they fit them again on the new data, or they forget them Steps store what they learned at fit time and replay it at score time. This includes the look-back tail of each group. Inverse transforms bring answers back to your units (Pipelines)
    Data is positional Column 7 changes meaning. A new market is "row 12". The lags of a forecast start from the wrong week Data is an xr.Dataset with named dims. Each dim declares what can occur at score time (fixed, extend, new_levels). The platform checks requests against it before any compute (Labelled data)
    The analysis is only in the head of one person "I ran ADF, it looked non-stationary, so I differenced and tried a few ARIMAs". This occurs one time, by hand, and nobody writes it down A workflow runs the tests and makes the decisions by stated rules. It searches the orders, backtests against naive forecasts and records each value that it read. It runs again on a schedule or when the data changes. It uses the unchanged steps again (Workflows)
    A model goes live because it looks good The fit looks good, and there is an R² on the training data. Nobody checks if noise can give the same result Governance policies: the model must be better than the same model fitted on shuffled results. It must give no credit to fake noise drivers. It must be better than naive benchmarks out of sample. A second person approves, and endpoints refuse versions that are not validated (Null tests explained)
    Uncertainty is lost or added incorrectly A point estimate controls a budget decision. Someone adds the 90% quantiles of 40 stores Each output has its representation (draws, quantiles, interval, point, moments). The platform gives only the valid summaries and aggregations (Representations)
    Each scenario needs the data scientist The analyst asks "what if we move 20% to search?" and waits a week Guided mode has templates, beliefs in business terms and a report in plain language. It has instant what-if sliders over a response curve for each draw, and budget plans from the posterior (Guided mode)
    To choose a model, you need a statistician The analyst uses the model of the last project, or the model with the most interesting name Each model, step, node and check has an About card in plain words. Help me choose asks some questions and gives a ranked shortlist with reasons (Choosing a model)
    You find data problems after the model Gaps, a constant driver or a series that wanders show in the residuals one week later The Data Explorer makes a profile of each upload in the sandbox. It shows quality warnings, the stationarity of each series, cross-correlation with the KPI by lag, STL and collinearity (Explore a dataset)
    Nobody knows if they can trust the model Convergence warnings are in a log that nobody reads A sanity scorecard (convergence, holdout error and coverage, plausibility, data) in plain words, and a promotion gate that uses it (Scorecard)
    Other tools need the model A Flask app for each model, a shared pickle, or a CSV file in an e-mail each Monday Endpoints with aliases, history and rollback. Scoped tokens, generated snippets, signed webhooks and charts that you can embed (Integrations)
    Many teams, untrusted code and data One shared server where all code can read all data Tenants with row-level security and a new sandbox for each run. Outputs that the platform verifies against the checksums of the storage and signs. Quotas and a kill switch (Security model)

    Compared with notebooks and an ad-hoc Flask app¶

    This is the most usual alternative. It is a good alternative for one model and one team.

    Notebook + a small web app modeling-api
    How to start Minutes: you already have the notebook A spec or a build() method. Guided templates and workflow recipes need no code
    Freedom Any library, any code Any PyMC or scikit-learn model through the plugin contract. Built-in models for MMM (mmm-framework), twelve statsmodels time-series models, forecasting, demand and choice. Your own plugins run now on a deployment that you control (installed into its runner). Upload to a shared deployment comes in v0.6, first for allow-listed teams
    Preprocessing at score time Someone copies it into the app by hand, or pickles it with the model Declared steps with fitted state that the platform replays exactly. Static checks find leakage
    Forecasts and new groups The result depends on what the code does with a row or date that it did not see Declared for each dim and checked before compute, with typed errors (UNSEEN_LEVELS, HORIZON_EXCEEDS_FIT, …)
    How to repeat the analysis Run the cells again, and hope that the sequence is correct A versioned workflow with typed ports. The platform validates it before it runs. A schedule or new data starts it. It records each decision
    How to validate the model A holdout number in a slide, if someone asks Null tests, benchmarks, residual checks and stability checks under a versioned policy. The approval of a second person. An evidence pack for the auditor
    Model versions File names, and a model registry if you set one up Immutable spec revisions, signed bundles, lineage, and endpoints with history and rollback
    Who can use it Persons who can run the notebook or call the app Analysts in Guided mode. Other apps through endpoints, sheets, BI embeds and webhooks
    Security It depends on the app. Often there is pickle and an open port Sign-in, roles, scoped tokens, sandboxed runs, no pickle, verified outputs
    How to operate it You own the server You own the deployment (a laptop, Docker Compose or Google Cloud). It is multi-tenant from the start

    Use the notebook when the model is a single analysis that nobody else must call or check. Move to modeling-api when a second person, a second model or a second application needs the model. Also move when someone asks "how do we know this is not noise?".

    Compared with workflow orchestrators¶

    Airflow, Prefect, Dagster and similar tools are very good when you must run any type of task on a schedule across systems. The workflows of modeling-api are narrower on purpose. They are the statistics of one analysis, not a data pipeline.

    General-purpose orchestrator modeling-api workflows
    A step is Any Python function or container A node from a catalog (51 nodes: 17 statistical tests, transforms, 7 train/test plans, order searches, fits, backtests, comparisons, governance, reports) or a saved sub-workflow
    Between steps The data that the code sends Typed ports (dataset, test_result, split_plan, model_version, …). The platform checks them before the run starts, with a JSON pointer to each problem
    Decisions Python if statements Branch conditions in a small, safe expression language (never eval). The run records the values that each condition read
    Where user data is read The location where the task runs In a new sandbox without network. The orchestrator sees only JSON results
    Reuse A task cache that you configure The identity of each node is its implementation, its parameters and the content of its inputs. The platform uses unchanged steps again automatically
    Output The data that the tasks write Verdicts in plain language, a report, governance evidence and a model version that is ready to validate and promote

    Use an orchestrator to move data between systems and to call modeling-api. Use a workflow for the analysis. The two tools work well together. For example, an orchestrator uploads the data of the new week, and the dataset trigger runs the workflow.

    Compared with marketing-mix vendors and libraries¶

    Marketing-mix models are the first domain pack, thus users ask about this comparison most. modeling-api is not a new MMM methodology. It does not compete with the statistics of the established libraries. It is a platform that runs MMMs, applies governance checks to them and puts them in front of planners.

    Open-source MMM libraries (for example, Google's Meridian and Meta's Robyn) are very good at the model. But they are libraries, and you run them in a notebook. You must supply the serving, the scenario tools for analysts, the validation, the versions and the access control.

    • The built-in MMMs run on mmm-framework. This is an open-source (Apache-2.0) Bayesian MMM framework on PyMC. Business priors become its ROI priors. Lift tests become its experiment likelihoods. Its planning module optimises budgets from the posterior (MMM guide).
    • The ingest recognises Meridian-shaped tables (time, geo, kpi, <channel>_spend). The Meridian model is not part of the platform, because it needs TensorFlow.
    • The platform does not support Robyn (R).

    Managed MMM services usually supply data collection from ad platforms, a methodology, models as a service and planning dashboards. modeling-api does not collect data from ad platforms, and it gives no consulting. But you own the spec, the data and the fitted posterior. You can read each prior and each check. You can run models other than MMM on the same platform, and connect the result to your own tools.

    Typical managed MMM service Open-source MMM library modeling-api
    Data collection from ad platforms Often included No No: upload CSV, Parquet, MFF or Meridian-shaped tables
    The model The model of the vendor Your model, in code The Bayesian (or fast frequentist) MMM of mmm-framework, national or pooled over geos and products, or your own plugin
    Priors and calibration Different for each vendor, frequently hidden Your priors, in code Business priors as ROI or share ranges, and lift tests. You can see all of them in the spec
    Proof that it does not fit noise Not frequently shown You must do it Shuffled-sales and fake-channel null tests, effect signs, holdout accuracy and prior sensitivity, with evidence and the approval of a reviewer
    Analyst scenarios Dashboards You build them What-if sliders with joint uncertainty, "Run exact", forecasts and counterfactuals
    Budget optimisation Usually included Library functions optimize runs in the sandbox on mmm-framework planning: bounds, groups, risk objectives (P10, CVaR) and the efficient frontier
    Other models on the same platform No No Forecasting, macro systems (VAR/VECM), store demand, customer choice, your own
    Who owns the posterior The vendor You You

    Compared with generic ML model serving¶

    MLflow, BentoML, KServe, Seldon and the endpoints of the cloud providers are very good at their task. They package a trained model from almost any framework. They serve it with low latency and autoscaling. modeling-api is for a narrower problem, and it makes different trade-offs.

    Generic model serving modeling-api
    Input contract Column or tensor signatures: names and shapes, but no dimensions xr.Dataset with named dims, coordinates, roles, units and a score policy for each dim
    Preprocessing at score time You must do it. Put it in the artifact, or write it again Declared steps with fitted state that the platform replays exactly. Splits that know the stage, and a context tail for each group
    New groups and horizons The result depends on what the model does with a row that it did not see Declared for each dim (fixed, extend, new_levels + strategy) and checked before compute
    Uncertainty Point predictions by default. Intervals are a custom output A primary representation that decides which summaries and aggregations are valid
    Units of the answer The space that the model used for training Inverted to original units. Each variable records its output space
    Serialization Native to the framework. Pickle and cloudpickle are usual Zarr zip + JSON, skops or xgboost JSON. The platform rejects pickle on write and on read
    Promotion Usually manual, or a CI job A sanity scorecard is the gate. When a policy tells so, a governance validation is also a gate. It has null tests and the approval of a second person
    Latency Milliseconds, warm replicas, autoscaling, GPUs Batch: one sandboxed run for each call (seconds, plus cold start in the cloud). Instant what-if from grids that the platform calculates before. No GPUs and no warm scorers yet
    Frameworks Almost any PyMC, scikit-learn, xgboost, statsmodels, mmm-framework and hand-written models through the plugin contract
    Who it is for ML engineers who serve many types of model Statisticians, data scientists, and the analysts and apps that use their models

    When to use something else¶

    • You need answers from the exact model in less than one second, or thousands of requests each second. Use a model server. modeling-api answers sliders immediately from grids that it calculates before. But an exact score is a sandboxed run.
    • Deep learning or GPU work. The platform does not support it before the scale milestone.
    • General data pipelines (move data between systems, join across databases, call APIs). Use an orchestrator. Workflows are for the statistics of an analysis. They use catalog nodes, and they run without network access.
    • Your model needs the network at run time (an API, a database). Runs have no egress, by design.
    • You want to upload public code to a hosted platform now. On a shared deployment, uploaded plugins come first to allow-listed teams (v0.6). They come to the public only after an external penetration test. On a deployment that you control, you can install and run your own plugins now.

    Where it stands¶

    v0.5 is complete, and we tested it on a laptop. The workflow, governance, mmm-framework, explorer and CLI journeys pass end to end against a live stack. All earlier journeys also pass. The numbers on the home page come from those runs. Two items are still open. We test the cloud controls against fakes until they meet a real Google Cloud project. Also, the study with five non-technical testers did not run yet. See M3.5 verification, M3 verification and the roadmap.
