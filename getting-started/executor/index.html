    Runs and executors¶

    fit_spec and score_bundle are plain functions. The platform does the same work as runs: JSON-only submissions handed to an executor, which reports progress as events and returns a status that is the source of truth. The in-process executor implements that protocol inside your Python process, so notebooks, tests and the platform's local-process and docker executors share one code path.

    sequenceDiagram
    participant You as Notebook / API
    participant Ex as Executor
    participant H as Harness (fit_spec / score_bundle)
    You->>Ex: submit(RunSubmit{kind: fit, payload: spec}, nonce)
    Ex->>H: resolve dataset refs, fit
    H-->>Ex: progress events
    Ex-->>You: event stream (state, progress, complete)
    You->>Ex: wait(handle) → SUCCEEDED
    You->>Ex: submit(RunSubmit{kind: score, payload: request + bundle})
    Ex->>H: score_bundle
    Ex-->>You: result: xr.DataTree

    Set up¶

    The executor resolves the dataset:// references in specs and requests through a resolver. Here it is a mapping to in-memory datasets; the built-in tabular plugin ships the store-demand data and spec used below.

    import asyncio

from mapi_plugin_tabular.datasets import (
    STORE_DEMAND_SCHEMA,
    STORE_DEMAND_SPEC_YAML,
    store_demand_dataset,
)
from mapi_sdk import InprocExecutor
from mapi_spec.executor import ExecState, RunEventType, RunKind, RunSubmit

history = store_demand_dataset(stores=4, skus=2, weeks=60, seed=1)
recent = history.isel(week=slice(-8, None))  # a window of fitted weeks to re-score

executor = InprocExecutor(
    # dataset refs in specs and requests resolve to in-memory datasets
    resolver={
        "dataset://retail/store_sku_weekly@latest": history,
        "dataset://retail/last_8_weeks@v1": recent,
    },
)
print(executor.caps().isolation.name)  # NONE: your own code, in your own process

    Submit, wait, score¶

    async def main() -> None:
    fit = await executor.submit(
        RunSubmit(
            run_id="fit-001",
            kind=RunKind.FIT,
            payload={
                "spec": STORE_DEMAND_SPEC_YAML,
                "raw_schema": STORE_DEMAND_SCHEMA.model_dump(mode="json"),
            },
        ),
        nonce="nonce-fit-0001",  # resubmitting the same nonce returns the same run
    )
    status = await executor.wait(fit, timeout=300)
    print(status.state)  # succeeded
    for event in executor.events(fit):  # the same event stream a cloud run will produce
        if event.type is RunEventType.PROGRESS:
            print(event.seq, event.payload.get("message"))  # 2 validated the spec and the data

    executor.put_bundle("store-demand@1", executor.result(fit))
    score = await executor.submit(
        RunSubmit(
            run_id="score-001",
            kind=RunKind.SCORE,
            payload={
                "bundle": "store-demand@1",
                "request": {
                    "apiVersion": "mapi/v1",
                    "kind": "ScoreRequest",
                    "model": "endpoint://retail/store-demand-xgb",
                    "mode": "predict",
                    "data": "dataset://retail/last_8_weeks@v1",
                },
            },
        ),
        nonce="nonce-score-0001",
    )
    assert (await executor.wait(score, timeout=300)).state is ExecState.SUCCEEDED
    tree = executor.result(score)  # an xr.DataTree, exactly what score_bundle returns
    print(dict(tree["summary"].to_dataset()["y_hat"].sizes))
    # {'stat': 3, 'store_id': 4, 'sku': 2, 'week': 8}


asyncio.run(main())  # in Jupyter: `await main()`

    What to notice:

    • Payloads are JSON. The spec travels as YAML text or a dict, the raw schema as a dict, and data only as references. This is exactly what the API will store and what a sandboxed runner will receive.
    • Submissions are idempotent. Re-submitting with the same nonce returns the same handle, so a retried API call never starts a second fit. adopt(nonce) finds a run after a restart.
    • Status is the source of truth. Events are for progress bars; status() and wait() decide whether a run succeeded. Failures come back as RFC 7807 problems with a stable code.
    • Cancellation is cooperative. cancel(handle) is checked between pipeline phases and inside long fits.

    Isolation levels¶

    Every executor declares how strongly it isolates a run, and the platform refuses to send untrusted code to an executor that is not strong enough.

    Executor Isolation For Status
    InprocExecutor NONE Notebooks, tests, your own trusted code available
    Local process / Docker PROCESS / GVISOR Local platform, CI v0.2
    Cloud Run Jobs (gen2) MICROVM Hosted runs, one fresh sandbox per run v0.3

    Never run untrusted code in-process

    The in-process executor runs plugins with your permissions in your interpreter. It is for code you wrote or trust. Public plugins only ever run in the sandboxed executors.

    See the roadmap for the sandbox design.
