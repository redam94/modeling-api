    Pipelines, stages and replay¶

    A pipeline is an ordered list of steps. Each step is a small, versioned transform with typed settings and, if it learns something, a fitted state. The promise of the platform is simple to state and fiddly to keep:

    Scoring replays exactly the preprocessing that was learned at fit time. It never refits.

    This page explains the pieces that keep that promise: stages, the split stage, context tails, inverse transforms and scenario entry points.

    Steps¶

    A step implements fit (learn, on train only), transform (apply; never learns) and, when it can, inverse. A complete one, from the porting guide:

    A scaling step, in full 
    from typing import ClassVar

from mapi_sdk import Step, StepContext, StepSettings, StepState
from mapi_spec import StepKind
from pydantic import Field, JsonValue


class ScaleSettings(StepSettings):
    vars: list[str]
    over: list[str] = Field(default=[])  # plain defaults: the exported JSON Schema keeps them
    unseen_levels: str = "error"  # error | pooled | fill: what a new level's scale becomes
    fill_value: float = 1.0  # the scale used by 'fill'


class ScaleStep(Step[ScaleSettings, StepState]):
    """Divide each variable by its mean absolute value over `over` (learned on train)."""

    id = "acme.scale"
    version = "1.0.0"
    kind = StepKind.VALUE
    Settings = ScaleSettings
    State = StepState  # stateful: fitted on the training data only
    invertible = True
    var_params = ("vars",)  # settings that name variables ...
    dim_params = ("over",)  # ... and dims, so the control plane can check them
    unseen_levels_param = "unseen_levels"
    effect_template: ClassVar[dict[str, JsonValue]] = {  # static: how the schema changes
        "template_params": ["vars"],
        "updates": {"{*vars as v}": {"units": "1"}},
    }
    summary = "Divide by the mean absolute value over the named dims"  # catalog and UI text
    summary_plain = "Puts each series on a comparable scale"

    def fit(self, ds: xr.Dataset, s: ScaleSettings, ctx: StepContext) -> StepState:
        return StepState(arrays=xr.Dataset({f"scale__{v}": abs(ds[v]).mean(s.over) for v in s.vars}))

    def _scale(self, v: str, ds: xr.Dataset, s: ScaleSettings, st: StepState, ctx: StepContext):
        state = st.array(f"scale__{v}")
        return ctx.align_state(state, ds, s.unseen_levels, fill_value=s.fill_value)

    def transform(self, ds, s, st, ctx):  # never learns; skips absent vars (the target at score)
        return ds.assign({v: ds[v] / self._scale(v, ds, s, st, ctx) for v in s.vars if v in ds})

    def inverse(self, ds, s, st, ctx):
        return ds.assign({v: ds[v] * self._scale(v, ds, s, st, ctx) for v in s.vars if v in ds})

    Every step has a kind:

    Kind Changes Inverted on the way out? Examples
    reshape Structure: dims, frequency, layout Never resample, to_long, stack, filter_coords
    value Values of existing variables Yes, if invertible fx_convert, mean_scale, standardize, log1p
    feature Adds new variables Not needed lag, fourier, calendar, one_hot, formula

    And a static schema effect: a JSON template that says how the step changes the schema (adds lag dim, sets units to 1, turns daily date into weekly time). The control plane uses it to propagate the schema through the whole pipeline without running anything.

    Stages¶

    A stage is the dataset after a named step; raw is the bound input. Static validation computes the schema at every stage, so problems surface before any data is read:

    from mapi_plugin_mmm.examples import E33_SPEC_YAML, e33_dataset, e33_raw_schema
from mapi_sdk import default_registry
from mapi_spec import load_model_spec, validate_spec

catalog = default_registry().catalog()  # static JSON: settings schemas + schema effects
data, _ = e33_dataset(weeks=12)
raw_schema = e33_raw_schema(data)

check = validate_spec(load_model_spec(E33_SPEC_YAML), catalog, raw_schema)
rs = check.resolved
for stage, schema in rs.stages.items():
    y, time = schema.vars["y"], schema.dims["time"]
    print(f"{stage:12} time={time.freq:6} y in {y.units:4} dims={', '.join(schema.dims)}")
# raw          time=D      y in LCU  dims=geo, channel, time
# to_eur       time=D      y in EUR  dims=geo, channel, time
# weekly       time=W-SUN  y in EUR  dims=geo, channel, time
# scale_spend  time=W-SUN  y in EUR  dims=geo, channel, time
# scale_y      time=W-SUN  y in 1    dims=geo, channel, time
# lags         time=W-SUN  y in 1    dims=geo, channel, time, lag
# season       time=W-SUN  y in 1    dims=geo, channel, time, lag, fourier_mode
# hols         time=W-SUN  y in 1    dims=geo, channel, time, lag, fourier_mode
print(rs.split_stage)  # weekly: the holdout is cut in whole weeks
print(rs.last_reshape_stage)  # weekly: outputs are inverted back to weekly EUR, not days

    Stages are how specs refer to points in the pipeline:

    • data.split.after_step: where the train/holdout split happens;
    • ScoreRequest.inputs_stage: where a scenario enters the pipeline;
    • the output space: the stage outputs are inverted back to.

    Where the split happens¶

    flowchart LR
    R["raw<br/>daily, LCU"] --> FX["to_eur<br/><i>stateless</i>"]
    FX --> W["weekly<br/><i>stateless reshape</i>"]
    W --> SPLIT{{"split<br/>last 8 weeks"}}
    SPLIT -->|train| SC["scale_spend, scale_y<br/><i>learn on train</i>"]
    SPLIT -.->|holdout| SC
    SC --> L["lags<br/><i>context tail</i>"]
    L --> M["model"]
    style SPLIT fill:#5eead4,stroke:#0f766e,color:#1e1b4b

    Some dims only exist after preprocessing: a holdout of "the last 8 weeks" cannot be cut from daily data before it is resampled. So the split happens at a stage. If after_step is not given, it defaults to the end of the stateless prefix, the leading steps that learn nothing (unit conversion, resampling).

    If a step that learns runs before the split, its state would be learned partly from the holdout and the evaluation would be optimistic. Validation reports it:

    leaky = E33_SPEC_YAML.replace("after_step: weekly", "after_step: scale_y")
for issue in validate_spec(load_model_spec(leaky), catalog, raw_schema).errors:
    print(issue.code, issue.pointer)
    print("  ", issue.message)
# LEAKAGE_RISK /data/split/after_step
#    stateful step 'scale_spend' (pipeline[2]) runs before the split at stage 'scale_y';
#    its state would be learned from holdout data
# LEAKAGE_RISK /data/split/after_step
#    stateful step 'scale_y' (pipeline[3]) runs before the split at stage 'scale_y'; ...

    Set allow_leakage: true on the split to downgrade the error to an acknowledged warning.

    Evaluate the way you will forecast¶

    fit.mode: evaluate_then_refit (the default) does this:

    sequenceDiagram
    participant D as Data
    participant P as Pipeline + model
    participant B as Bundles
    D->>P: stateless prefix on all data, then split at the split stage
    P->>P: fit step states + model on TRAIN
    P->>P: score HOLDOUT through the score path<br/>(context tails from train)
    P->>B: evaluation bundle + metrics
    P->>P: refit states + model on ALL data
    P->>B: production bundle (links evaluation + metrics)

    The holdout is never scored by a separate code path: it goes through score_bundle, with the context it would have in production. Then everything is refitted on all data, so the context tails and terminal states that forecasts start from are the latest ones. train_only stops after evaluation and keeps the train fit.

    Context tails: looking back across the fit boundary¶

    Steps that look back in time (lags, carry-over) declare a context need, for example {along: time, n: 6, within: [geo]}. At fit time the step stores the last n rows of its own input stage, per group. At score time the platform prepends them before transforming, checks that the new data continues the fitted range, and drops them from the output.

    flowchart LR
    subgraph Fit
        T1["… w49 w50 w51 w52"] --> TAIL["stored tail per geo:<br/>w47–w52 (weekly, scaled)"]
    end
    subgraph Score
        TAIL --> CAT["w47–w52 ‖ w53 w54 w55 w56"]
        NEW["forecast payload<br/>w53–w56"] --> CAT
        CAT --> LAG["lag_tensor"] --> DROP["drop context rows"] --> OUT["w53–w56 with<br/>real carry-over"]
    end

    The result is identical to transforming the whole series at once; the contract kit checks this "context-window equivalence" for every step and model. A new market has no tail, so its lags are padded according to the step's settings (pad: first).

    Sequential models (HMMs, Kalman filters) keep a model-side terminal state instead; see Forecasting.

    Inverse transforms and the output space¶

    On the way out, the platform undoes invertible value steps in reverse order and stops at the last reshape step. A model fitted on weekly, scaled EUR returns weekly EUR: scaling can be undone, the weekly resample cannot (daily values are not recoverable from weekly sums).

    Every output records where it ended up:

    Attribute Example Meaning
    output_space {"y_hat": "weekly"} The stage the values live at
    units EUR Units after inversion
    retransform {"y_hat": "median"} For point models through a non-linear inverse: the inverse of a mean is not a mean, so the value is labelled (or Duan smearing is used)

    Ask for output: {units: model} to skip inversion, for example to get contributions that add up exactly through a log1p.

    Scenarios enter at a stage¶

    A planner should not have to invent daily local-currency spend to ask about a weekly EUR budget. ScoreRequest.inputs_stage lets data enter the pipeline after a named step; the steps before it, and the side tables they need, are skipped:

    mode: forecast
horizon: {dim: time, periods: 8}
inputs_stage: weekly        # send weekly EUR spend; to_eur and the FX table are skipped

    The E33 conformance fixture checks that this gives exactly the same forecast as the raw daily path for the same spend.

    Models that own their preprocessing¶

    Some models do their own scaling or carry-over (pymc-marketing's MMM does both). They declare owns: [scaling, carryover, inverse_units] in their capabilities, the platform steps aside, and outputs are labelled as already in original units. See the pymc-marketing adapter.

    Recursion¶

    A lag of the target is a recursive feature: forecasting more periods than the smallest lag would need predictions as inputs. v1 forecasts are direct, so such specs are rejected with RECURSIVE_UNSUPPORTED unless the model declares owns: [recursion].
