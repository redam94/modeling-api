    Roadmap¶

    modeling-api ships as three products, in this sequence:

    1. A typed modelling runtime.
    2. A job platform around the runtime.
    3. A hosted platform for many users.

    Some rules make the hosted platform safe. These rules are in the code from the first release: no pickle, contracts in JSON only, static validation, sanitized plots, and sandboxed runs with verified outputs.

    Milestone names

    The plan before v0.5 gave the names M4 and M5 to plugin upload and to public code upload. The releases used these names for tree datasets (M4) and the science gallery (M5). Plugin upload, the MCP server and public code upload are not done. They have no release number yet.

    What v0.9 contains¶

    • Eleven new science models from the pymc-challenges case studies, 15 sci.* models in all. They are for images, fields, maps, graphs, trees of species and angles (models reference).
    • 14 plot recipes: maps, networks (net.graph), trees, polar charts, image checks, colour swatches and posterior views (core.pair, core.ridge, core.rank_matrix, core.calibration, core.state_sequence) (plot reference).
    • Workflow nodes for Bayesian models: model.summary, evaluate.ppc, compare.stacking, model.score and plot.render. Plots also go into reports (Bayesian models in a workflow).
    • Tree datasets in workflows: model.fit and model.backtest take nodes and join (Tree datasets in a workflow).
    • Six workflow recipes: model ladders (sci_spatial_ladder, sci_network_ladder, sci_phylo_signal), sci_calibrate_then_design, bayes_workflow_audit and sci_image_model_check (workflow cookbook).
    • Circular outputs (OutputDecl.circular): the holdout metrics and the score summaries of an angle are on the circle (Circular outputs).
    • Tutorials for the 15 case studies, and the complex workflows tutorial. The command python -m mapi_plugin_science.export makes datasets that you can upload from the data of pymc-challenges.

    We did the steps of the E18, E51 and E21 tutorials on a live dev stack, in a browser. Only sci_spatial_ladder ran end to end on a live dev stack. The six recipes run through the server orchestrator in a slow test, with small fits. The same as for v0.5, no part of v0.9 ran on real Google Cloud or in Docker. These items are not done yet:

    • governance.check with sensitivity.prior cannot find the prior widths of sci.areal_bym2, so the check is skipped.
    • The graph check of the network ladder does not mark the statistics of the observed network.
    • core.prior_predictive cannot draw the prior draws of sci.heat_plate. Some science models keep no prior draws.
    • A backtest of a tree dataset gives the full tree to each fold. search.grid has no nodes parameter.
    • The HTML report does not show plot sections.
    • Some fits mix slowly: sci.turing_pattern at the size of the notebook, and the latent-space fit of sci.network_latent_space with covariates.

    Read the changelog for the full list. Some of the case studies of pymc-challenges are not ported yet.

    What v0.5.1 to v0.8 contain¶

    • v0.5.1, forecasts with actuals. All twelve statsmodels models can forecast from actuals with their fitted parameters. Other models refuse with ACTUALS_NOT_SUPPORTED (Forecasts with actuals).
    • v0.6, the spec builder. Completions, hover text and settings checks in the YAML editor come from the catalog of the tenant. The Insert panel and the Visual view edit the same document. This release changed only the web app.
    • v0.7, scientific models. sci.lgcp_grid, sci.fisher_kpp, sci.traction_force and sci.strong_lens. OutputDecl.grid declares an output on a grid (Capabilities). The Score page guides each request in steps.
    • v0.8 (M4), tree datasets. A dataset version can hold an xr.DataTree. A guard does a check of each HDF5 file in the sandbox before it opens the file. A model can declare input: tree to get the full tree (Tree datasets). The catalog shows each plot recipe as a card with an example picture.

    The web flows for trees ran against the mock API only. The real server and runner path ran in the end-to-end test. The v0.6 spec builder ran in the unit and Playwright smoke tests against the mock API.

    What v0.5 contains¶

    • Workflows: versioned DAGs of statistical tests, transforms, branches, split plans, order searches, model fits, evaluations, comparisons, governance and reports. Also live events, a cache, schedules and dataset triggers (cookbook).
    • Governance: versioned project and tenant policies and twelve checks. The checks include null tests against shuffled targets and placebo regressors. Also second-person approval, evidence packs and promotion that needs validation (null tests explained).
    • Data and Model Explorers, with side-by-side comparisons and Diebold-Mariano tests
    • mmm-framework as the marketing-mix engine, with budget optimisation in the sandbox
    • Twelve statsmodels time-series models
    • About cards on each item that you can select, and Help me choose (choosing a model)
    • The Python client and the CLI for all of these items
    • The screens of the web app for all of these items: the visual workflow builder, the run monitor, Guided recipes, the policy editor, the review queue, the explorers, About cards and the chooser, and budget plans

    We verified these items end to end on a live local stack (M3.5 verification):

    • the canonical workflow
    • governance with a second person
    • mmm-framework with a budget plan
    • the explorers and the chooser
    • the CLI.

    Some work is not done yet, the same as for v0.4. It includes a real Google Cloud project, Docker-isolated executors, and the sessions with five non-technical testers.

    What v0.4 contains¶

    • Guided mode: four templates (geo marketing mix, weekly forecast, demand by store, customer choice). Also a question flow with role detection, drafts with "View as YAML", and the persona lock (tutorial).
    • Sandboxed ingest of CSV, Parquet, MFF and Meridian-shaped tables. Refusals are in plain language.
    • Business priors as ROI or share ranges. A sandbox translates them and shows a prior-predictive preview. Also lift tests as calibration (Guided modelling).
    • The sanity scorecard that each fit writes, and the promotion gate that uses it
    • What-if sliders over response grids for each draw, "Run exact", and forecast and counterfactual views
    • Endpoints and aliases, score:<alias> tokens, snippets in seven languages, and a Google Sheets card (Connect Google Sheets)
    • Signed webhooks with an outbox, retries, a delivery log, replays and an SSRF guard (Receive webhooks)
    • Saved plots, static renders and embed links (Embed a chart)
    • The endpoints of the Python client, and new CLI commands
    • Sign-up with e-mail verification and abuse controls, tenant deletion, the GDPR export, and a Cloud Armor policy
    • The Integrations hub, trust pages and admin additions in the web app

    We verified these items end to end on a laptop (M3 verification). The exit of M3 also needs the sessions with five non-technical testers. These sessions are not done yet. Some work against a real Google Cloud project is not done yet, the same as for v0.3:

    • the [verify M0] checklist
    • cold-start measurements
    • public workspaces on an executor that enforces egress and DNS.

    Planned: expert plugins and MCP¶

    Plugin upload for allow-listed experts. Experts upload their own model plugins. The platform builds them into hash-pinned overlays, with native wheels from a curated mirror. The contract kit checks each plugin on upload. Also fast dev overlays and a vetted tier of ported sibling models.

    An MCP server gives AI assistants and agents a small, curated set of tools that are safe from injection. The tools list and describe models, score an endpoint, read a run and get a plot.

    Budget optimisations already run as in-sandbox optimize jobs, and backtests run as workflow nodes (v0.5). Sweeps are workflows with a search.grid node (v0.14 retired the Sweep document). SBC runs as one parent. More.

    After expert plugins¶

    This is the planned sequence:

    1. Public code upload: uploaded plugins for all tenants. This release needs these controls:

      • a separate execution project
      • signed base images
      • verification before code runs
      • Sybil controls
      • a takedown process
      • a rehearsed kill-switch drill
      • an external penetration test.

      The security suite must first be green for two weeks. 2. Scale and depth. Each item comes when real usage needs it: - warm scorers for exact answers in less than one second - GPU and large-data executors - other clouds - recursive forecasting - chained models (full-funnel and KPI graphs) - a plugin marketplace with a consent model.

    Dates

    We cut a release when it passes its exit criteria, not on a calendar date. Read the changelog to see the changes that we released.
