    The HTTP API v0.2¶

    Everything the web app, the CLI and the Python client do is a call to the versioned /v1 HTTP API. This guide does the main flow with curl and jq, so you can see every request. The script is docs/snippets/http_tour.sh; make e2e runs it against a live stack. The outputs below are from one of those runs, shortened.

    Where What
    HTTP API reference Conventions, errors, pagination, idempotency, SSE and every endpoint with its DTOs
    OpenAPI explorer The OpenAPI 3.1 document, browsable, with every schema and example
    GET /openapi.json on a running API The same document, served by the API itself
    Error codes Every stable error code and its HTTP status

    Start the stack and load the demo first: make dev, make seed, uv run python scripts/seed.py --export demo/ and uv run mapi datasets upload demo/eu_media_future.zarr.zip --name eu_media_future (see the quickstart).

    From v0.3, make dev requires sign-in. Set MAPI_TOKEN to an API token (the web app's Tokens page, or mapi tokens create) and MAPI_PROJECT to the <tenant>/<project> it acts in. The script's api function then adds Authorization: Bearer … and X-Mapi-Project to every API call. It never sends them to signed storage URLs, which carry their own authorization. See authentication.

    Health and the catalog¶

    API=${MAPI_API_URL:-http://127.0.0.1:8000}
api() {  # curl the API; signed in when MAPI_TOKEN is set (every multi-tenant stack, v0.3)
  if [ -n "${MAPI_TOKEN:-}" ]; then
    curl -s -H "Authorization: Bearer $MAPI_TOKEN" \
      -H "X-Mapi-Project: ${MAPI_PROJECT:-default/default}" "$@"
  else
    curl -s "$@"
  fi
}
curl -s "$API/readyz" | jq -c '{status, version, checks: .checks | map_values(.status)}'
api "$API/v1/catalog/models" \
  | jq -r '.items[].manifest | "\(.id)@\(.version)  \(.capabilities.representation)"'

    {"status":"ok","version":"0.4.0","checks":{"postgres":"ok","object_store":"ok","catalog":"ok"}}
mmm.hierarchical_geo@1.3.0  draws
mmm.pymc_marketing@1.0.0  draws
sklearn.tabular_bootstrap@1.0.0  draws
…
ts.hsgp_trend@1.0.0  draws

    /healthz says the process is alive; /readyz checks PostgreSQL, the object store and the catalog, and answers 503 with the same body when one is not ready. The catalog is what the runner image provides, exported by a sandboxed describe run; specs are validated against it.

    Upload a CSV¶

    Data never passes through the API. You create a dataset, ask for an upload session, and PUT the bytes to the signed URL it returns:

    DS=$(api "$API/v1/datasets?limit=200" | jq -r '.items[] | select(.name == "weekly_sales") | .id')
if [ -z "$DS" ]; then
  DS=$(api -X POST "$API/v1/datasets" -H 'Content-Type: application/json' \
    -d '{"name": "weekly_sales", "description": "a CSV upload from the HTTP guide"}' | jq -r .id)
fi
echo "dataset $DS"
printf 'week,sales\n2026-01-04,120\n2026-01-11,131\n2026-01-18,127\n2026-01-25,140\n' > sales.csv
SIZE=$(wc -c < sales.csv | tr -d ' ')
UP=$(api -X POST "$API/v1/datasets/$DS/uploads" -H 'Content-Type: application/json' \
  -d "{\"filename\": \"sales.csv\", \"content_type\": \"text/csv\", \"size_bytes\": $SIZE}")
HEADERS=()  # the signed URL binds these headers: send them exactly
while IFS= read -r h; do HEADERS+=(-H "$h"); done \
  < <(jq -r '.upload.headers | to_entries[] | "\(.key): \(.value)"' <<<"$UP")
curl -s -o /dev/null -w 'PUT %{http_code}\n' -X PUT "${HEADERS[@]}" \
  --data-binary @sales.csv "$(jq -r .upload.url <<<"$UP")"

    dataset ds_01m4zy65cdbxtaa4vgsvpeb4rt
PUT 200

    The URL is a V4-style signed URL for one object in the quarantine bucket, valid for an hour. Send the headers from upload.headers exactly, because they are part of the signature: content-type must be the one you declared, x-goog-content-length-range caps the size at size_bytes, and x-goog-if-generation-match: 0 makes the object write-once, so a second PUT to the same URL is rejected.

    Then turn the upload into a dataset version. For CSV and Parquet the mapping names the column of every dim and variable, with its kind, score-time policy and role:

    MAPPING='{
  "format": "csv",
  "dims": {"week": {"column": "week", "spec": {"kind": "time", "policy": "extend", "freq": "W-SUN"}}},
  "vars": {"sales": {"column": "sales", "role": "target", "units": "units"}}
}'
DV=$(api -X POST "$API/v1/datasets/$DS/versions" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d "{\"upload_id\": $(jq .id <<<"$UP"), \"mapping\": $MAPPING}")
V=$(jq -r .version <<<"$DV")
STATUS=ingesting
while [ "$STATUS" = ingesting ]; do  # a sandboxed ingest run parses and checks the file
  sleep 1
  STATUS=$(api "$API/v1/datasets/$DS/versions/$V" | jq -r '.status // "ingesting"')
done
api "$API/v1/datasets/$DS/versions/$V" | jq '{ref, status, dims: .data_schema.dims | keys}'

    {
  "ref": "dataset://default/weekly_sales@v1",
  "status": "ready",
  "dims": ["week"]
}

    POST …/versions answers 202 with the version in status ingesting and the id of the sandboxed ingest run that parses the file. It accepts an Idempotency-Key: a retried request with the same key and body returns the same version instead of ingesting twice.

    Validate and fit a spec¶

    jq -Rs '{yaml: .}' demo/eu-geo-mmm.yaml \
  | api -X POST "$API/v1/specs:validate" -H 'Content-Type: application/json' -d @- \
  | jq '{valid, issues: [.issues[] | {code, pointer}], stages: [.stages[] | .name]}'

    {
  "valid": true,
  "issues": [],
  "stages": ["raw", "to_eur", "weekly", "scale_spend", "scale_y", "lags", "season", "hols"]
}

    POST /v1/specs:validate answers 200 even for an invalid spec: the verdict is in valid and every problem is in issues with its code and JSON pointer. Non-2xx statuses are kept for requests that cannot be validated at all (unparseable YAML, too large).

    SPEC=$(api "$API/v1/specs?limit=200" | jq -c '.items[] | select(.name == "eu-geo-mmm")')
RUN=$(api -X POST "$API/v1/runs" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d "{\"kind\": \"fit\", \"spec_id\": $(jq .id <<<"$SPEC"), \"revision\": $(jq .latest_revision <<<"$SPEC")}" \
  | jq -r .id)
echo "run $RUN"

    POST /v1/runs answers 201 with the run in state created or queued. The same Idempotency-Key with the same body answers 200 with the same run; with a different body, 409 IDEMPOTENCY_CONFLICT. Generate one key per user intent and reuse it on retries.

    Follow the run¶

    # server-sent events: a snapshot, the persisted events, live progress, then `end`
api -N -H 'Accept: text/event-stream' "$API/v1/runs/$RUN/events" | grep '^event:' | uniq -c
api "$API/v1/runs/$RUN" | jq '{state, output_model_version_id}'

       3 event: snapshot
   1 event: state
   1 event: warning
   2 event: state
   6 event: progress
   1 event: state
   5 event: diagnostic
   3 event: metric
   1 event: state
   1 event: complete
   1 event: state
   2 event: snapshot
   1 event: end
{
  "state": "succeeded",
  "output_model_version_id": "mv_01m4zy6yc82qy97jzjmv9phv1j"
}

    With Accept: text/event-stream the events endpoint is a live stream: a snapshot of the run first, then the persisted events (each with an id:), live progress and log frames (no id, never replayed), a fresh snapshot on every state change, and end when the run is terminal, after which the server closes the stream. Reconnect with Last-Event-ID: <id> to resume exactly after the last persisted event. Without that Accept header the same URL returns the persisted events as a JSON page. See Run events.

    Read the model version¶

    MODEL=$(api "$API/v1/models?limit=200" | jq -c '.items[] | select(.name == "eu-geo-mmm")')
M=$(jq -r .id <<<"$MODEL")
MV=$(jq -r .latest_version <<<"$MODEL")
api "$API/v1/models/$M/versions/$MV" \
  | jq '{ref, scorecard: .scorecard.overall, metrics, signed: .manifest.signature.alg}'

    {
  "ref": "model://default/eu-geo-mmm@v1",
  "scorecard": "warn",
  "metrics": {"mape": 7.59, "elpd_loo": 183.47, "coverage_90": 0.875},
  "signed": "KMS-EC-P256-SHA256"
}

    GET …/artifacts/{name} returns a signed GET URL for any bundle object or ui/ view. It is minted only after the server has verified the version's signed manifest; each link is pinned to an object generation, supports HTTP Range requests and expires after 15 minutes.

    Score¶

    RES=$(api -X POST "$API/v1/models/$M/versions/$MV:score" \
  -H 'Content-Type: application/json' -H 'Prefer: wait=60' -H "Idempotency-Key: $(uuidgen)" \
  -d '{"request": {
        "apiVersion": "mapi/v1", "kind": "ScoreRequest",
        "model": "model://default/eu-geo-mmm@latest",
        "mode": "forecast",
        "horizon": {"dim": "time", "periods": 8},
        "data": "dataset://default/eu_media_future@latest",
        "side_tables": {"fx": "dataset://default/fx_daily@latest"}}}')
jq '{done, state: .run.state, outputs: [.outputs[] | {name, size, crc32c}]}' <<<"$RES"
curl -s "$(jq -r '.outputs[] | select(.name == "result.json") | .url' <<<"$RES")" \
  | jq '{mode, representation, output_space}'

    {
  "done": true,
  "state": "succeeded",
  "outputs": [
    {"name": "plots.json", "size": 4122, "crc32c": "d8PGZA=="},
    {"name": "result.json", "size": 406, "crc32c": "PonvmQ=="},
    {"name": "score.zarr.zip", "size": 9396, "crc32c": "Uwymhw=="},
    {"name": "ui/summary.arrow", "size": 27266, "crc32c": "hxiS8w=="}
  ]
}
{
  "mode": "forecast",
  "representation": "draws",
  "output_space": {"contributions": "weekly", "y_hat": "weekly"}
}

    Prefer: wait=60 holds the request until the score run finishes (at most 60 seconds) and answers 200 with done: true and signed links to the outputs. If it takes longer the answer is 202 with done: false: repeat the request with the same Idempotency-Key to get the same run's result, or follow the run. The response header Preference-Applied says which wait the server used. Over HTTP the ScoreRequest needs its apiVersion and kind (the Python client fills them in).

    Errors¶

    api -X POST "$API/v1/models/$M/versions/$MV:score" -H 'Content-Type: application/json' \
  -d '{"request": {"apiVersion": "mapi/v1", "kind": "ScoreRequest",
       "model": "model://default/eu-geo-mmm@latest", "mode": "filter",
       "data": "dataset://default/eu_media_future@latest"}}' | jq '{status, code, detail}'

    {
  "status": 422,
  "code": "MODE_NOT_SUPPORTED",
  "detail": "validation failed with 2 errors; first at /mode: model 'mmm.hierarchical_geo@1.3.0' does not support mode 'filter'"
}

    Every error is an RFC 7807 problem document (application/problem+json) with a stable code, an HTTP status, and every individual problem in errors[] with a JSON pointer. Tracebacks and plugin messages only ever appear in an untrusted_text field; render them as text. The score request above was rejected statically: no run was created.

    Other clients¶

    The OpenAPI document is generated from the server itself (apps/web/scripts/gen_openapi.py writes apps/web/openapi.json, and CI fails if it drifts), so any OpenAPI generator produces a typed client. The web app's TypeScript client is generated that way (openapi-typescript and openapi-fetch). For Python, use mapi_client.
