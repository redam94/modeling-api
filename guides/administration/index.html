    Administration v0.3¶

    From v0.3 one deployment serves many organisations. This guide is for the people who look after it: who may do what, how compute is limited and paid for, and what to do when something goes wrong. The concepts behind it are in Tenancy and authentication and Quotas and cost; signing in is in Authentication.

    There are three administrative jobs, and the platform keeps them apart:

    Who Holds Works in Does
    Platform operator A verified e-mail listed in MAPI_OPERATOR_EMAILS, signed in Admin console, mapi admin …, /v1/admin/* Creates and suspends tenants, sets trust tiers and quotas, flips kill switches, watches executors, reads every audit log. Never reads tenant content (datasets, specs, models, plots)
    Tenant admin The admin role, tenant-wide Members, Usage (Organisation), /v1/tenants/{tenant}/… Creates projects, adds and removes people, reads the tenant's bill and audit log
    Project admin The admin role in one project Members, Tokens, Usage Manages that project's members, endpoints, plugins and everyone's tokens there

    Every example on this page is one walkthrough, docs/snippets/admin_tour.sh, which the test suite runs against a development stack (make dev). It signs in through the development identity provider twice: as admin@dev.local (a platform operator) and as analyst@dev.local (who becomes the new tenant's admin).

    API=${MAPI_URL:-${MAPI_API_URL:-http://127.0.0.1:8000}}
export MAPI_URL=$API
dev_login() {  # dev profile only: an ID token for one seeded account, valid for an hour
  python -c 'import sys; from mapi_client.oidc import dev_idp_login
print(dev_idp_login(sys.argv[1], sys.argv[2]))' "$API" "$1"
}
OPERATOR=$(dev_login admin@dev.local)          # a platform operator
TENANT_ADMIN=$(dev_login analyst@dev.local)    # becomes the new tenant's admin below
MAPI_TOKEN=$OPERATOR mapi whoami

    On a real deployment each person runs mapi login instead (see Authentication). Operator commands always need a sign-in: an API token never carries operator powers, even its owner's.

    Tenants¶

    A tenant is an organisation: the boundary of billing, isolation and quotas. PostgreSQL row-level security keeps every tenant's rows apart, and every storage key starts with t/{tenant}/. Only operators create tenants:

    export MAPI_TOKEN=$OPERATOR
mapi admin tenants create "$TENANT" --name "Acme Retail" --tier verified \
    --residency eu --admin-email analyst@dev.local --yes
mapi admin tenants ls
    Field Values Effect
    id A lowercase slug (acme) Part of every reference (dataset://growth/eu_media_daily lives in a tenant's project) and storage key; it cannot change
    Trust tier internal, verified, public, self-hosted-trusted Where the tenant's runs may execute, and its default quotas (below)
    Status active, suspended, deleting suspended: people can read and download, but nothing can be created, changed or run. deleting: no access at all
    Data residency eu, us, asia or one region (europe-west1) Runs are placed only on executors in a matching region. Changing it applies to new runs only
    Admin e-mail Any address Invited as tenant admin. The invitation is claimed at that person's first sign-in with that verified e-mail

    The Admin console (operators only; everyone else sees an explanation instead) lists every tenant with its tier, status and residency. New tenant and Edit do the same as the commands above. Suspending or deleting asks for a reason and for the tenant's id, typed out.

    Suspending is the reversible way to stop an organisation: its people keep read access to their work, and every change, upload and run is refused with 403 FORBIDDEN. Operators can still act on the tenant.

    mapi admin tenants update "$TENANT" --status suspended --reason "contract ended" --yes
mapi admin tenants update "$TENANT" --status active --yes

    Trust tiers¶

    The tier decides where a tenant's code may run, and this is enforced by the dispatcher in code, never by tenant configuration: a run whose executor does not meet its tenant's requirement is never submitted. The dispatcher fails it with INFRA_ERROR and a detail naming the requirement (for example verified tenants require an executor with isolation >= gvisor and enforced egress/DNS). The tier also sets the tenant's default quotas until an operator overrides them.

    Tier Executor must provide vCPU-s / day vCPU-s / month Concurrent runs Fan-out tasks Largest class Storage Egress / month Requests / min
    internal isolation ≥ process — — 100 1,000 — — — 6,000
    self-hosted-trusted isolation ≥ process — — — — — — — —
    verified isolation ≥ gvisor, egress and DNS enforced 86,400 1,000,000 20 256 L 100 GiB 100 GiB 600
    public isolation ≥ gvisor, egress and DNS enforced 3,600 36,000 2 16 S 2 GiB 5 GiB 60

    Platform-wide (global) defaults: concurrent_runs = 700. A dash means no limit at that level.

    Which executors can take verified and public tenants today

    Shared tiers need an executor with gVisor or microVM isolation and enforced egress and DNS. In v0.3 that is:

    • cloudrun-jobs, once MAPI_CLOUDRUN_DNS_ENFORCED=true. It is false by default, because the DNS response policy has not yet been verified against a real Cloud Run Jobs execution (the first item of the M0 checklist). Until then, verified and public runs fail at dispatch rather than run somewhere weaker.
    • docker-gvisor, only with MAPI_DOCKER_NETWORK=none, which needs an HTTPS bootstrap URL; with the local GCS shim it is not available.

    internal and self-hosted-trusted tenants run anywhere, including local-process (which refuses to start at all under MAPI_PROFILE=multi-tenant).

    Projects and members¶

    A project is a workspace inside a tenant and the unit of access control. Tenant admins create projects and decide who works in them; there is no CLI command for members yet, so the walkthrough uses the HTTP API:

    as_admin -X POST "$API/v1/tenants/$TENANT/projects" \
    -d '{"id": "growth", "name": "Growth marketing"}' | jq -c '{tenant_id, id, name}'
as_admin -X POST "$API/v1/tenants/$TENANT/projects/growth/members" \
    -d '{"email": "viewer@dev.local", "role": "runner"}' | jq -c '{project_id, email, role}'
as_admin "$API/v1/tenants/$TENANT/members" \
    | jq -r '.items[] | "\(.email // .principal_id)\t\(.role)\t(tenant-wide)"'
as_admin "$API/v1/tenants/$TENANT/projects/growth/members" \
    | jq -r '.items[] | "\(.email // .principal_id)\t\(.role)\t\(.project_id // "(tenant-wide)")"'

    A membership grants one role, either on one project or tenant-wide (on the tenant and every project in it). In a project, a person's effective role is the higher of the two. Membership is read at every request, so removing someone from a project immediately disarms their sessions and their tokens there.

    Members shows the project's members (or, with Organisation, the tenant-wide grants). Admins change a role in place, remove a member, or Add member by e-mail: an address nobody has signed in with yet becomes an invitation, claimed at first sign-in. A grant marked organisation comes from a tenant-wide membership and is changed there.

    Roles¶

    There are four roles, each including the one before it. Running sits above editing on purpose: compute costs money, so someone can be trusted to edit a spec without being able to start a 200-task sweep.

    Role Adds
    viewer Read everything in the project; validate specs; mint tokens for themselves
    editor Create and change datasets, specs and saved plots
    runner Spend compute: submit, cancel and retry runs, score models and endpoints, render plots
    admin Manage members, endpoints, plugins and other people's tokens; delete things

    API tokens¶

    Programs (the Python client, the CLI in CI, Atlas, BI exports) use API tokens. A token is minted by a person in one project, acts as that person narrowed by its scopes, and is bound to that project. Anyone with a role can mint tokens for themselves; project admins can list and revoke everyone's.

    export MAPI_TOKEN=$TENANT_ADMIN
mapi use "$TENANT/growth"
mapi tokens create nightly-report -s models:read --expires-in-days 30 --rate-limit 60 \
    --budget 3600 --budget-period day > nightly-report.token   # the secret, once
mapi tokens ls

    New token asks for a name, the scopes, optional endpoint aliases, an expiry (default 90 days, at most 365), a requests-per-minute limit and a vCPU-second budget per day or month. It names your role, which is the most any of your tokens can do.

    The secret is shown once. The server stores only an HMAC of it, so a lost token is revoked and replaced, never recovered. Revoking takes effect on the next request.

    Quotas¶

    Compute is limited in vCPU-seconds, at three levels checked in order: the token's own limits, the tenant's policy (or its tier's defaults, above), and platform-wide limits that protect the cloud project. The first limit a request would exceed answers 429 with QUOTA_EXCEEDED or RATE_LIMITED, a detail naming the level and the limit, and Retry-After when it resets (Quotas and cost explains every limit). Operators override a tenant's defaults:

    export MAPI_TOKEN=$OPERATOR
mapi admin quotas set tenant "$TENANT" --vcpu-seconds-per-day 172800 \
    --concurrent-runs 40 --max-fanout-tasks 256 --storage 200GiB \
    --note "private beta customer" --yes
mapi admin quotas ls

    set replaces the policy: limits you leave out are removed, and the tier default applies to them again. mapi admin quotas rm tenant acme removes the override.

    Cost and usage¶

    Every run is estimated when it is submitted (and checked against the quotas with that estimate), then metered when each attempt ends: vCPU-seconds and GiB-seconds of its resource class, at the deployment's versioned price table, written to an append-only cost ledger. Amounts are exact integer micros of a currency, and each names the price table it used. A run's page and mapi runs get show its cost; usage pages add it up.

    mapi usage --group-by resource_class             # the selected project, this UTC month
mapi usage --tenant "$TENANT" --period day       # the whole tenant today (tenant admins)

    Usage shows a project's (or, with Organisation, the whole tenant's) cost, compute, runs and memory for a UTC day or month; a daily chart; how close each quota is (warnings at 70 % and 90 %); and the totals by token and by resource class. Anyone in a project sees its usage; the tenant-wide view needs a tenant-wide admin. The amounts are an estimate of compute cost at list prices, not an invoice.

    Kill switches¶

    Two platform-wide switches stop compute fast. Both are audited and need a reason:

    Switch Effect
    Uploaded code (untrusted_execution_enabled) Off: no run of tenant-uploaded plugin code is accepted or leased. Built-in models keep working
    Global spend cap Once the platform's spend in the current UTC day or month reaches the cap, no new compute starts except for internal tenants 
    mapi admin kill-switches set --spend-cap 500 --spend-cap-period month \
    --reason "private beta budget" --yes
mapi admin kill-switches get

    Turning off uploaded code is the first step of the sandbox-escape runbook (ops/runbooks/sandbox-escape.md). Spend opens a ticket at 70 % of the cap and pages at 90 % (Observability).

    Executors¶

    Executors in the admin console (and mapi admin executors ls) show each execution backend's health, isolation, resource classes, running and queued work, failures in the last hour, its jobs.run rate against the limit, and whether it has passed the executor conformance suite. trusted tenants only marks an executor that verified and public tenants can never be placed on.

    Audit log¶

    Security-relevant actions are appended to an audit log: sign-ins (and failed ones), tenant, project and membership changes, token creation, revocation and failed use, quota and kill-switch changes, quota denials, run creation and cancellation, integrity failures, artifact links and dataset downloads, and refused run events. Each entry records who (and whether as an operator), what, on which resource, the outcome and a problem code. IP addresses and user agents are kept only as keyed hashes: entries can be correlated, never reversed.

    mapi admin audit --tenant "$TENANT" -n 10        # operators: any tenant
# tenant admins: their own tenant's log
as_admin "$API/v1/tenants/$TENANT/audit?limit=5" \
    | jq -r '.items[] | "\(.ts)  \(.action)  \(.resource_kind):\(.resource_id)  \(.outcome)"'

    Tenant admins read their own tenant's log (GET /v1/tenants/{tenant}/audit); operators read everyone's in the Audit log tab or with mapi admin audit, filtered by tenant, project, actor, action, outcome and time.
