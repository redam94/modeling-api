    The command line v0.2¶

    mapi (package mapi-cli, Apache-2.0) works in two places:

    • locally, without any server: scaffold a spec, check it, fit it and score it in your own Python process with the installed plugins (new, check, fit, score, catalog, plugin, spec);
    • remotely, against the HTTP API of a running platform: upload datasets, fit, follow runs and score model versions (datasets, runs, and --remote on check, fit, score and catalog).

    Every command and option is listed in the generated CLI reference. The examples on this page are scripts that the test suite runs: the local ones in the default suite, the remote ones in make e2e.

    Running the commands

    make install puts mapi into the workspace environment. Either activate it (source .venv/bin/activate) or prefix every command with uv run (uv run mapi --help).

    Without a server¶

    Scaffold a spec from a template. --with-data also writes the matching conformance fixture's sample data (it needs the mapi-conformance package, which the workspace has):

    mapi new tabular -o spec.yaml --with-data     # an XGBoost demand model plus its sample data
    Template What it is Conformance fixture
    geo-mmm Hierarchical geo MMM (weekly EUR, adstock, saturation) E33
    forecast HSGP trend and seasonality forecast C08
    tabular XGBoost demand with quantile uncertainty xgb_store_demand
    glm Hierarchical GLM, long layout E02

    Check it statically against the installed plugins and the data's schema. --stages prints the schema after every pipeline step; the exit status is 1 when there are errors, so it works in CI:

    mapi check spec.yaml --data data.zarr.zip --stages

    Fit in-process. The bundle (zarr zip, sidecars, plots, metrics and the evaluation bundle of evaluate_then_refit) goes to bundles/<name>/; --side-table NAME=PATH supplies side tables:

    mapi fit spec.yaml --data data.zarr.zip       # in-process: writes bundles/<name>/
ls bundles/tabular

    mapi score request.yaml --bundle bundles/<name> --data future.zarr.zip -o result.zarr.zip scores a local bundle with a ScoreRequest document.

    Local means trusted

    Local fit and score import and run the plugins in your own process (isolation NONE), exactly like a notebook. Use them with code and data you trust. On the platform, the same work runs in a sandbox.

    Inspect the catalog of installed plugins, and upgrade spec documents across apiVersions:

    mapi catalog models
mapi --json catalog steps | jq -r '.steps[].id' | head -n 5
mapi spec upgrade spec.yaml --check           # exit 0: already the current apiVersion

    mapi plugin init NAME scaffolds a plugin package (model, entry point, contract-kit tests) and mapi plugin test NAME runs its tests; see Write a plugin.

    Against a running platform¶

    Start the stack first (make dev, then make seed; see the quickstart).

    Choosing the API¶

    Every remote command resolves the API the same way as the Python client, first match wins:

    1. --url and --token (global options, before the command: mapi --url http://… runs ls);
    2. MAPI_URL (falling back to MAPI_API_URL, the name make dev uses), MAPI_TOKEN and MAPI_PROFILE;
    3. the selected profile in ~/.config/mapi/config.toml ($MAPI_CONFIG or $XDG_CONFIG_HOME/mapi/config.toml if set);
    4. http://127.0.0.1:8000.
    # ~/.config/mapi/config.toml
profile = "local"

[profiles.local]
url = "http://127.0.0.1:8000"

[profiles.other-ports]
url = "http://127.0.0.1:18000"
timeout = 60

    mapi config show prints the resolved URL and profile and where each value came from (never the token); mapi config path prints the file's location. --remote @ on check, fit, score and catalog means "the configured API"; --remote URL overrides it for one command.

    Tokens

    v0.2 is single-tenant and has no authentication: the API listens on 127.0.0.1 only. The client already sends MAPI_TOKEN as a bearer token, and refuses to send it over plain HTTP to anything but a loopback address. OIDC and scoped tokens arrive with multi-tenancy in v0.3.

    Upload data¶

    mapi datasets upload creates the dataset if it does not exist, sends the file to the signed URL the API returns, starts the sandboxed ingest run and waits until the version is ready. CSV and Parquet files need --mapping mapping.yaml, an IngestMapping with the column of each dim and variable:

    python scripts/seed.py --export demo/      # the E33 tables, score payloads and spec
mapi datasets upload demo/eu_media_future.zarr.zip --name eu_media_future
mapi datasets ls

    Fit and follow¶

    mapi fit SPEC --remote @ creates the spec (or adds a revision when the text changed), submits a fit run and follows its event stream until it ends, printing warnings, diagnostics and metrics as they arrive. --no-wait returns after submitting; mapi runs watch RUN follows any run later.

    mapi check demo/eu-geo-mmm.yaml --remote @   # the server's static validation
mapi fit demo/eu-geo-mmm.yaml --remote @     # create or revise the spec, fit, follow
mapi runs ls --kind fit --limit 3

    mapi runs cancel RUN requests cancellation, and mapi runs retry RUN --resource-class L starts a new run from a failed one.

    Score¶

    cat > forecast.yaml <<'EOF'
apiVersion: mapi/v1
kind: ScoreRequest
model: model://default/eu-geo-mmm@latest
mode: forecast
horizon: {dim: time, periods: 8}
data: dataset://default/eu_media_future@latest
side_tables: {fx: dataset://default/fx_daily@latest}
output: {kind: expected, summary: [mean, hdi_90]}
EOF
# the CLI has no `models` command yet: take the model id and version from the API
MODEL=$(curl -s "${MAPI_API_URL:-http://127.0.0.1:8000}/v1/models" \
  | jq -c '.items[] | select(.name == "eu-geo-mmm")')
mapi score forecast.yaml --remote @ --model "$(jq -r .id <<<"$MODEL")" \
  --version "$(jq -r .latest_version <<<"$MODEL")" -o forecast.zarr.zip

    mapi score --remote @ sends Prefer: wait=60 (change it with --wait), follows the run if it takes longer, prints the outputs with their sizes and CRC32C, and with -o downloads the result tree, checking it against that CRC32C.

    Scripting with --json¶

    --json (a global option) prints one JSON document on stdout instead of tables; runs watch --json prints one JSON event per line. Errors become {"error": {...}} with exit status 1, and usage errors exit with 2.

    RUN=$(mapi --json runs ls --kind score --limit 1 | jq -r '.[0].id')
mapi --json runs get "$RUN" | jq '{state, attempt, kind}'
mapi runs logs "$RUN" | tail -n 5

    Text that came from the server, a plugin or a run log is printed with ANSI and control sequences removed, so a hostile log line cannot rewrite your terminal.

    mapi serve¶

    mapi serve runs mapi-server dev: database migrations, then the API and the orchestrator in one process, with an embedded PostgreSQL unless DATABASE_URL is set and an in-process GCS shim unless one already listens at MAPI_GCS_ENDPOINT. It is the smallest way to get an API for the CLI or the client. For the web app as well, use make dev (Local deployment).
