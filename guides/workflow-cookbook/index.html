    Workflow cookbook v0.5¶

    This page gives ten complete analyses. Each analysis is one YAML document. You can save, run and schedule it, and give it to a colleague. The tests of the documentation validate each document on this page against the node catalog and run it from start to end. Thus the documents that you copy operate correctly. For the format, see Workflows. For all nodes, see the node reference. For short parts with one pattern each, see the workflows guide.

    Recipe The question it answers
    Is my weekly KPI ready to forecast? Does the series need differencing? Which ARIMA orders are correct? Is ARIMAX better than a naive forecast on honest backtests? Can we use it?
    Do these series move together? Do some series have a long-run relation (VECM), or a relation only in their changes (VAR)? Does one series help to predict a different series?
    Which forecasting model? Which of SARIMAX, ARIMA, ETS and Theta forecasts best on the same folds? Is the advantage of the winner more than chance?
    Which spatial model for a disease map? Do the areas share their risk with their neighbours (iid, ICAR or BYM2)? Does the effect of the covariate stay clear in the best model, also with different priors?
    Which model explains the ties of a network? Do shared traits explain the ties, or do the activity of each node and a hidden map also help? Can the best model make networks like the real network?
    Does an effect across species stay when the tree is in the model? Which correlation of relatives (none, Brownian motion, Pagel's lambda, Ornstein-Uhlenbeck) predicts best? Is the slope of the predictor clear of zero in the winner?
    Can I trust a calibration to design with it? What are the material and the losses of a heated plate? Does the calibration predict a run that it did not see? What temperature field does a new heater layout give?
    Can I trust this Bayesian model? Do the priors make sense? Do the chains agree? Does the model make data like my data? Do the priors set the results? Does the model find known values?
    Where does my image model go wrong? Do the predicted images look like the observed image? Where on the image are the residuals large?
    What did my geo-lift test show, and does the MMM agree? What did a campaign in some markets add? Does the marketing mix model agree with the test after it uses the test as a lift test?

    Two more sections tell how to read a grid search in the run page and how to compare the runs of a workflow in an experiment.

    Readiness to ARIMAX¶

    In plain words. Before you trust a forecast, you must know four things:

    • If the series "wanders". If it does, you must model its changes, not its levels.
    • How much of the past is important.
    • If the model forecasts better than the obvious rule "next week is like this week".
    • If the model found a real effect, not noise.

    This workflow answers each question with the standard statistical tool. It records each decision with the numbers that caused it. It keeps the model only if the model is better than the benchmarks. It also records the governance evidence.

    For the statistician. ADF, KPSS, Phillips-Perron and Zivot-Andrews (one endogenous break) decide d with a conservative rule: difference the series unless the evidence for stationarity is clear on the two sides. Seasonal strength (STL) decides D. The ARMA orders come from a grid of information criteria over p ≤ max_p, q ≤ max_q. The workflow fits each point as ARIMA(p, d, q) on the levels. Thus the model estimates d, and does not apply it to data that is already differenced. The report shows ACF/PACF for the reader.

    The backtest is a rolling origin with a fixed training window, a gap and some horizons. The workflow scores ARIMAX and the naive and seasonal-naive benchmarks on the same folds. A Diebold-Mariano test with the Harvey-Leybourne-Newbold correction tells if the difference in squared errors at horizon 1 is significant. select.best keeps the model only if its MAE is better than each benchmark in must_beat.

  T["adf · kpss · pp · za<br/>seasonal strength"] --> B{"wanders?<br/>seasonal?"}

  B --> O

    The document¶

    # Workflow cookbook: is the weekly KPI ready to forecast, which ARIMAX, does it beat naive,
# and may we use it? (validated by conformance/tests/test_docs_v05.py and run end to end
# against a real server by packages/server/tests/test_docs_client_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata:
  name: weekly-readiness
  project: growth
  description: Unit roots -> differencing -> AR/MA orders -> rolling-origin backtest -> ARIMAX vs naive -> select -> governance
params:
  alpha: {type: number, default: 0.05, minimum: 0.001, maximum: 0.2, description: "Significance level of every test"}
  season: {type: integer, default: 52, minimum: 2, maximum: 400, description: "Season length (52 for weekly data)"}
  drivers: {type: array, default: [], description: "Drivers known for the future (planned price, promotions)"}
  window: {type: integer, default: 104, minimum: 20, description: "Training weeks per backtest fold"}
  horizons: {type: array, default: [1, 4, 8], description: "Forecast horizons scored separately"}
  gap: {type: integer, default: 1, minimum: 0, maximum: 52, description: "Weeks between training and test (data arrives late)"}
  max_p: {type: integer, default: 3, minimum: 0, maximum: 8}
  max_q: {type: integer, default: 3, minimum: 0, maximum: 8}
inputs:
  data: {type: dataset, description: "The weekly KPI with its drivers"}
nodes:
# 1. Unit-root tests. ADF and Phillips-Perron: "the series wanders" is the null hypothesis;
#    KPSS: "the series is stable" is the null; Zivot-Andrews allows one structural break.
- {id: adf, use: test.adf, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: kpss, use: test.kpss, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: pp, use: test.pp, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: za, use: test.zivot_andrews, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: seas, use: test.seasonal_strength, inputs: {data: inputs.data}, with: {period: {$param: season}}}
# 2. Decide the differencing (a branch reads the test results; never eval).
- id: wanders
  use: branch.if
  label: Difference?
  with: {condition: "(not nodes.adf.reject or nodes.kpss.reject) and not (nodes.pp.reject and nodes.za.reject)"}
- id: seasonal
  use: branch.if
  label: Seasonal difference?
  with: {condition: nodes.seas.seasonal}
- {id: sdiff, use: transform.seasonal_difference, inputs: {data: inputs.data}, when: seasonal.then,
   with: {period: {$param: season}}}
- {id: diff, use: transform.difference, inputs: {data: [sdiff.data, inputs.data]}, when: wanders.then}
# 3. AR and MA orders: autocorrelations to read, an information-criterion grid to decide.
- {id: acf, use: test.acf_pacf, inputs: {data: [diff.data, sdiff.data, inputs.data]},
   with: {max_order: {$param: max_p}}}
- id: order
  use: search.arma_order
  inputs: {data: inputs.data}
  with:
    d: {$expr: "if(nodes.wanders.value, 1, 0)"}
    max_p: {$param: max_p}
    max_q: {$param: max_q}
    exog: {$param: drivers}
    criterion: aic
# 4. An honest backtest: a rolling origin with a fixed training window, a gap and several
#    horizons; ARIMAX and the naive benchmarks on the very same folds.
- id: folds
  use: split.rolling_origin
  inputs: {data: inputs.data}
  with:
    window: {$param: window}
    horizons: {$param: horizons}
    gap: {$param: gap}
    n_folds: 6
    step: 4
- id: backtest
  use: model.backtest
  inputs: {data: inputs.data, split: folds.plan}
  with:
    model: ts.sarimax@^1
    settings:
      order: {$expr: "[nodes.order.best_p, if(nodes.wanders.value, 1, 0), nodes.order.best_q]"}
      seasonal_order: {$expr: "[0, if(nodes.seasonal.value, 1, 0), 0, params.season]"}
      exog: {$param: drivers}
    metrics: [mae, rmse, mape, mase]
- id: naive
  use: evaluate.baseline
  inputs: {data: inputs.data, split: folds.plan}
  with: {methods: [naive, seasonal_naive], season: {$param: season}}
# 5. ARIMAX vs naive: rank them, and test whether the difference is more than luck.
- {id: compare, use: compare.models, inputs: {candidates: [backtest.metrics, naive.metrics]},
   with: {metric: mae}}
- {id: dm, use: compare.diebold_mariano, inputs: {a: backtest.metrics, b: naive.metrics},
   with: {loss: squared, horizon: 1, alpha: {$param: alpha}}}
# 6. Fit (scored on the last 13 weeks first, then refitted on everything, so governance has
#    a test period) and keep it only if it beats naive.
- id: holdout
  use: split.holdout
  inputs: {data: inputs.data}
  with: {split: {kind: time_holdout, dim: time, last: 13}}
- id: fit
  use: model.fit
  inputs: {data: inputs.data, split: holdout.plan}
  with:
    model: ts.sarimax@^1
    settings:
      order: {$expr: "[nodes.order.best_p, if(nodes.wanders.value, 1, 0), nodes.order.best_q]"}
      seasonal_order: {$expr: "[0, if(nodes.seasonal.value, 1, 0), 0, params.season]"}
      exog: {$param: drivers}
    fit: {mode: evaluate_then_refit}
    evaluate: {metrics: [mape, mase, coverage_90]}
- id: select
  use: select.best
  inputs: {table: compare.table, models: [fit.model]}
  with: {metric: mae, must_beat: [naive], margin: 0.0}
# 7. Governance: the policy in force (null tests, benchmarks, residuals...), recorded as a
#    validation of the model version when it passes; the evidence pack only if it did.
- {id: governance, use: governance.policy, inputs: {model: select.model, data: inputs.data},
   with: {submit: true}}
- {id: trusted, use: branch.if, with: {condition: nodes.governance.passed}}
- {id: pack, use: report.evidence_pack, inputs: {model: select.model, evidence: governance.evidence},
   when: trusted.then, with: {format: json}}
- id: report
  use: report.summary
  inputs:
    tests: [adf.result, kpss.result, pp.result, za.result, seas.result, acf.result, dm.result]
    metrics: [backtest.metrics, naive.metrics]
    items: [order.table, compare.table]
    model: select.model
  with: {title: Weekly readiness and ARIMAX}
outputs: {model: select.model, report: report.report, evidence: governance.evidence}

    Copy these three details into your own workflows:

    • Alternatives keep the graph honest. diff reads [sdiff.data, inputs.data]. This is the seasonally differenced series if that node ran. If not, it is the raw series. acf uses the series with the most processing that exists. The workflow calculates nothing two times. If the workflow does not take a branch, nothing breaks: skipped nodes are skipped, not failed.
    • Decisions move as values. $expr: "[nodes.order.best_p, if(nodes.wanders.value, 1, 0), nodes.order.best_q]" changes the search result and the branch decision into the order of the model. The server parses the expression language and never uses eval on it. The run records each value that it read.
    • The fit has its own holdout. split.holdout keeps the last 13 weeks out of the first fit (mode: evaluate_then_refit). Thus the governance checks that need unseen data have it. These checks are the null tests, the naive benchmark and the holdout accuracy. Then the workflow fits the model again on all the data.

  --input data=dataset://growth/weekly_sales@latest \
  --param 'drivers=["price"]' --param window=104 \
  --watch                                     # live node status; exit 1 if the run fails

    Run it with the Python client¶

    Do these steps:

    1. Validate the file on the server. The server saves nothing.
    2. Make the workflow, or save a new revision.
    3. Run the workflow.
    4. Follow the live events.
    from pathlib import Path

check = api.workflows.validate(Path("weekly-readiness.yaml"))  # on the server; saves nothing
for issue in check.issues:  # every problem with a JSON pointer into the document
    print(issue.severity.value, issue.pointer, issue.message)
print(" -> ".join(check.order))  # the order the nodes will run in

workflow, revision = api.workflows.upsert(Path("weekly-readiness.yaml"))

    workflow.id,
    inputs={"data": "dataset://growth/weekly_sales@latest"},  # pinned to a version at start

    What the shuffle test measures on a random walk

    The model has a driver. Thus the test shuffles the driver in blocks and does not change the result. It scores each fit by its skill against the null forecast on the held-out weeks. Persistence ("next week is like this week") helps the shuffled fits exactly as much as it helps the real fit. Thus the test measures what the driver adds to persistence. For a model without drivers, the test uses shuffled changes of the series (null tests explained).

    VAR/VECM cointegration¶

    In plain words. Some series wander but stay together. Examples are the prices of close substitutes, sales and distribution, and income and consumption. If they have a relation, a model that knows the relation (an error-correction model) forecasts better. It also tells you how fast a gap closes. If they do not have a relation, model their changes. In the two cases, find out if one series helps to predict a different series.

    For the statistician. The Johansen trace test (at 5%) on the levels decides the branch. If the series have a relation, search.coint_rank selects the rank. Then the workflow fits a VECM with k_ar_diff: 1 on the levels. If the series do not have a relation, the workflow differences them. Then AIC selects the VAR lag order up to maxlags, and the workflow fits a VAR on the changes. If the workflow took the changes (the first alternative), it tests Granger causality on them. If not, it tests on the levels. The forecast node uses the model that exists, with the related data.

    # Workflow cookbook: do these series move together for good? VECM if they are tied in the
# long run, a VAR on the levels if they are already stable, else a VAR on the changes;
# Granger tests either way; a forecast of the winner.
# (validated by conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: macro-system, project: growth}
params:
  target: {type: string, required: true, description: "The main result (one of the series)"}
  driver: {type: string, required: true, description: "A series that may help predict it"}
  maxlags: {type: integer, default: 8, minimum: 1, maximum: 52}
  horizon: {type: integer, default: 8, minimum: 1, maximum: 104}
inputs:
  # one value per series and period: value(series, quarter), the layout of ts.var/ts.vecm
  data: {type: dataset, description: "The series along one dimension"}
nodes:
# 1. Is there a long-run relationship? (Johansen trace test, every series of the dimension)
- {id: johansen, use: test.johansen, inputs: {data: inputs.data}, with: {alpha: "0.05"}}
# rank 0: no tie; rank = number of series: every series is stable (no unit root)
- id: tied
  use: branch.if
  with: {condition: "nodes.johansen.rank > 0 and nodes.johansen.rank < len(nodes.johansen.trace_stats)"}
# 2a. Tied: choose the cointegration rank and fit an error-correction model on the levels.
- {id: rank, use: search.coint_rank, inputs: {data: inputs.data}, when: tied.then}
- id: vecm
  use: model.fit
  inputs: {data: inputs.data}
  when: tied.then
  with:
    model: ts.vecm@^1
    settings:
      coint_rank: {$expr: "min(max(nodes.rank.rank, 1), len(nodes.johansen.trace_stats) - 1)"}
      k_ar_diff: 1
# 2b. Not tied: a VAR on the levels when every series is stable, else on the changes.
- id: stationary
  use: branch.if
  when: tied.else
  with: {condition: "nodes.johansen.rank >= len(nodes.johansen.trace_stats)"}
- {id: diff, use: transform.difference, inputs: {data: inputs.data}, when: stationary.else}
- {id: lags, use: search.var_lag_order, inputs: {data: [diff.data, inputs.data]},
   when: tied.else, with: {maxlags: {$param: maxlags}, criterion: aic}}
- id: var
  use: model.fit
  inputs: {data: [diff.data, inputs.data]}
  when: tied.else
  with:
    model: ts.var@^1
    settings: {lags: {$expr: nodes.lags.best_lag}}
# 3. Does the driver help predict the target? (on the changes when they were taken)
- id: granger
  use: test.granger
  inputs: {data: [diff.data, inputs.data]}
  with: {y: {$param: target}, x: {$param: driver}, maxlag: {$param: maxlags}}
# 4. Forecast with whichever system was fitted (the first alternative that ran).
- id: forecast
  use: model.forecast
  inputs: {model: [vecm.model, var.model], data: [diff.data, inputs.data]}
  with: {horizon: {$param: horizon}}
- id: report
  use: report.summary
  inputs:
    tests: [johansen.result, granger.result]
    items: [rank.table, lags.table]
    model: [vecm.model, var.model]
  with: {title: Series that move together}
outputs: {report: report.report, forecast: forecast.forecast}

    Forecast bake-off¶

    In plain words. If you do not know which forecast method is correct for your data, let the methods compete fairly. They use the same history, the same cut-off points, the same horizons and the same naive benchmarks. Keep the winner only if it is clearly better than a simple method.

    For the statistician. The plan is an expanding window with n_folds origins, one each 4 periods. The workflow scores each horizon. SARIMAX(1,1,1)(0,1,0)₅₂, ARIMA(0,1,1), damped-trend ETS and Theta compete against naive, seasonal-naive and drift. MASE puts them in sequence. MASE has no scale, so you can compare series of different sizes. Two Diebold-Mariano tests (absolute loss, horizon 1) compare the leaders with the benchmark. select.best needs a 5% MASE improvement over each benchmark. Only then does the branch fit the winner again.

    # Workflow cookbook: a forecast bake-off. Four models and the naive benchmarks compete on the
# same expanding-window folds; Diebold-Mariano tests say whether the winner's edge is more
# than luck; the winner is refitted on all the data only if it beats naive.
# (validated by conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: forecast-bakeoff, project: growth}
params:
  horizons: {type: array, default: [1, 4, 8]}
  season: {type: integer, default: 52, minimum: 2, maximum: 400}
  n_folds: {type: integer, default: 6, minimum: 2, maximum: 50}
inputs:
  data: {type: dataset}
nodes:
- id: folds
  use: split.expanding_window
  inputs: {data: inputs.data}
  with: {horizons: {$param: horizons}, n_folds: {$param: n_folds}, step: 4, gap: 0}
# the candidates, each backtested on the same plan
- {id: sarimax, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.sarimax@^1, settings: {order: [1, 1, 1], seasonal_order: [0, 1, 0, 52]}}}
- {id: arima, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.arima@^1, settings: {order: [0, 1, 1]}}}
- {id: ets, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.ets@^1, settings: {trend: add, damped_trend: true}}}
- {id: theta, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.theta@^1}}
- {id: naive, use: evaluate.baseline, inputs: {data: inputs.data, split: folds.plan},
   with: {methods: [naive, seasonal_naive, drift], season: {$param: season}}}
# the league table, then two head-to-head tests against the benchmark
- id: compare
  use: compare.models
  inputs: {candidates: [sarimax.metrics, arima.metrics, ets.metrics, theta.metrics, naive.metrics]}
  with: {metric: mase}
- {id: dm_ets, use: compare.diebold_mariano, inputs: {a: ets.metrics, b: naive.metrics},
   with: {loss: absolute, horizon: 1}}
- {id: dm_sarimax, use: compare.diebold_mariano, inputs: {a: sarimax.metrics, b: naive.metrics},
   with: {loss: absolute, horizon: 1}}
# the winner, if it beats naive by at least 5%, refitted on everything
- {id: best, use: select.best, inputs: {table: compare.table},
   with: {metric: mase, must_beat: [naive], margin: 0.05}}
- {id: winner, use: branch.if, with: {condition: nodes.best.beats_baselines}}
- id: refit
  use: model.fit
  inputs: {data: inputs.data}
  when: winner.then
  with: {model: {$expr: nodes.best.selected_model}}
- id: report
  use: report.summary
  inputs:
    tests: [dm_ets.result, dm_sarimax.result]
    items: [compare.table]
    model: [refit.model]
  with: {title: Forecast bake-off}
outputs: {model: refit.model, comparison: compare.table, report: report.report}

  -p 'horizons=[1,4]' -p n_folds=6 --watch
mapi workflows node "$RUN" compare      # the league table
mapi workflows node "$RUN" best         # who won, and whether they beat naive by 5%

    Disease map: which spatial model?¶

    In plain words. A disease map shows the risk in each area, for example in each district. Small areas have few cases, so their raw rates have much noise. A model can let adjacent areas share their risk. This makes the estimates of small areas more stable. But is this correct for your data? And does it change your answer about a cause, for example the percentage of people who work outdoors?

    This workflow fits three models, from independent areas to areas that share their risk. Then it keeps the model that predicts best. It tells you if the effect of the covariate is clear, and if the effect stays clear with different priors.

    For the statistician. Each rung is sci.areal_bym2, Poisson(E exp(b0 + b1 x + u)), on all the data. The area effects u are iid, icar or bym2. Each fit keeps the pointwise PSIS-LOO values (evaluate: {metrics: [elpd_loo]}), so the rungs are scored on the same areas. compare.models ranks them by elpd_loo. compare.stacking gives the stacking weights (Yao et al. 2018). select.best keeps the rung with the largest elpd_loo. model.summary gives the HDI of b1 (hdi_prob). governance.check (convergence) reads R-hat of the winner. If the check does not fail and the HDI excludes zero, the workflow fits the winner again with the prior widths of b0, b1 and sigma multiplied and divided by prior_scale.

  D["dataset"] --> I["iid"] & C["icar"] & B["bym2"]
  I & C & B --> R["compare.models<br/>(elpd_loo)"] & W["compare.stacking"]
  R --> S["select.best"]
  S --> E["model.summary<br/>(b1)"] & G["convergence"]
  E & G --> Q{"chains agree and<br/>b1 clear?"}
  Q -- then --> P["refit: wider and<br/>narrower priors"]

  M & E & P --> Rep["report"]

    The document¶

    # Workflow cookbook: which spatial model for a disease map? Fit iid, ICAR and BYM2 area
# effects on the same areas, compare them by PSIS-LOO (ranking and stacking weights), keep the
# best one, read its covariate effect, check convergence, refit it with wider and narrower
# priors when the chains agree and the effect is clear, and draw the relative-risk map.
# This is the sci_spatial_ladder template of the gallery (a test keeps the two the same).
# (validated and run by conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: disease-map-ladder, project: epidemiology}
params:
  # the names of the area dims and of the covariate in your dataset (the e18 export)
  bind:
    type: object
    default: {dims: {area: district, area_: district_}, vars: {covariate: aff}}
    description: The names in your dataset of the area dims and of the covariate (the default
      fits the e18 export)
  islands:
    type: string
    default: link_nearest
    enum: [link_nearest, isolate, error]
    description: What to do with areas that have no neighbours. link_nearest links each one to
      the area with the closest border
  hdi_prob: {type: number, default: 0.94, minimum: 0.5, maximum: 0.999,
             description: The probability inside the range of each parameter}
  prior_scale:
    type: number
    default: 2.0
    minimum: 1.1
    maximum: 10
    description: When the effect is clear, the workflow fits the best model again with the
      prior widths multiplied and divided by this value
  # one MCMC configuration for every rung, so the rungs are comparable
  draws: {type: integer, default: 1000, minimum: 50, maximum: 20000,
          description: The posterior draws to keep in each chain}
  tune: {type: integer, default: 1000, minimum: 50, maximum: 20000,
         description: The warm-up steps of each chain (the sampler discards them)}
  chains: {type: integer, default: 4, minimum: 2, maximum: 16,
           description: 'The number of chains (two or more, for R-hat)'}
  target_accept: {type: number, default: 0.9, minimum: 0.6, maximum: 0.99,
                  description: The target acceptance rate of the sampler. A higher value gives
                    smaller steps and fewer divergences}
  engine: {type: string, default: pymc, enum: [pymc, nutpie],
           description: The sampler (nutpie is faster on large data)}
  seed: {type: integer, default: 18, minimum: 0, maximum: 2147483647,
         description: The random seed of each fit}
inputs:
  data: {type: dataset, description: 'Counts, expected counts, a covariate, the adjacency matrix
      and the outlines of the areas'}
nodes:
# 1. Three rungs on all the data. PSIS-LOO scores each area as if the fit had not seen it.
- id: iid
  use: model.fit
  label: Independent areas
  inputs: {data: inputs.data}
  with:
    model: sci.areal_bym2@^1
    bind: {$param: bind}
    settings: {kind: iid, islands: {$param: islands}}
    fit: &fit
      mode: train_only
      draws: {$param: draws}
      tune: {$param: tune}
      chains: {$param: chains}
      target_accept: {$param: target_accept}
      engine: {$param: engine}
      seed: {$param: seed}
    evaluate: {metrics: [elpd_loo]}
- id: icar
  use: model.fit
  label: Neighbours share risk (ICAR)
  inputs: {data: inputs.data}
  with:
    model: sci.areal_bym2@^1
    bind: {$param: bind}
    settings: {kind: icar, islands: {$param: islands}}
    fit: *fit
    evaluate: {metrics: [elpd_loo]}
- id: bym2
  use: model.fit
  label: Neighbours and noise (BYM2)
  inputs: {data: inputs.data}
  with:
    model: sci.areal_bym2@^1
    bind: {$param: bind}
    settings: {kind: bym2, islands: {$param: islands}}
    fit: *fit
    evaluate: {metrics: [elpd_loo]}
# 2. Rank the rungs, weigh them by stacking and keep the best one.
- id: compare
  use: compare.models
  inputs: {candidates: [iid.metrics, icar.metrics, bym2.metrics]}
  with: {metric: elpd_loo, direction: max}
- id: weights
  use: compare.stacking
  label: Stacking weights
  inputs: {candidates: [iid.metrics, icar.metrics, bym2.metrics]}
- id: best
  use: select.best
  inputs: {table: compare.table, models: [iid.model, icar.model, bym2.model]}
  with: {metric: elpd_loo, direction: max}
# 3. Is the covariate effect clear in the best rung?
- id: effect
  use: model.summary
  label: Covariate effect
  inputs: {model: best.model}
  with: {vars: [b0, b1, sigma], hdi_prob: {$param: hdi_prob}}
- id: converged
  use: governance.check
  label: Did the chains agree?
  inputs: {model: best.model, data: inputs.data}
  with: {check: convergence}
# an effect is clear only when the chains of the best model agree
- id: clear
  use: branch.if
  label: Is the effect clear?
  with:
    condition: >-
      coalesce(nodes.converged.status, 'error') not in ['fail', 'error'] and
      (nodes.effect.params.b1.hdi_low > 0 or nodes.effect.params.b1.hdi_high < 0)
    explain_then: The chains of the best model agree, and the range of the covariate effect
      does not include zero. The covariate has a clear effect on the risk. The workflow fits
      the best model again with wider and narrower priors.
    explain_else: The chains of the best model do not agree, or the range of the covariate
      effect includes zero. Look at the convergence evidence first. When the chains agree,
      the data does not show a clear effect of the covariate when the areas share their
      risk.
# 4. A clear effect must come from the data, not from the priors: refit the best rung
#    (kind = the id of the winner) with the prior widths x prior_scale and / prior_scale.
- id: wide
  use: model.fit
  label: Wider priors
  when: clear.then
  inputs: {data: inputs.data}
  with:
    model: sci.areal_bym2@^1
    bind: {$param: bind}
    settings:
      kind: {$expr: nodes.best.selected}
      islands: {$param: islands}
      intercept_sd: {$expr: params.prior_scale}
      slope_sd: {$expr: params.prior_scale}
      sigma_scale: {$expr: params.prior_scale}

- id: narrow
  use: model.fit
  label: Narrower priors
  when: clear.then
  inputs: {data: inputs.data}
  with:
    model: sci.areal_bym2@^1
    bind: {$param: bind}
    settings:
      kind: {$expr: nodes.best.selected}
      islands: {$param: islands}
      intercept_sd: {$expr: 1 / params.prior_scale}
      slope_sd: {$expr: 1 / params.prior_scale}
      sigma_scale: {$expr: 1 / params.prior_scale}

- id: effect_wide
  use: model.summary
  label: 'Wider priors: effect'
  inputs: {model: wide.model}

- id: effect_narrow

  label: 'Narrower priors: effect'
  inputs: {model: narrow.model}
  when: clear.then
  with: {vars: [b1], hdi_prob: {$param: hdi_prob}}

- id: map
  use: plot.render
  label: Relative risk map
  inputs: {model: best.model}

    recipe: sci.area_map
    source: model

    title: Relative risk of each area (best model)
- id: report

    metrics: [iid.metrics, icar.metrics, bym2.metrics]
    model: best.model
    plots: [map.plot]
  with: {title: 'Disease map: which spatial model?'}

  comparison: compare.table
  weights: weights.table
  effect: effect.table
  map: map.plot
  convergence: converged.evidence
  report: report.report

    • The winner sets the next fit. kind: {$expr: nodes.best.selected} gives the id of the winner (iid, icar or bym2) to the refits. The id of each rung is also its kind.
    • One fit configuration for all rungs. The YAML anchor &fit gives the same draws, chains and seed to each rung. Thus the rungs differ only in their area effects.
    • The workflow writes the priors out. governance.check with sensitivity.prior finds only prior widths with names such as prior_sigma. The prior widths of sci.areal_bym2 are intercept_sd, slope_sd and sigma_scale. Thus the workflow fits the model again with these widths, and model.summary shows the effect for each fit.

    Network ties: which model?¶

    In plain words. In a network, some pairs of nodes have a tie, for example two lawyers who work together. Shared traits can explain the ties: two lawyers in the same office work together more often. But some lawyers work with many colleagues, and groups form for other reasons.

    This workflow fits three models of the ties. The first model uses only the shared traits. The second model adds the activity of each node. The third model adds a hidden map of the group. The workflow keeps the model that predicts best. Then it simulates new networks from that model. The workflow does not calculate the statistics of the real network. To compare, calculate them from your data yourself (the E21 tutorial shows a table of them).

    For the statistician. Each rung is sci.network_latent_space, a Bernoulli-logit model of the pairs i < j. covariates uses alpha + x β. sociality adds s_i + s_j. latent_space also subtracts the distance ‖z_i − z_j‖ between Procrustes-aligned positions. The log-likelihood is over the observed pairs, in the same order for each rung. Thus elpd_loo is leave-one-pair-out, and compare.stacking can weigh the rungs. model.score in simulate mode draws whole graphs from the best rung. It gives graph_stat(statistic) for each graph: density, sd and maximum of the degree, isolates, triangles, transitivity, ties without shared partners (esp0), mean geodesic and the share of unreachable pairs.

    flowchart LR
  D["dataset"] --> C["covariates"] & S["sociality"] & L["latent_space"]
  C & S & L --> R["compare.models<br/>(elpd_loo)"] & W["compare.stacking"]
  R --> B["select.best"]
  B --> E["model.summary<br/>(alpha, beta)"] & G["net.graph"] & X["model.score<br/>simulate"]

    Trait regression across species¶

    In plain words. Close relatives are similar because they share most of their history. If you use each species as an independent data point, an effect can look clear only because related species are near each other. This recipe fits the same regression four times. The first fit ignores the tree. The other three fits let relatives share part of their residual.

    The workflow keeps the fit that predicts best. Then it tells you if the effect that you ask about is clear of zero in that fit. It reports a clear effect only with a check that the fit agrees with the data.

    For the statistician. sci.phylo_regression regresses the log of the trait on the log of each predictor (standardised). The four fits differ only in the residual kind:

    • iid: no tree, K = σ²I.
    • brownian: Brownian motion on the tree, K = σ²R. R is the shared branch length of two tips divided by the depth of the tree.
    • lambda: Pagel's lambda, K = σ²(λR + (1 − λ)I).
    • ou: Ornstein-Uhlenbeck on the patristic distance.

    Each fit stores the leave-one-out density of each species given the other species. Thus elpd_loo compares the four kinds correctly. compare.models ranks them by elpd_loo, compare.stacking gives the stacking weights and select.best keeps the highest elpd_loo. model.summary with focus reads the slope of one predictor of the winner. The branch tests if the HDI of that slope excludes zero. Only then does evaluate.ppc compare the predictions of the winner with the observed traits.

    Calibrate, then design¶

    In plain words. A heated plate conducts heat in its plane and loses heat through its faces and its edges. Some calibration runs with a known heater and some thermocouples tell how much heat the plate conducts and loses. The calibrated model can then predict the temperature of each point of the plate for a heater layout that you did not build.

    Before you trust such a prediction, test the calibration on a run that it did not see. This recipe holds out one calibration run, fits the other runs and predicts the run held out. It predicts the new layout only if that error is small and the sampler converged.

    For the statistician. sci.heat_plate solves the 2-D steady heat equation A(θ) u = η q on the finite-volume grid of the data. θ is the conductivity k, the face and edge loss coefficients h and h_edge, and the heater efficiency η. split.holdout holds out one random run (leave_group_out, n: 1). model.fit with mode: evaluate_then_refit fits the other runs and scores the run held out (rmse, mae, coverage_90). Then it fits all the runs again. model.summary gives the parameters and max_rhat. The branch needs rmse ≤ max_error and max_rhat ≤ max_rhat. The field is linear in the heater power, so model.score (predict) gives the posterior draws of the expected field of each new run. These draws have no sensor noise. plot.render draws them with sci.field_map, one frame for each run.

    The document¶

    # Workflow cookbook: calibrate a heated plate, then predict a new heater layout.
# sci.heat_plate is fitted on the calibration runs with one run held out. The design step
# runs only if the calibration predicts that run within `max_error` and the sampler
# converged. The split and the plot read the bound dim names (`bind`), else the model's.
# (the gallery template sci_calibrate_then_design; validated and run by
# conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: heat-plate-design, project: engineering}
params:
  thickness_mm: {type: number, default: 5.0, minimum: 0.01, maximum: 1000,
                 description: The thickness of the plate in mm}
  room_temperature: {type: number, default: 20.0, minimum: -100, maximum: 1000,
                     description: The temperature of the room in degC}
  max_error: {type: number, default: 0.5, minimum: 0,
              description: The largest RMSE in degC on the run held out that the design step accepts}
  max_rhat: {type: number, default: 1.01, minimum: 1, maximum: 2,
             description: The largest R-hat that the design step accepts}
  draws: {type: integer, default: 1000, minimum: 10, maximum: 20000,
          description: The posterior draws that each chain keeps}
  tune: {type: integer, default: 1000, minimum: 10, maximum: 20000,
         description: The tuning steps of each chain (the sampler drops them)}
  # the gate reads R-hat, and one chain gives no R-hat
  chains: {type: integer, default: 4, minimum: 2, maximum: 16,
           description: The number of chains (two or more give R-hat)}
  seed: {type: integer, default: 51, minimum: 0, maximum: 2147483647,
         description: The random seed of the sampler}
  bind:
    type: object
    default: {}
    description: >-
      The names of the model (dims and vars) mapped to the names in your dataset, when they
      are different. The workflow finds the target itself when your dataset has one target.
inputs:
  data: {type: dataset,
         description: "The calibration runs: heater power and the thermocouple readings on the grid"}
  layout: {type: dataset, required: false,
           description: The new heater layouts to predict (the heater power of each new run on the same grid)}
nodes:
# 1. calibrate: hold out one random run, fit the others, score it, then fit all the runs
- id: holdout
  use: split.holdout
  inputs: {data: inputs.data}
  with:
    split: {kind: leave_group_out, dim: {$expr: "coalesce(params.bind.dims.run, 'run')"},
            n: 1, seed: {$param: seed}}
- id: fit
  use: model.fit
  label: Calibrate
  inputs: {data: inputs.data, split: holdout.plan}
  with:
    model: sci.heat_plate@^1
    settings: {thickness_mm: {$param: thickness_mm}, room_temperature: {$param: room_temperature}}
    fit: {draws: {$param: draws}, tune: {$param: tune}, chains: {$param: chains},
          seed: {$param: seed}, mode: evaluate_then_refit, target_accept: 0.9}
    bind: {$param: bind}
    evaluate: {metrics: [rmse, mae, coverage_90]}
- id: plate
  use: model.summary
  label: Plate parameters
  inputs: {model: fit.model}
  with: {vars: [k, h, h_edge, eta, sigma, spread_length]}
- id: residuals
  use: plot.render
  label: Calibration residuals
  inputs: {model: fit.model}
  with: {recipe: sci.image_residuals}
# 2. the gate: the error on the run held out, and convergence
- id: good
  use: branch.if
  label: Is the calibration good enough?
  with:
    condition: >-
      coalesce(nodes.fit.metrics.rmse, 1e9) <= params.max_error and
      coalesce(nodes.plate.max_rhat, 99) <= params.max_rhat
    explain_then: >-
      The calibration predicted the run that it did not see within the error limit, and the
      sampler converged. The workflow predicted the new layout.
    explain_else: >-
      The calibration did not predict the run that it did not see within the error limit, or
      the sampler did not converge. The workflow did not predict the new layout. Add
      calibration runs or thermocouples.
# 3. design: the expected field of the new layout (else of the calibration runs), as a map
- id: design
  use: model.score
  label: Predict the layout
  when: good.then
  inputs: {model: fit.model, data: [inputs.layout, inputs.data]}
  with: {mode: predict}
- id: field
  use: plot.render
  label: Field of the layout
  when: good.then
  inputs: {data: design.scores}
  with:
    recipe: sci.field_map
    source: data
    settings:
      var: field
      y: {$expr: "coalesce(params.bind.dims.y, 'y')"}
      x: {$expr: "coalesce(params.bind.dims.x, 'x')"}
      frame: {$expr: "coalesce(params.bind.dims.run, 'run')"}
      origin: lower
      colormap: magma
- id: report
  use: report.summary
  inputs:
    items: [plate.table]
    metrics: [fit.metrics]
    model: fit.model
    plots: [residuals.plot, field.plot]
  with: {title: "Calibrate a heated plate, then test a heater layout"}
outputs: {model: fit.model, parameters: plate.table, residuals: residuals.plot,
          design: design.scores, field: field.plot, report: report.report}

    The recipe reads two datasets:

    • data: the calibration runs. heater_power(run, y, x) in W and temperature(run, y, x) in degC on a regular grid in cm. temperature has no value where there is no thermocouple. The run dim needs the policy new_levels, because the fit does not see the run held out. Use three runs or more.
    • layout (optional): the new heater layouts. heater_power(run, y, x) on the same grid, with new run labels. If you do not give a layout, the workflow predicts the calibration runs.

    If the names in your datasets are different, give bind. The split and the map read the names of the run, y and x dims from bind. To try the recipe, export the E51 case study and make a layout with two 5 W heaters:

    Bayesian workflow audit¶

    In plain words. A Bayesian model gives ranges, not only numbers. Before you use the ranges, do the checks of a careful Bayesian workflow:

    • Can the model make data like your data before it sees the data (the priors)?
    • Do the chains of the sampler agree (R-hat and the effective sample size)?
    • Can the fitted model make data like your data (the posterior predictive check)?
    • Do the results change much when the priors are wider or narrower?
    • Does the model find known values in data that it simulated?

    This workflow does all five checks on one model and writes one report with the plots. It works with each model that gives posterior draws. You give the model, its settings and the binding as parameters, the same as in a model spec.

    For the statistician. The fit keeps prior_predictive.draws prior predictive draws (500 by default) for core.prior_predictive. model.summary gives the rank-normalised split R-hat and the bulk ESS of all the posterior values. The branch converged needs R-hat under rhat_max (1.01) and the ESS at or over min_ess (400, that is 100 for each of 4 chains). Only then do the other checks run:

    • evaluate.ppc: the coverage of the 50% and 90% ranges, the PIT distance and the p-value of statistic (sd by default).
    • governance.check with sensitivity.prior: refits with the prior widths times each of prior_scales.
    • governance.check with recovery.simulated: n_sims refits on targets that the fit simulated.

    The branch trusted needs ppc.ok and no fail or error from the two refit checks. A check that does not apply to the model (skipped) does not block. The plots use on_failure: continue. If a recipe cannot read the model, the report tells why, and the audit continues. The defaults are for real use: 4 chains of 1000 draws after 1000 tuning steps. The recovery check fits the model n_sims more times, at the refit budget of the governance run.

    The document¶

    # Workflow cookbook: the checks of a careful Bayesian workflow for any model with draws.
# Prior predictive draws -> convergence gate -> posterior predictive check, prior
# sensitivity and simulated recovery -> plots -> one report.
# (the gallery template bayes_workflow_audit; validated and run by
# conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: bayes-workflow-audit, project: templates}
params:
  model:
    type: string
    required: true
    description: The model to audit, for example tabular.hierarchical_glm@^1 or sci.heat_plate@^1
  settings: {type: object, default: {}, description: The settings of the model (see its About card)}
  bind:
    type: object
    default: {}
    description: The binding of the dataset names to the names of the model (dims and vars), as in data.bind of a model spec
  draws: {type: integer, default: 1000, minimum: 10, maximum: 100000, description: The posterior draws for each chain}
  tune: {type: integer, default: 1000, minimum: 0, maximum: 100000, description: The tuning steps for each chain (the sampler drops them)}
  chains: {type: integer, default: 4, minimum: 2, maximum: 16, description: "The number of chains (two or more, so that R-hat is available)"}
  seed: {type: integer, default: 1, minimum: 0, description: The random seed of the fit}
  prior_predictive:
    type: object
    default: {draws: 500}
    description: "The prior predictive draws of the fit, as {draws: N}. Type {} for a model that cannot sample its priors (the workflow then does not draw the prior plot)"
  vars: {type: array, default: [], description: "The parameters of the pair plot and the estimate plot (empty: the plots select them)"}
  rhat_max: {type: number, default: 1.01, minimum: 1.0, maximum: 1.5, description: The largest R-hat that passes}
  min_ess: {type: number, default: 400, minimum: 0, description: The smallest bulk effective sample size that passes (100 for each of 4 chains)}
  statistic: {type: string, default: sd, enum: [mean, sd, max, min], description: The statistic of the predictive p-value}
  prior_scales: {type: array, default: [0.5, 2.0], description: "The prior widths that the sensitivity check tries, as multiples of the model priors"}
  n_sims: {type: integer, default: 20, minimum: 5, maximum: 100, description: The simulated datasets of the recovery check (each one is a fit)}
inputs:
  data: {type: dataset, description: The dataset that the model fits}
nodes:
# 1. Fit the model and keep draws from the priors (unless prior_predictive is {}).
- id: fit
  use: model.fit
  label: Fit with prior draws
  inputs: {data: inputs.data}
  with:
    model: {$param: model}
    settings: {$param: settings}
    bind: {$param: bind}
    fit:
      draws: {$param: draws}
      tune: {$param: tune}
      chains: {$param: chains}
      seed: {$param: seed}
      prior_predictive: {$expr: "if(len(params.prior_predictive) > 0, params.prior_predictive, null)"}
- id: has_prior
  use: branch.if
  label: Prior draws?
  with:
    condition: len(params.prior_predictive) > 0
    explain_then: The run asked for draws from the priors, so the workflow compared them with the data.
    explain_else: The run did not ask for draws from the priors, so the workflow did not draw the prior plot.
# 2. Can the priors make data like the observed data? (A plot that fails does not stop the audit.)
- id: prior_plot
  use: plot.render
  label: Prior predictive check
  inputs: {model: fit.model}
  when: has_prior.then
  on_failure: continue
  with: {recipe: core.prior_predictive, source: model}
# 3. The parameters, R-hat, the bulk ESS and the divergences; a pair plot of a few parameters.
- {id: summary, use: model.summary, label: Parameters and convergence, inputs: {model: fit.model}}
- id: pair_plot
  use: plot.render
  label: Pair plot
  inputs: {model: fit.model}
  on_failure: continue
  with:
    recipe: core.pair
    source: model
    settings:
      var_names: {$expr: "if(len(params.vars) > 0, params.vars, null)"}
# 4. The gate: the other checks only mean something when the chains agree.
- id: converged
  use: branch.if
  label: Did the sampler converge?
  with:
    condition: coalesce(nodes.summary.max_rhat, 99) < params.rhat_max and coalesce(nodes.summary.min_ess, 0) >= params.min_ess
    explain_then: R-hat and the effective sample size are in their limits, so the chains agree. The workflow did the checks of the predictions and the priors.
    explain_else: R-hat is too large or the effective sample size is too small, so the chains do not agree. The workflow stopped the audit. Fit with more draws and tuning steps, or change the model.
# 5. Posterior predictive check (coverage, PIT, a p-value) and its plot.
- id: ppc
  use: evaluate.ppc
  label: Predictions against the data
  inputs: {model: fit.model}
  when: converged.then
  on_failure: continue
  with: {statistic: {$param: statistic}}
- id: ppc_plot
  use: plot.render
  label: Posterior predictive check
  inputs: {model: fit.model}
  when: converged.then
  on_failure: continue
  with: {recipe: core.ppc, source: predictions}
# 6. Refits: wider and narrower priors, and data simulated from the fit.
- id: sensitivity
  use: governance.check
  label: Prior sensitivity
  inputs: {model: fit.model, data: inputs.data}
  when: converged.then
  with:
    check: sensitivity.prior
    params: {scales: {$param: prior_scales}}
- id: recovery
  use: governance.check
  label: Recovery of known values
  inputs: {model: fit.model, data: inputs.data}
  when: converged.then
  with:
    check: recovery.simulated
    params: {n_sims: {$param: n_sims}}
# 7. The verdict; a skipped check (one that does not apply to the model) does not block.
- id: trusted
  use: branch.if
  label: Can you trust the model?
  when: converged.then
  with:
    condition: coalesce(nodes.ppc.ok, false) and nodes.sensitivity.status not in ['fail', 'error'] and nodes.recovery.status not in ['fail', 'error']
    explain_then: No check failed. The model makes data like the observed data, and the prior and recovery checks did not fail. Read their warnings, then use the estimates.
    explain_else: One or more checks failed. Look at the predictive check, the prior sensitivity and the recovery evidence before you use the estimates.
- id: estimates
  use: plot.render
  label: Estimates
  inputs: {model: fit.model}
  when: trusted.then
  on_failure: continue
  with:
    recipe: core.posterior_forest
    source: model
    settings:
      var_names: {$expr: "if(len(params.vars) > 0, params.vars, null)"}
# 8. One report: the decisions, the table, the predictive scores and the plots that ran.
- id: report
  use: report.summary
  inputs:
    items: [summary.table]
    metrics: [ppc.metrics]
    plots: [prior_plot.plot, pair_plot.plot, ppc_plot.plot, estimates.plot]
    model: fit.model
  with: {title: Bayesian workflow audit}
outputs:
  model: fit.model
  report: report.report
  summary: summary.table
  ppc: ppc.metrics
  sensitivity: sensitivity.evidence
  recovery: recovery.evidence

    Note

    A model that cannot sample its priors (for example sci.areal_bym2, because of its ICAR prior) fails the fit when the run asks for prior draws. For such a model, set prior_predictive to {}. The branch has_prior then skips the prior plot.

    Read the outputs¶

    Output What it tells you
    has_prior, converged, trusted The three decisions, with the values that each condition read. The report starts with their plain words.
    summary (table) The mean, sd, 94% HDI, R-hat and bulk ESS of each parameter (the first 200 values). The result also has max_rhat, min_ess and n_divergent.
    prior_plot The data that the priors can make (grey) and your data (black). If your data is far from the grey curves, the priors are on the wrong scale.
    pair_plot The draws of two parameters at a time. Red points are divergent transitions. Look at funnels and strong correlations.
    ppc, ppc_plot The share of the observations in the 50% and 90% ranges, the PIT distance, and the p-value of the statistic. ok is true when all of them pass.
    sensitivity The largest relative change of a key estimate when the priors change. Above 0.2 is warn, above 0.5 is fail. skipped if the settings do not set the priors.
    recovery How often the 90% ranges contained the known values in the simulated data (target 90%).
    estimates The posterior forest of the parameters. It shows only when no check failed.

    Image model check¶

    In plain words. When a model predicts a full image, a table of numbers does not show where the model is wrong. This workflow fits the model and puts its predicted images next to the observed image. It shows the residuals as maps, so that you can see the areas where the model does not agree with the data. Use it for a sky map (sci.cmb_field), a lensed galaxy (sci.strong_lens), a Turing pattern (sci.turing_pattern) or a different model that predicts an image.

    For the statistician. The plots read the in-sample predictions of the model (source: predictions) with the observed image as observed_data:

    • sci.image_residuals shows the observed image, the posterior predictive mean, the residual and the normalised residual (obs − mean) / √(sd² + σ²), with a histogram against N(0, 1).
    • sci.ppc_image_grid shows the observed image next to n_draws predicted images on one colour scale. With shuffle: true the observed image has a random position, and the caption gives the answer.
    • evaluate.ppc pools all the pixels: the coverage of the 50% and 90% ranges, the PIT distance and a p-value. It needs 10 or more predictive draws. If it fails, the report tells why and the plots stay.

    The parameters var and frame select the image variable and the dim of the slider when the recipes cannot find them.

    The document¶

    # Workflow cookbook: does an image model make images like the observed image?
# Fit -> parameter summary -> residual maps and a grid of predicted images -> posterior
# predictive check -> one report.
# (the gallery template sci_image_model_check; validated and run by
# conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: sci-image-model-check, project: templates}
params:
  model: {type: string, required: true, description: "The image model, for example sci.cmb_field@^1"}
  settings: {type: object, default: {}, description: The settings of the model (see its About card)}
  bind:
    type: object
    default: {}
    description: The binding of the dataset names to the names of the model (dims and vars), as in data.bind of a model spec
  draws: {type: integer, default: 1000, minimum: 10, maximum: 100000, description: The posterior draws for each chain}
  tune: {type: integer, default: 1000, minimum: 0, maximum: 100000, description: The tuning steps for each chain (the sampler drops them)}
  chains: {type: integer, default: 4, minimum: 2, maximum: 16, description: "The number of chains (two or more, so that R-hat is available)"}
  seed: {type: integer, default: 1, minimum: 0, description: The random seed of the fit}
  var: {type: string, default: "", description: "The predicted image variable (empty: the plots find it)"}
  frame: {type: string, default: "", description: "The dim with one image for each level, for example run or t (empty: the plots find it)"}
  n_draws: {type: integer, default: 5, minimum: 1, maximum: 11, description: The predicted images next to the observed image}
  shuffle: {type: boolean, default: false, description: Hide which panel is the observed image (the caption gives the answer)}
  statistic: {type: string, default: sd, enum: [mean, sd, max, min], description: The statistic of the predictive p-value}
inputs:
  data: {type: dataset, description: The observed image (or images) and the inputs of the model}
nodes:
- id: fit
  use: model.fit
  inputs: {data: inputs.data}
  with:
    model: {$param: model}
    settings: {$param: settings}
    bind: {$param: bind}
    fit: {draws: {$param: draws}, tune: {$param: tune}, chains: {$param: chains}, seed: {$param: seed}}
- {id: summary, use: model.summary, label: Parameters and convergence, inputs: {model: fit.model}}
# Both plots read the in-sample predictions with the observed image (source: predictions).
# An empty var or frame becomes null, and the recipe finds the image and the slider dim.
- id: residuals
  use: plot.render
  label: Residual maps
  inputs: {model: fit.model}
  with:
    recipe: sci.image_residuals
    source: predictions
    settings:
      var: {$expr: "if(params.var == '', null, params.var)"}
      frame: {$expr: "if(params.frame == '', null, params.frame)"}
- id: grid
  use: plot.render
  label: Observed and predicted images
  inputs: {model: fit.model}
  with:
    recipe: sci.ppc_image_grid
    source: predictions
    settings:
      var: {$expr: "if(params.var == '', null, params.var)"}
      frame: {$expr: "if(params.frame == '', null, params.frame)"}
      n_draws: {$param: n_draws}
      shuffle: {$param: shuffle}
# Coverage, PIT and a p-value over all the pixels (needs 10 or more predictive draws).
- id: ppc
  use: evaluate.ppc
  label: Predictions against the data
  inputs: {model: fit.model}
  on_failure: continue
  with: {statistic: {$param: statistic}}
- id: report
  use: report.summary
  inputs:
    items: [summary.table]
    metrics: [ppc.metrics]
    plots: [residuals.plot, grid.plot]
    model: fit.model
  with: {title: Image model check}
outputs:
  model: fit.model
  report: report.report
  summary: summary.table
  ppc: ppc.metrics

    Read the outputs¶

    Output What it tells you
    residuals Four maps on the image grid. The normalised residuals must look like noise with sd near 1. A pattern (a ring, an edge, a blob) shows structure that the model does not have.
    grid The observed image and the predicted images. If the model fits, the observed image looks like one of them.
    ppc The coverage of the 50% and 90% ranges over all the pixels, the PIT distance and ok.
    summary The parameters, R-hat and the bulk ESS.

    A run on a laptop checked the mock lens of sci.strong_lens (24 × 24 pixels, 2 chains of 100 draws for the test). 92% of the pixels were in the 90% ranges, the PIT distance was 0.03 (limit 0.06) and ok was true.

    Read a grid search in the run page v0.11¶

    A search.grid node logs each grid point in its search run. Thus you can see the scores of the points while the search runs, and compare them after it ends.

    A sandboxed search.grid node has two runs. The search run comes first. It does the backtest of each grid point and keeps the data in the table below. Then the node fits the winner again on all the data in a second run, the refit run. After the search, the run_id of the node is the refit run. The refit run does not have the grid data. The search run is always the first item in the child_runs of the node.

    What Name in the run
    The settings of point i The params trial.<i>.<pointer>, for example trial.3.adstock/l_max = 4
    The search The params grid.metric, grid.direction, grid.points and grid.nested
    The scores of point i The metrics mae, rmse, mape, smape, mase and coverage_90 (when present), with step i
    Nested search The inner scores have the labels stage=inner and fold=<j>. The outer scores have stage=outer and step j.
    The winner The metric best_<metric> (for example best_rmse) and the tag grid.best_point
    A point that failed A warning log line with the field point

    On the workflow run page, open the node. Then open the first run in Runs (the search run). The Metrics tab shows the score of each point as a curve over the point number. The Params tab lists the trial.* params. Type trial.3. in the filter to see the settings of one point. With the CLI:

    mapi workflows node "$RUN" grid               # "child runs": the search run comes first
SEARCH_RUN=$(mapi --json workflows node "$RUN" grid | jq -r '.child_runs[0]')
mapi runs metrics "$SEARCH_RUN" --key rmse    # the score of each grid point
mapi runs params "$SEARCH_RUN"                # the trial.* params

    A model.backtest node logs the metrics of each fold as scalars with the label fold.

    Geo-lift test to a calibrated MMM v0.13¶

    In plain words. You ran a test on one channel in some markets: more spend, or no spend. The workflow measures what the test changed, against a mix of the markets without the test. Then it gives the result to the marketing mix model as a lift test, so that the model agrees with the test.

    For the statistician. geolift fits causal.synthetic_control (simplex weights, train_only) on the experiment data. lift (model.lift_test) sums the effect over the post cells and the treated markets for each draw. kpi_delta is the mean, se the sd and ci the 90% HDI. mmm fits mmm.bayesian with calibration.lift_tests set from nodes.lift.lift_test. lift_plot shows the test next to the estimate of the model (mmm.lift_tests).

    This recipe is the gallery template geo_lift_mmm. Start from the template. Do not copy the document from this page:

    mapi workflows create --template geo_lift_mmm
mapi workflows run geo-lift-mmm \
  -i experiment=dataset://growth/geo_test@latest \
  -i data=dataset://growth/eu_media_weekly@latest \
  -p 'treated=["geo_03"]' -p test_start=2024-03-04 -p test_end=2024-04-14 \
  -p channel=tv -p spend_delta=-50000 --watch
mapi workflows node "$RUN" lift       # the lift test: kpi_delta, se, hdi_low, hdi_high, geo

    To see the document, use mapi workflows init geo_lift_mmm. These rules apply:

    • The dates of the test must be in the data of the marketing mix model.
    • With one test market, the lift test has the geo of that market. That geo must be in the data of the marketing mix model. With two or more test markets, the lift test is national.
    • The time labels of the experiment must be dates.

    See Measure the effect of a change for the Guided version of this analysis.

    Compare the runs of a workflow in an experiment v0.14¶

    In plain words. You run the same workflow some times with different parameters. You want to see the results next to each other. Put all the runs in one experiment. Then the runs table of the experiment shows the node runs, and the compare page shows 2 to 10 of them side by side.

    1. Make the experiment one time.
    2. Start each workflow run with --experiment. The workflow run and each node run that it starts go into the experiment.
    3. List the runs of the experiment with the columns that you want to compare.
    4. Compare the node runs on the compare page, or with mapi runs compare.
    mapi experiments create "arimax drivers" --description "Readiness with and without promotions."
mapi workflows run ts-readiness-arimax -i data=dataset://growth/weekly_sales@latest \
  -p 'drivers=["price"]' --experiment "arimax drivers" --watch
mapi workflows run ts-readiness-arimax -i data=dataset://growth/weekly_sales@latest \
  -p 'drivers=["price", "promo"]' --experiment "arimax drivers" --watch
mapi runs ls --experiment "arimax drivers"            # the workflow runs and their node runs
mapi runs compare "$RUN_A" "$RUN_B"                    # two node runs, for example the backtests

    A model.backtest node run logs the metrics of each fold with the label fold. On the compare page, select the label fold to draw each fold with a different dash.

    From Python, give experiment_id= to api.workflows.run. Runs that a schedule or a trigger starts are in no experiment. See Put the runs in an experiment and Compare runs and use experiments.

    Make your own¶

    1. Start from the recipe that is nearest to your analysis. Use mapi workflows init <template>, or copy a document above.
    2. Find nodes with mapi workflows nodes-catalog --kind test. To see the About card, ports and parameters of one node, use --about test.kpss.
    3. Validate the document after each change. Before anything runs, mapi workflows validate my.yaml shows each problem with a JSON pointer.
    4. Save the workflow (apply).
    5. Run the workflow with --watch.
    6. Read the summary.
    7. To compare runs with different parameters, put them in an experiment (above).
    8. Add a schedule or a dataset trigger to run the workflow automatically.
    9. Add a governance gate to the workflow.
