    Workflow cookbook v0.5¶

    Three complete analyses, each a single YAML document you can save, run, schedule and hand to a colleague. Every document on this page is validated against the node catalog and run end to end by the documentation's tests, so what you copy works. For the format itself see Workflows; for every node, the node reference; for short fragments (one pattern each), the workflows guide.

    Recipe The question it answers
    Is my weekly KPI ready to forecast? Does the series need differencing, which ARIMA orders, does ARIMAX beat a naive forecast on honest backtests, and may we use it?
    Do these series move together? Are several series tied in the long run (VECM) or only in their changes (VAR), and does one help predict another?
    Which forecasting model? Which of SARIMAX, ARIMA, ETS and Theta forecasts best on the same folds - and is the winner's edge more than luck?

    Readiness to ARIMAX¶

    In plain words. Before trusting a forecast you want to know four things: whether the series "wanders" (and must be modelled in changes rather than levels), how much of the past matters, whether the model forecasts better than the obvious "next week is like this week", and whether it learned something real rather than noise. This workflow answers each with the standard statistical tool, writes down every decision with the numbers behind it, keeps the model only if it beats the benchmarks, and records the governance evidence.

    For the statistician. ADF, KPSS, Phillips-Perron and Zivot-Andrews (one endogenous break) decide d by a conservative rule - difference unless the evidence for stationarity is clear on both sides; seasonal strength (STL) decides D. The ARMA orders come from an information-criterion grid over p ≤ max_p, q ≤ max_q fitted as ARIMA(p, d, q) on the levels (so d is estimated, not imposed on already-differenced data); ACF/PACF are reported for the reader. The backtest is a rolling origin with a fixed training window, a gap and several horizons; ARIMAX and the naive and seasonal-naive benchmarks are scored on the same folds; a Diebold-Mariano test with the Harvey-Leybourne-Newbold correction says whether the difference in squared errors at horizon 1 is significant. select.best keeps the model only if its MAE beats every benchmark in must_beat.

    flowchart LR
  T["adf · kpss · pp · za<br/>seasonal strength"] --> B{"wanders?<br/>seasonal?"}
  B -- then --> D["difference /<br/>seasonal difference"]
  T --> O["AR/MA order<br/>search (AIC)"]
  B --> O
  O --> BT["rolling-origin backtest<br/>ARIMAX"]
  F["folds: window 104,<br/>gap 1, h = 1, 4, 8"] --> BT
  F --> N["naive and<br/>seasonal naive"]
  BT --> C["compare +<br/>Diebold-Mariano"]
  N --> C
  C --> S{"select:<br/>beats naive?"}
  FIT["fit on all data<br/>(13-week holdout first)"] --> S
  S --> G["governance policy<br/>(null tests, benchmarks...)"]
  G --> P["evidence pack<br/>when it passed"]
  S --> R["report"]

    The document¶

    # Workflow cookbook: is the weekly KPI ready to forecast, which ARIMAX, does it beat naive,
# and may we use it? (validated by conformance/tests/test_docs_v05.py and run end to end
# against a real server by packages/server/tests/test_docs_client_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata:
  name: weekly-readiness
  project: growth
  description: Unit roots -> differencing -> AR/MA orders -> rolling-origin backtest -> ARIMAX vs naive -> select -> governance
params:
  alpha: {type: number, default: 0.05, minimum: 0.001, maximum: 0.2, description: "Significance level of every test"}
  season: {type: integer, default: 52, minimum: 2, maximum: 400, description: "Season length (52 for weekly data)"}
  drivers: {type: array, default: [], description: "Drivers known for the future (planned price, promotions)"}
  window: {type: integer, default: 104, minimum: 20, description: "Training weeks per backtest fold"}
  horizons: {type: array, default: [1, 4, 8], description: "Forecast horizons scored separately"}
  gap: {type: integer, default: 1, minimum: 0, maximum: 52, description: "Weeks between training and test (data arrives late)"}
  max_p: {type: integer, default: 3, minimum: 0, maximum: 8}
  max_q: {type: integer, default: 3, minimum: 0, maximum: 8}
inputs:
  data: {type: dataset, description: "The weekly KPI with its drivers"}
nodes:
# 1. Unit-root tests. ADF and Phillips-Perron: "the series wanders" is the null hypothesis;
#    KPSS: "the series is stable" is the null; Zivot-Andrews allows one structural break.
- {id: adf, use: test.adf, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: kpss, use: test.kpss, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: pp, use: test.pp, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: za, use: test.zivot_andrews, inputs: {data: inputs.data}, with: {alpha: {$param: alpha}}}
- {id: seas, use: test.seasonal_strength, inputs: {data: inputs.data}, with: {period: {$param: season}}}
# 2. Decide the differencing (a branch reads the test results; never eval).
- id: wanders
  use: branch.if
  label: Difference?
  with: {condition: "(not nodes.adf.reject or nodes.kpss.reject) and not (nodes.pp.reject and nodes.za.reject)"}
- id: seasonal
  use: branch.if
  label: Seasonal difference?
  with: {condition: nodes.seas.seasonal}
- {id: sdiff, use: transform.seasonal_difference, inputs: {data: inputs.data}, when: seasonal.then,
   with: {period: {$param: season}}}
- {id: diff, use: transform.difference, inputs: {data: [sdiff.data, inputs.data]}, when: wanders.then}
# 3. AR and MA orders: autocorrelations to read, an information-criterion grid to decide.
- {id: acf, use: test.acf_pacf, inputs: {data: [diff.data, sdiff.data, inputs.data]},
   with: {max_order: {$param: max_p}}}
- id: order
  use: search.arma_order
  inputs: {data: inputs.data}
  with:
    d: {$expr: "if(nodes.wanders.value, 1, 0)"}
    max_p: {$param: max_p}
    max_q: {$param: max_q}
    exog: {$param: drivers}
    criterion: aic
# 4. An honest backtest: a rolling origin with a fixed training window, a gap and several
#    horizons; ARIMAX and the naive benchmarks on the very same folds.
- id: folds
  use: split.rolling_origin
  inputs: {data: inputs.data}
  with:
    window: {$param: window}
    horizons: {$param: horizons}
    gap: {$param: gap}
    n_folds: 6
    step: 4
- id: backtest
  use: model.backtest
  inputs: {data: inputs.data, split: folds.plan}
  with:
    model: ts.sarimax@^1
    settings:
      order: {$expr: "[nodes.order.best_p, if(nodes.wanders.value, 1, 0), nodes.order.best_q]"}
      seasonal_order: {$expr: "[0, if(nodes.seasonal.value, 1, 0), 0, params.season]"}
      exog: {$param: drivers}
    metrics: [mae, rmse, mape, mase]
- id: naive
  use: evaluate.baseline
  inputs: {data: inputs.data, split: folds.plan}
  with: {methods: [naive, seasonal_naive], season: {$param: season}}
# 5. ARIMAX vs naive: rank them, and test whether the difference is more than luck.
- {id: compare, use: compare.models, inputs: {candidates: [backtest.metrics, naive.metrics]},
   with: {metric: mae}}
- {id: dm, use: compare.diebold_mariano, inputs: {a: backtest.metrics, b: naive.metrics},
   with: {loss: squared, horizon: 1, alpha: {$param: alpha}}}
# 6. Fit (scored on the last 13 weeks first, then refitted on everything, so governance has
#    a test period) and keep it only if it beats naive.
- id: holdout
  use: split.holdout
  inputs: {data: inputs.data}
  with: {split: {kind: time_holdout, dim: time, last: 13}}
- id: fit
  use: model.fit
  inputs: {data: inputs.data, split: holdout.plan}
  with:
    model: ts.sarimax@^1
    settings:
      order: {$expr: "[nodes.order.best_p, if(nodes.wanders.value, 1, 0), nodes.order.best_q]"}
      seasonal_order: {$expr: "[0, if(nodes.seasonal.value, 1, 0), 0, params.season]"}
      exog: {$param: drivers}
    fit: {mode: evaluate_then_refit}
    evaluate: {metrics: [mape, mase, coverage_90]}
- id: select
  use: select.best
  inputs: {table: compare.table, models: [fit.model]}
  with: {metric: mae, must_beat: [naive], margin: 0.0}
# 7. Governance: the policy in force (null tests, benchmarks, residuals...), recorded as a
#    validation of the model version when it passes; the evidence pack only if it did.
- {id: governance, use: governance.policy, inputs: {model: select.model, data: inputs.data},
   with: {submit: true}}
- {id: trusted, use: branch.if, with: {condition: nodes.governance.passed}}
- {id: pack, use: report.evidence_pack, inputs: {model: select.model, evidence: governance.evidence},
   when: trusted.then, with: {format: json}}
- id: report
  use: report.summary
  inputs:
    tests: [adf.result, kpss.result, pp.result, za.result, seas.result, acf.result, dm.result]
    metrics: [backtest.metrics, naive.metrics]
    items: [order.table, compare.table]
    model: select.model
  with: {title: Weekly readiness and ARIMAX}
outputs: {model: select.model, report: report.report, evidence: governance.evidence}

    Three details worth copying into your own workflows:

    • Alternatives keep the graph honest. diff reads [sdiff.data, inputs.data]: the seasonally differenced series if that node ran, else the raw one. acf looks at the most processed series that exists. Nothing is computed twice and nothing breaks when a branch is not taken - skipped nodes are skipped, not failed.
    • Decisions travel as values. $expr: "[nodes.order.best_p, if(nodes.wanders.value, 1, 0), nodes.order.best_q]" turns the search result and the branch decision into the model's order. The expression language is parsed, never eval-ed, and the run records every value it read.
    • The fit has its own holdout. split.holdout keeps the last 13 weeks out of the first fit (mode: evaluate_then_refit), so the governance checks that need unseen data - the null tests, the naive benchmark, holdout accuracy - have it. The model is then refitted on everything.

    Run it with the Python client¶

    Validate the file on the server (nothing is saved), then create it or save a new revision, run it and follow the live events:

    from pathlib import Path

check = api.workflows.validate(Path("weekly-readiness.yaml"))  # on the server; saves nothing
for issue in check.issues:  # every problem with a JSON pointer into the document
    print(issue.severity.value, issue.pointer, issue.message)
print(" -> ".join(check.order))  # the order the nodes will run in

    from mapi_client import WorkflowEnd, WorkflowEventFrame, WorkflowSnapshot

# create the workflow, or save the file as its next revision when it changed
workflow, revision = api.workflows.upsert(Path("weekly-readiness.yaml"))
run = api.workflows.run(
    workflow.id,
    inputs={"data": "dataset://growth/weekly_sales@latest"},  # pinned to a version at start
    params={"drivers": ["price"], "window": 80, "max_p": 2, "max_q": 2},
)
for item in api.workflows.stream_events(run.run_id):  # server-sent events, resumable
    match item:
        case WorkflowSnapshot(run=now):
            print(f"{len(now.nodes)} nodes, {now.status.value}")
        case WorkflowEventFrame(event=e) if e.type.value == "workflow.branch.decided":
            print(f"  {e.node_id}: took the {e.data['arm']} arm")
        case WorkflowEventFrame(event=e) if e.node_id is not None:
            print(f"  {e.node_id}: {e.type.value.rsplit('.', 1)[-1]}")
        case WorkflowEnd(status=status):
            print("run", status.value if status else "ended")

    Read what it found - every test's verdict, every branch with the values it read, the chosen orders, the Diebold-Mariano verdict and why the model was (or was not) selected:

    run = api.workflows.wait(run.run_id)  # raises the run's error if it failed
nodes = {n.node_id: n for n in run.nodes}
print(nodes["adf"].result["verdict_plain"])  # e.g. "The series wanders: consider differencing it."
for d in run.decisions:
    print(d.node_id, d.arm, d.inputs)  # every branch with the values its condition read
order, d = nodes["order"].result, 1 if nodes["wanders"].result["value"] else 0
print(f"ARIMA({order['best_p']}, {d}, {order['best_q']})")  # chosen by information criterion
print(nodes["dm"].result["verdict_plain"])  # is ARIMAX's edge over naive more than luck?
print(nodes["select"].result["reason_plain"])  # kept only if it beats the benchmarks
model_ref = run.outputs["model"].ref  # model://growth/wf-weekly-readiness-fit@v1
report = run.outputs["report"].inline  # mapi.report/v1: every test, decision and table

    The governance node measured the selected model against the policy in force and, with submit: true, recorded a validation of that model version:

    gov = nodes["governance"].result  # the policy in force, measured on the selected model
print("passed" if gov["passed"] else f"failed: {gov['failed_checks']}")
validation = api.validations.get(gov["validation_id"])  # recorded because submit: true
print(validation.status.value)  # validated, or awaiting_approval when a reviewer must sign
for r in validation.results:
    print(f"{r.check:28} {r.status.value:7} {r.message_plain}")
api.validations.download_evidence_pack(validation.id, "evidence.html")  # for the auditor

    Read it like a reviewer would: the model beats naive by 25% on unseen weeks, leaves no pattern in its errors, and forecasts better than every fit with the price driver shuffled in time, but the AR coefficient is not stable across windows. That check failed and the version is still validated, because a check's status and its severity are different things: the default forecasting policy holds stability at information, so it does not block; it is on the record for the reviewer and in the evidence pack. A stricter policy (see governance) makes it blocking, and this model would then need more history or a simpler specification. That is the point: the evidence is written down, and the decision is explicit.

    What the shuffle test measures on a random walk

    The model has a driver, so the test shuffles the driver in blocks and leaves the result untouched, and it scores each fit by its skill against the null forecast on the held-out weeks. Persistence ("next week is like this week") helps the shuffled fits exactly as much as the real one, so the test measures what the driver adds beyond it. A model without drivers is tested on shuffled changes of the series instead (null tests explained).

    VAR/VECM cointegration¶

    In plain words. Some series wander but stay tied together - prices of close substitutes, sales and distribution, income and consumption. If they are tied, a model that knows the tie (an error-correction model) forecasts better and tells you how fast a gap closes. If they are not, model their changes instead. Either way, ask whether one series helps predict another.

    For the statistician. The Johansen trace test (at 5%) on the levels decides the branch. Tied: search.coint_rank chooses the rank and a VECM with k_ar_diff: 1 is fitted on the levels. Not tied: the series are differenced, the VAR lag order is chosen by AIC up to maxlags, and a VAR is fitted on the changes. Granger causality is tested on the changes when they were taken (the first alternative), else on the levels. The forecast node takes whichever model exists, with the matching data.

    # Workflow cookbook: do these series move together for good? VECM if they are tied in the
# long run, a VAR on the levels if they are already stable, else a VAR on the changes;
# Granger tests either way; a forecast of the winner.
# (validated by conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: macro-system, project: growth}
params:
  target: {type: string, required: true, description: "The main result (one of the series)"}
  driver: {type: string, required: true, description: "A series that may help predict it"}
  maxlags: {type: integer, default: 8, minimum: 1, maximum: 52}
  horizon: {type: integer, default: 8, minimum: 1, maximum: 104}
inputs:
  # one value per series and period: value(series, quarter), the layout of ts.var/ts.vecm
  data: {type: dataset, description: "The series along one dimension"}
nodes:
# 1. Is there a long-run relationship? (Johansen trace test, every series of the dimension)
- {id: johansen, use: test.johansen, inputs: {data: inputs.data}, with: {alpha: "0.05"}}
# rank 0: no tie; rank = number of series: every series is stable (no unit root)
- id: tied
  use: branch.if
  with: {condition: "nodes.johansen.rank > 0 and nodes.johansen.rank < len(nodes.johansen.trace_stats)"}
# 2a. Tied: choose the cointegration rank and fit an error-correction model on the levels.
- {id: rank, use: search.coint_rank, inputs: {data: inputs.data}, when: tied.then}
- id: vecm
  use: model.fit
  inputs: {data: inputs.data}
  when: tied.then
  with:
    model: ts.vecm@^1
    settings:
      coint_rank: {$expr: "min(max(nodes.rank.rank, 1), len(nodes.johansen.trace_stats) - 1)"}
      k_ar_diff: 1
# 2b. Not tied: a VAR on the levels when every series is stable, else on the changes.
- id: stationary
  use: branch.if
  when: tied.else
  with: {condition: "nodes.johansen.rank >= len(nodes.johansen.trace_stats)"}
- {id: diff, use: transform.difference, inputs: {data: inputs.data}, when: stationary.else}
- {id: lags, use: search.var_lag_order, inputs: {data: [diff.data, inputs.data]},
   when: tied.else, with: {maxlags: {$param: maxlags}, criterion: aic}}
- id: var
  use: model.fit
  inputs: {data: [diff.data, inputs.data]}
  when: tied.else
  with:
    model: ts.var@^1
    settings: {lags: {$expr: nodes.lags.best_lag}}
# 3. Does the driver help predict the target? (on the changes when they were taken)
- id: granger
  use: test.granger
  inputs: {data: [diff.data, inputs.data]}
  with: {y: {$param: target}, x: {$param: driver}, maxlag: {$param: maxlags}}
# 4. Forecast with whichever system was fitted (the first alternative that ran).
- id: forecast
  use: model.forecast
  inputs: {model: [vecm.model, var.model], data: [diff.data, inputs.data]}
  with: {horizon: {$param: horizon}}
- id: report
  use: report.summary
  inputs:
    tests: [johansen.result, granger.result]
    items: [rank.table, lags.table]
    model: [vecm.model, var.model]
  with: {title: Series that move together}
outputs: {report: report.report, forecast: forecast.forecast}

    The data holds the series along one dimension, one value per series and period (value(series, quarter)), the layout of ts.var and ts.vecm; ingest a wide sheet with the wide mapping. Run it like the first recipe, with the two parameters it requires:

    mapi workflows apply macro-system.yaml
mapi workflows run macro-system -i data=dataset://growth/us_macro@latest \
  -p target=realcons -p driver=realgdp --watch

    run = api.workflows.run(
    wf.id,
    inputs={"data": "dataset://growth/us_macro@latest"},
    params={"target": "realcons", "driver": "realgdp", "maxlags": 4},
    wait=True,
)
nodes = {n.node_id: n for n in run.nodes}
print(nodes["johansen"].result["verdict_plain"])  # "The series share at least one long-run relationship."
print(nodes["granger"].result["verdict_plain"])   # "Past values of the driver help predict the result."
print([n.node_id for n in run.nodes if n.status.value == "skipped"])  # the branch not taken

    Run on a laptop against three simulated weekly series, two of which share a stochastic trend (target=a, driver=b), it printed the two verdicts above and ['diff', 'lags', 'var']: the Johansen trace statistic (69.1) put the rank at 1, the VECM branch ran, and Granger found that b helps predict a (p = 0.0015). See Macro and VAR analysis.

    The fitted model's impulse responses, variance decomposition, Granger table and Johansen table are in the Model Explorer (mapi explore model … -s irf -s fevd).

    Forecast bake-off¶

    In plain words. When you do not know which forecasting method suits your data, let them compete fairly: same history, same cut-off points, same horizons, and the same naive benchmarks. Keep the winner only if it clearly beats doing nothing clever.

    For the statistician. An expanding window with n_folds origins every 4 periods, scored at each horizon; SARIMAX(1,1,1)(0,1,0)₅₂, ARIMA(0,1,1), damped-trend ETS and Theta against naive, seasonal-naive and drift. MASE ranks them (scale-free, so series of different size compare); two Diebold-Mariano tests (absolute loss, horizon 1) check the leaders against the benchmark; select.best requires a 5% MASE improvement over every benchmark, and the branch refits the winner only then.

    # Workflow cookbook: a forecast bake-off. Four models and the naive benchmarks compete on the
# same expanding-window folds; Diebold-Mariano tests say whether the winner's edge is more
# than luck; the winner is refitted on all the data only if it beats naive.
# (validated by conformance/tests/test_docs_v05.py)
apiVersion: mapi/v1
kind: Workflow
metadata: {name: forecast-bakeoff, project: growth}
params:
  horizons: {type: array, default: [1, 4, 8]}
  season: {type: integer, default: 52, minimum: 2, maximum: 400}
  n_folds: {type: integer, default: 6, minimum: 2, maximum: 50}
inputs:
  data: {type: dataset}
nodes:
- id: folds
  use: split.expanding_window
  inputs: {data: inputs.data}
  with: {horizons: {$param: horizons}, n_folds: {$param: n_folds}, step: 4, gap: 0}
# the candidates, each backtested on the same plan
- {id: sarimax, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.sarimax@^1, settings: {order: [1, 1, 1], seasonal_order: [0, 1, 0, 52]}}}
- {id: arima, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.arima@^1, settings: {order: [0, 1, 1]}}}
- {id: ets, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.ets@^1, settings: {trend: add, damped_trend: true}}}
- {id: theta, use: model.backtest, inputs: {data: inputs.data, split: folds.plan},
   with: {model: ts.theta@^1}}
- {id: naive, use: evaluate.baseline, inputs: {data: inputs.data, split: folds.plan},
   with: {methods: [naive, seasonal_naive, drift], season: {$param: season}}}
# the league table, then two head-to-head tests against the benchmark
- id: compare
  use: compare.models
  inputs: {candidates: [sarimax.metrics, arima.metrics, ets.metrics, theta.metrics, naive.metrics]}
  with: {metric: mase}
- {id: dm_ets, use: compare.diebold_mariano, inputs: {a: ets.metrics, b: naive.metrics},
   with: {loss: absolute, horizon: 1}}
- {id: dm_sarimax, use: compare.diebold_mariano, inputs: {a: sarimax.metrics, b: naive.metrics},
   with: {loss: absolute, horizon: 1}}
# the winner, if it beats naive by at least 5%, refitted on everything
- {id: best, use: select.best, inputs: {table: compare.table},
   with: {metric: mase, must_beat: [naive], margin: 0.05}}
- {id: winner, use: branch.if, with: {condition: nodes.best.beats_baselines}}
- id: refit
  use: model.fit
  inputs: {data: inputs.data}
  when: winner.then
  with: {model: {$expr: nodes.best.selected_model}}
- id: report
  use: report.summary
  inputs:
    tests: [dm_ets.result, dm_sarimax.result]
    items: [compare.table]
    model: [refit.model]
  with: {title: Forecast bake-off}
outputs: {model: refit.model, comparison: compare.table, report: report.report}

    mapi workflows apply forecast-bakeoff.yaml
mapi workflows run forecast-bakeoff -i data=dataset://growth/weekly_sales@latest \
  -p 'horizons=[1,4]' -p n_folds=6 --watch
mapi workflows node "$RUN" compare      # the league table
mapi workflows node "$RUN" best         # who won, and whether they beat naive by 5%

    A typical outcome on a short, noisy series is the honest one: "ets is the best model (0.0456) but does not beat naive.drift by the required 5%: no model is selected." The refit node is skipped, the report says why, and nobody ships a model that only looks clever.

    Make your own¶

    1. Start from the closest recipe (mapi workflows init <template> or copy a document above).
    2. Find nodes with mapi workflows nodes-catalog --kind test (or --about test.kpss for one node's About card, ports and parameters).
    3. Validate as you go: mapi workflows validate my.yaml points at every problem with a JSON pointer before anything runs.
    4. Save it (apply), run it with --watch, and read the summary.
    5. Automate it with a schedule or a dataset trigger, and gate it on governance.
