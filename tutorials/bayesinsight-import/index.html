    Import a BayesInsight model v0.4¶

    A BayesInsight project is three files: model_def.json (the model), metadata.json (the keys of the data) and the data itself as an MFF long table. modeling-api imports them as a draft: an ingest mapping for the MFF table and a ModelSpec, plus a report of every feature that did not carry over exactly. Nothing is dropped silently.

    In this tutorial you import a project, read the report, check the draft and fit it on your laptop - where you can see that it recovers the parameters the data was simulated with - and then run it on the platform. The code is docs/snippets/bayesinsight_import.py in the repository, which the test suite runs.

    The example project¶

    The files come from mapi_plugin_mmm.bayesinsight_examples: 60 weeks of sales for two geographies (US, DE) × two products (Phones, Watches), driven by TV (delayed carry-over, Hill curve) and search (geometric carry-over, Hill curve), a price control with a negative sign, an annual season and Normal noise. The MFF table looks like this:

    Period,Geography,Product,Outlet,Campaign,Creative,VariableName,VariableValue
2023-01-02,DE,Phones,Total,Total,Total,Price,8.904
2023-01-02,DE,Phones,Total,Total,Total,Sales,240.633
2023-01-02,DE,Phones,Total,Total,Total,Search,26.58
2023-01-02,DE,Phones,Total,Total,Total,TV,102.21

    and model_def.json names its variables BayesInsight's way, TV_Total_Total_Total, with priors in the KPI's own units (a TV coefficient around 30 sales per unit of the curve).

    1. Choose a target¶

    mmm.bayesinsight mmm.hierarchical_geo (default)
    What it fits BayesInsight's model as model_def.json defines it: likelihoods (Normal, log-normal, Poisson, negative binomial, zero-inflated), priors in KPI units, Hill/linear/S-shaped curves, delayed, geometric or Weibull carry-over, enforced signs, random effects per row id, seasons, local trends The platform's hierarchical geo MMM, with every BayesInsight feature that has an equivalent mapped onto it
    Panel dims Every row id besides Period is its own dim (geo, product) One geo dim; several row ids are joined (US|Phones)
    Priors Kept, in KPI units Coefficient priors are not carried over (they would mean something else on the mean-scaled KPI): state them as business priors instead
    Guided extras Lift tests (under the model's own likelihood) Business priors, lift tests, what-if grids
    Use it when You want BayesInsight's results, reproduced and served You want to move to the platform's geo MMM and its Guided tools

    2. Import¶

    The import is pure JSON in, JSON out, the same function the API runs, so you can call it offline:

    from mapi_spec.bayesinsight import import_bayesinsight
from mapi_spec.guided import BayesInsightImport

request = BayesInsightImport(
    name="bi-sales",
    dataset="bi_mff",  # the dataset the MFF upload becomes
    target="mmm.bayesinsight",  # or "mmm.hierarchical_geo" (the default)
    model_def=json.loads(Path("model_def.json").read_text("utf-8")),
    metadata=json.loads(Path("metadata.json").read_text("utf-8")),
)
draft = import_bayesinsight(request, project="retail")  # pure JSON: no server, no numpy
for issue in draft.issues:
    print(f"{issue.severity.value:7} {issue.pointer}: {issue.message[:70]}…")
print(sorted(draft.mapping.dims), sorted(draft.mapping.vars))

    info    /model_def/variable_details/2/adstock: Search_Total_Total_Total: BayesInsight's code cannot run 'geometric' c…
info    /model_def/variable_details/3/sign: Price_Total_Total_Total: the negative sign is enforced (BayesInsight d…
['date', 'geo', 'product'] ['price', 'sales', 'search', 'tv']

    Each issue has a severity, a JSON pointer into your files and a message:

    • info: faithful but perhaps surprising. Here, geometric carry-over is fitted as documented although BayesInsight's own code cannot run it, and the price sign is enforced (BayesInsight declares signs without enforcing them).
    • warning: something fell back to BayesInsight's default or has no equivalent. Read every one before you fit.
    • error: the project cannot be imported (no single KPI, no media or control, names that do not match the row ids); the API answers 422 IMPORT_UNSUPPORTED.

    The same project imported for the geo MMM warns about what does not carry over:

    geo = import_bayesinsight(request.model_copy(update={"target": "mmm.hierarchical_geo"}),
                          project="retail")  # fmt: skip
for issue in geo.issues:
    if issue.severity.value == "warning":
        print(f"warning {issue.pointer}: {issue.message[:70]}…")

    3. Check the draft¶

    Validate the spec against the installed catalog and the schema the mapping promises, as the API does when you save it:

    from mapi_sdk.registry import default_registry
from mapi_spec.guided import draft_schema
from mapi_spec.spec import ModelSpec
from mapi_spec.validate import validate_spec

spec = ModelSpec.model_validate(draft.spec)
check = validate_spec(spec, default_registry().catalog(), draft_schema(draft.mapping))
print("valid" if check.ok else [(e.pointer, e.message) for e in check.errors])

    valid

    draft.yaml is the spec as YAML, the file you would review in a pull request: model.settings.model_def carries your model_def.json, variables maps each analytic name (TV_Total_Total_Total) to its variable, and a core.lag_tensor step with 12 lags feeds the carry-over.

    4. Fit it on your laptop¶

    Before you spend platform compute, fit the draft in-process with tiny settings. The dataset comes from the sandboxed ingest's own code applied to the MFF table:

    from mapi_runner.jobs import IngestJob
from mapi_runner.worker.ingest import build_dataset
from mapi_sdk.harness import fit_spec

# the sandboxed ingest's own code: the MFF table through the draft's mapping
ds, schema, _ = build_dataset(Path("sales_mff.csv"), IngestJob(mapping=draft.mapping))
quick = spec.model_dump(mode="json", by_alias=True, exclude_defaults=True)
quick["model"]["fit"] = {"mode": "evaluate_then_refit", "engine": "pymc",
                         "tune": 100, "draws": 100, "chains": 2, "seed": 1}  # fmt: skip
bundle = fit_spec(ModelSpec.model_validate(quick), ds, registry=default_registry(),
                  raw_schema=schema)  # fmt: skip
post = bundle.model.posterior.mean(("chain", "draw"))
print({v: round(float(post[f"{v}__coef"]), 1) for v in ("tv", "search", "price")})
print("holdout MAPE %:", round(bundle.metrics.values["mape"], 1))

    {'tv': 25.9, 'search': 17.5, 'price': -7.6}
holdout MAPE %: 1.9

    The data was simulated with coefficients of 30 (TV), 20 (search) and −8 (price): 100 draws on two chains, well under a minute on a laptop, land close, and the eight held-back weeks are forecast within 2%. Keep the draft's own fit settings (500 tuning steps and 500 draws on 4 chains) for results you act on.

    5. Run it on the platform¶

    The same import through the API (here with the Python client; the answer is the same draft):

    remote = api.guided.import_bayesinsight(request)  # the same draft, from the platform
print(remote.dataset_ref, len(remote.issues), "issues")

    Then upload the MFF table with the draft's mapping, save the spec and fit:

    version = api.datasets.upload("sales_mff.csv", dataset="bi_mff", mapping=remote.mapping)
revision = api.specs.upsert(remote.yaml)
run = api.runs.wait(api.runs.fit(revision.spec_id, revision.revision).id,
                    raise_on_failure=True)
print(run.output_model_version_id)

    The upload is checked in a sandbox with the bayesinsight preset: only the allowed_* key values and the start_period/end_period range of metadata.json are kept, and the necessary_variables must be present. With curl, the import is POST /v1/guided/import/bayesinsight (the guide).

    The fitted version gets the same sanity scorecard as every model; promote it to an endpoint from the Integrations hub, and Atlas, Sheets and embeds work with it like with any other model.
