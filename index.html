    Labelled models · replayed preprocessing · typed, honest answers

    Fit with preprocessing.
    Score with the same preprocessing.¶

    modeling-api is a platform for Bayesian and classical models whose data has named dimensions: geo × channel × week, store × sku × day, household × trip. Describe a model in a small YAML spec or a few lines of Python. The platform checks your data, learns every preprocessing step on the training data only, and replays exactly that work whenever you forecast, add a new market or ask "what if".

    Quickstart: 10 minutes Get started How it works

    Where the project is today: v0.2, the platform runs end to end on your laptop

    make install && make dev && make seed starts the whole platform locally, without Docker: an HTTP API with an OpenAPI document, a job queue, a sandboxed runner, an object store that behaves like Google Cloud Storage, the web app and an isolated plot sandbox. From the browser, the CLI, the Python client or plain HTTP, you upload data, validate a spec as you type, fit it, follow the sampler live, inspect a signed model and score forecasts, new markets and what-ifs. The v0.1 contract layer (specs, 28 steps, 11 model plugins, plots, conformance corpus) still runs in your own Python process too. Cloud execution and multiple tenants come next: see the roadmap.

    Why labelled, multi-dimensional models?¶

    Most model-serving stacks see a matrix: rows in, numbers out. Real business models do not live in a matrix.

    What goes wrong with positional data

    • Column 7 used to be search spend; after a schema change it is social.
    • The forecast starts in week 53, but the lag features were built from week 1.
    • A market opens. Is it row 12? Does the model even know it is new?
    • Revenue was scaled by the mean, so the prediction came back in "1.37".
    • Someone sums the 90% quantiles of 40 stores and calls it the 90% quantile of the total.

    What modeling-api does instead

    • Every array is an xr.Dataset with named dims and coordinates; nothing is positional, so shuffled, subset or reordered data scores the same.
    • Each dim declares what may happen at score time: fixed, extend (time) or new_levels (markets, stores, counties) with a declared strategy.
    • Every output says what it is: its representation (draws, quantiles, interval, point, moments), its units and its output space.
    • Requests that cannot be answered honestly fail before any compute, with a typed error code and a JSON pointer.

    The whole story in one picture¶

    The same pipeline object runs at fit time and at score time. At fit time each step learns its state from the training data; at score time it replays that state. Steps that look back in time store a small per-group tail, so a forecast sees exactly the history the model was fitted on.

    M --> BUN[("Bundle<br/>states · context tails · posterior<br/>hashes · no pickle")]

        direction LR
        F["Next quarter's plan<br/>or a new market"] --> G["same steps,<br/><b>replayed</b> state"]
        G --> H["model.score"]
        H --> I["inverse → weekly EUR<br/>summaries · your names"]
    end
    BUN --> G
    pipeline:
  - {id: to_eur, use: core.fx_convert@^1, with: {vars: [y, spend], table: fx, ...}}
  - {id: weekly, use: core.resample@^1,   with: {dim: time, freq: W-SUN, how: sum}}
  - {id: scale,  use: core.mean_scale@^1, with: {vars: [spend], over: [time]}}
  - {id: lags,   use: core.lag_tensor@^1, with: {vars: [spend], along: time, within: [geo], l_max: 6}}
model:
  use: mmm.hierarchical_geo@^1.3
  fit: {mode: evaluate_then_refit}
    1. Checks the whole spec statically: names, dims, settings, units at every stage, where the split happens and whether any step would learn from the holdout (LEAKAGE_RISK).
    2. Fits each stateful step on the training weeks only, fits the model, then scores the holdout through the same path a forecast uses and records the metrics.
    3. Refits on all weeks so forecasts start from the latest data, and writes a bundle with every state, context tail and hash.
    • Forecasts in weekly EUR, not "model units": scaling is inverted, and inversion stops at the weekly resample because daily values cannot be recovered from weekly sums. The output says so in its output_space attribute.
    • A new market drawn from the fitted hyperprior, honestly wider than a known one.
    • What-if deltas that share their noise with the baseline (common random numbers), so the delta reflects the change, not sampling noise.

    Safe by construction¶

    • No pickle, anywhere

      Bundles are single zarr zips plus JSON sidecars. Native models are stored as skops (allow-listed types) or xgboost JSON. Every file carries CRC32C, MD5 and SHA-256, and reading verifies them.

    • Contracts are pure JSON

      mapi-spec never imports numpy or xarray, and the control plane never imports plugin code. Specs are validated from exported static JSON: settings schemas and schema effects. An import-linter contract enforces it.

    • Plots are sanitized

      Vega-Lite and Plotly specs are checked against pinned schemas. URL data, links, external images, tile maps, prototype keys and unsafe expressions are rejected before anyone sees a chart.

    • Typed errors, early

      UNSEEN_LEVELS, HORIZON_EXCEEDS_FIT, MISSING_FUTURE_COVARIATE, CAPABILITY_UNSUPPORTED, … Stable codes, HTTP statuses and JSON pointers, raised before any compute is spent.

    Built for two kinds of people¶

    • Guided: analysts

      Marketing and finance analysts pick a template, answer questions in business terms ("which column is revenue?"), enter priors as ROI ranges, and get a report with a sanity scorecard, plain-language captions on every plot and instant what-if sliders.

      Every plot recipe already ships a caption_plain and a persona, every model setting an x-ui-level, and every scorecard item a plain-language message. The Guided UI arrives in v0.4.

    • Expert: data scientists

      Write specs and plugins, inspect posteriors and preprocessing state, and pull any bundle into a notebook. The Expert web app, the mapi CLI and the Python client work today, and so does everything in plain Python.

      The Expert web app

    • Plugin authors

      A PyMC model is one build() method; an sklearn model is one estimator(). The contract kit tells you, before anyone runs your code, whether you followed the rules.

      Port a model

    • Integrators

      A versioned HTTP API with an OpenAPI 3.1 document, RFC 7807 errors, idempotency keys and server-sent events, plus a typed Python client. Endpoints, webhooks and MCP tools follow in v0.4.

      HTTP API guide

    What you get in v0.2¶

      A supervisor and worker per run, HMAC-signed events, outputs checked against the store's own checksums and a signed manifest. Security model

    • Labelled data contract

      DataSchema, dim policies, roles, units, ragged layouts and plain-language data checks. Labelled data

    • Stateful pipelines

      28 built-in steps with fitted state, stages, splits, context tails and inverse transforms. Steps catalog

    • PyMC and scikit-learn

      nutpie, PyMC (segmented and resumable), MAP, ADVI; allow-listed sklearn and xgboost estimators with quantile, bootstrap and conformal uncertainty. Guides

    • Marketing-mix models

      A hierarchical geo MMM with response curves, marginal costs and a budget objective, and an adapter for pymc-marketing. MMM guide

    • Forecasting

      HSGP trends with horizon contracts, HMMs with terminal state and filtering. Time series

    • A conformance corpus

      Six reference problems run end to end on every change: validate, fit, score, evaluate, contract kit, plots. Corpus

    How it compares¶

    MLflow and BentoML are excellent at what they target: packaging a trained model from almost any framework and serving it behind an API. modeling-api targets a narrower problem, labelled statistical models whose preprocessing, coordinates and uncertainty must survive the trip to production, and makes different trade-offs.

    Tabular model serving (MLflow / BentoML style) modeling-api
    Input contract Column or tensor signatures: names and shapes, no dimensions xr.Dataset with named dims, coordinates, roles, units and per-dim score policies
    Preprocessing at score time Up to you: bundle it into the model artifact, or re-implement it in the service Declared steps with fitted state, replayed exactly; stage-aware splits and per-group context tails
    New groups and horizons Whatever the model happens to do with an unseen row Declared per dim (fixed, extend, new_levels + strategy); checked before compute
    Uncertainty Point predictions by default; intervals are a custom output A first-class representation that decides which summaries and aggregations are valid
    Units of the answer Whatever space the model was trained in Inverted to original units, with the output space recorded on every variable
    Serialization Framework-native; pickle and cloudpickle are common Zarr zip + JSON, skops or xgboost JSON; pickle is rejected on write and on read
    Validating a request At call time, inside the model Statically, from JSON, before a run starts: typed errors with JSON pointers
    Who it is for Any model, any framework Bayesian and classical models of panels, time series and hierarchies; analysts and data scientists

    A taste¶

    The same model in plain Python, without any server. The Python guide builds it end to end; every snippet on this site is executed by the test suite.

    from mapi_sdk import fit_spec

bundle = fit_spec(spec, data, registry=registry, raw_schema=schema)
print(bundle.metrics.values)  # holdout metrics, in units sold: {'rmse': ..., 'mape': ..., ...}
print(bundle.metrics.n_holdout)  # 48 cells: 3 stores x 2 skus x 8 weeks

    from mapi_spec import ErrorCode, MapiError


def try_score(request_yaml: str, payload: xr.Dataset) -> ErrorCode:
    try:
        score_bundle(bundle, request_yaml, payload, registry=registry)
    except MapiError as err:
        print(err.code, "-", err)
        return err.code
    raise AssertionError("expected a typed error")


FORECAST = """
apiVersion: mapi/v1
kind: ScoreRequest
model: endpoint://quickstart/fruit-demand
mode: forecast
horizon: {dim: time, periods: 4}
"""

# 1. a forecast without next month's promotions: promo is future_required
code_1 = try_score(FORECAST, plan.drop_vars("promo"))

# 2. quantiles are per cell, so "total over all stores" would be a made-up number
code_2 = try_score(FORECAST + "output: {aggregate: {over: [store]}}\n", plan)

# 3. a product outside the fitted range: sku is a fixed dim
code_3 = try_score(FORECAST, plan.assign_coords(sku=["apples", "kiwis"]))
