    Guided mode for analysts · exact control for data scientists · honest uncertainty · one safe platform

    Trustworthy models,
    from spreadsheet to endpoint.¶

    modeling-api fits Bayesian and classical models of data that has named dimensions (market × channel × week, store × product × day, household × trip). It also fits science models of images, fields, maps and graphs, causal models that measure the effect of a change, and neural networks for tables and images. The models answer questions in the units that your business uses. An analyst uploads a spreadsheet and gets a report, a sanity scorecard and instant what-if sliders. A data scientist writes a small spec or some lines of Python and gets the same model behind a versioned endpoint. Each call uses the same fitted preprocessing again, exactly.

    Full analyses (tests, decisions, models and benchmarks) run as versioned workflows. A model goes live only after it is better than shuffled data, fake drivers and a naive forecast. Each run occurs in a new sandbox, and each result tells how sure it is. Each run also keeps its metrics, params, tags and images, so that you can compare runs side by side.

    Two ways in, one model¶

    Analysts¶

    Upload → report → scenario in minutes, with honest uncertainty.

    • Select what you want to learn. Answer questions such as "which column is revenue?". The platform suggests the answer and tells you why.
    • Tell what you already believe ("TV returns 1.5 to 4 per euro"), or enter a lift test.
    • Read a report in plain words. A sanity scorecard tells you if you can trust it.
    • Move the what-if sliders. Your browser gives the answers. The range stays honest when some channels move at the same time. "Run exact" asks the full model.
    • Share a live chart, or put the model in a Google Sheet.
    • Measure the effect of a campaign or a geo-lift test with the Effect of a campaign and Geo-lift test templates. Use the result as a lift test for your marketing mix.
    • If you are not sure which model to use, use Help me choose. It asks some questions and explains its recommendations. Each option has an About card in plain words.

    Data scientists¶

    Any PyMC, scikit-learn, JAX or forecasting model. The same preprocessing, exactly. Endpoints in one click.

    • A PyMC model is one build() method. An sklearn model is one estimator(). Built-in marketing-mix, forecasting, causal, demand, choice and classification models are ready to use. So are 15 science models and three neural networks for tables and images.
    • Each run logs its metrics, params, tags and images. Log your own from model code, a notebook or mapi runs log-metric. Filter, sort and compare 2 to 10 runs side by side, and group them in experiments.
    • Steps learn on the training data only. At score time, the platform replays them and does not fit them again. This applies to forecasts, new markets and counterfactuals.
    • Uncertainty is a primary part of each result: draws, quantiles or intervals. Each one has the aggregations that are valid for it.
    • Promote a version to an endpoint through the scorecard gate. Copy a snippet for Python, TypeScript, curl, R, Apps Script or a notebook.
    • Automate the statistics with workflows of tests, branches, searches, backtests and governance checks. Posterior summaries, predictive checks, stacking weights and plots are nodes too. Run them live from mapi workflows run --watch or api.workflows.

    How it works¶

    flowchart LR
    D["Your data<br/>CSV · Parquet · MFF ·<br/>Meridian · NetCDF · HDF5 ·<br/>images"] --> I["Sandboxed ingest<br/>checked, profiled,<br/>dims and roles"]
    Q["Guided answers<br/>or a YAML spec"] --> V{{"Static checks<br/>before any compute"}}
    I --> V
    V --> F["Fit in a fresh sandbox<br/>preprocessing learned<br/>on train only"]
    F --> B[("Signed bundle<br/>states · posterior ·<br/>scorecard · grids")]
    F -.-> T["Run tracking<br/>metrics · params ·<br/>images · compare"]
    W["Workflow<br/>tests → decisions →<br/>search → backtest"] -.-> F
    B --> R["Report, explorers,<br/>what-if, budget plans"]
    B --> G{{"Governance<br/>null tests · benchmarks ·<br/>second-person approval"}}
    G --> E["Endpoint<br/>gated on the scorecard<br/>and the validation"]
    E --> S["Sheets · BI embeds ·<br/>webhooks ·<br/>Python, TS, R"]
    1. Your data stays labelled. The upload becomes an xr.Dataset with named dims, roles and units. No later part of the process uses the position of the data.
    2. Mistakes fail early. Examples are a spec that leaks the holdout, a forecast past the limit of the model, or a market that the model did not see. You get typed errors before any compute.
    3. The fit learns, and the score replays. Each preprocessing step stores what it learned. Thus a forecast or a new market goes through exactly the same transformations. Then the result goes back into your units.
    4. The platform checks results two times. It compares the outputs with the checksums of the storage, and it signs them. The scorecard checks convergence, holdout error and plausibility.
    5. Models must show that they are good. A governance policy applies null tests and benchmarks to each version and records the evidence. If you ask, it waits for a second person. Endpoints can refuse all versions that are not validated.
    6. Other tools connect to an endpoint, not to a file. Promote a better model, and all integrations use it. Roll back with one call.
    7. Full analyses repeat automatically. A workflow runs the tests, decisions, fits and checks again each Monday, or when the data changes. It uses again each step whose inputs did not change.
    8. Each run keeps its record. A run logs its metrics, params, tags and images while it runs. You can search the runs, compare them side by side and group them in experiments.

    Your first MMM in Guided mode¶

    This section shows the full path of a geo marketing-mix model. The path starts with a spreadsheet of weekly spend and revenue by region. It ends with a budget scenario. The times are from an automated "tester" on a laptop. The platform used almost all of this time. The full path took 135 seconds from upload to scenario.

    1. Choose "Geo marketing mix". Then drop your CSV file on the page. The platform makes a profile of each column in your browser. It suggests which column is revenue and which columns are spend. It also tells why. (5 s)
    2. Say what you believe, if you have beliefs. For example, give an ROI range for each channel, or a lift test. Preview what this means shows it in business units before the fit. (22 s, optional)
    3. Fit the model. The progress shows in plain language. The platform tests the model on weeks that it did not see. Then it fits the model again on all the data. (80 s)
    4. Read the results. You see the ROI and share of each channel with 90% ranges. You also see the sanity scorecard, with the next action for each check. (instant)
    5. Ask "what if". Move search +20%. The change in revenue and its range show immediately. Run exact confirms the result with the full model. (30 s with the exact run and a forecast)
    6. Share it. Put the model live as an endpoint, or share a chart with a link.

    The core idea: fit with preprocessing, score with the same preprocessing¶

    The same pipeline object runs at fit time and at score time. At fit time, each step learns its state from the training data. At score time, it replays that state. Steps that look back in time store a small tail for each group. Thus a forecast sees exactly the history that the model used for the fit.

    flowchart LR
    subgraph FIT["Fit (once)"]
        direction LR
        A["Daily spend & revenue<br/>local currency"] --> B["fx_convert<br/>(side table)"]
        B --> C["resample<br/>daily → weekly"]
        C --> S{{"split<br/>last 8 weeks"}}
        S --> D["holidays<br/><i>pinned side table</i>"]
        D --> M["model.fit<br/><i>keeps the fitted history<br/>for carry-over</i>"]
    end
    M --> BUN[("Bundle<br/>states · context tails · posterior<br/>hashes · no pickle")]
    subgraph SCORE["Score (any time)"]
        direction LR
        F["Next quarter's plan<br/>or a new market"] --> G["same steps,<br/><b>replayed</b> state"]
        G --> H["model.score"]
        H --> I["inverse → weekly EUR<br/>summaries · your names"]
    end
    BUN --> G
    pipeline:
  - {id: to_eur, use: core.fx_convert@^1, with: {vars: [y, spend], table: fx, ...}}
  - {id: weekly, use: core.resample@^1,   with: {dim: time, freq: W-SUN, how: sum}}
  - {id: hols,   use: core.holidays@^1,   with: {table: holidays, along: time}}
model:
  use: mmm.bayesian@^1                 # mmm-framework: scaling and carry-over inside
  settings: {hierarchy: {pool_over: [geo]}, new_levels: hyperprior}
  fit: {mode: evaluate_then_refit}
    1. The platform checks the full spec statically. It checks names, dims, settings and units at each stage. It also checks where the split occurs, and if a step can learn from the holdout (LEAKAGE_RISK).
    2. It fits each stateful step on the training weeks only, and then fits the model. Then it scores the holdout through the same path that a forecast uses and records the metrics.
    3. It fits again on all weeks, so that forecasts start from the latest data. Then it writes a bundle with each state, context tail and hash.
    • Forecasts in weekly EUR, not in "model units". The model reports its own units. The units stop at the weekly resample, because you cannot get daily values back from weekly sums. The output_space (model-owned) and units attributes of the output tell this.
    • A new market that comes from the fitted hyperprior. Its range is honestly wider than the range of a known market.
    • What-if deltas that share their noise with the baseline (common random numbers). Thus the delta shows the change, not the sampling noise.

    from mapi_spec import ErrorCode, MapiError


def try_score(request_yaml: str, payload: xr.Dataset) -> ErrorCode:
    try:
        score_bundle(bundle, request_yaml, payload, registry=registry)
    except MapiError as err:
        print(err.code, "-", err)
        return err.code
    raise AssertionError("expected a typed error")

    Secure by design¶

    The platform can run models and data from persons that it does not trust. The most important controls are not settings that you can forget to set. They are part of how the platform works. The security model tells what each control stops. It also tells what we must still verify in the cloud.

    • A fresh sandbox per run

      Each ingest, fit, score and render runs in its own sandbox (a microVM on Cloud Run Jobs). The sandbox has no secrets. Its only network access is signed URLs to its own objects. The code enforces the placement by trust tier.

    • Tenants never see each other

      Each table has PostgreSQL row-level security. It is pinned for each transaction, and it fails closed. The platform checks roles at each request. Operators manage the platform, but they do not read tenant data.

    • Outputs are claims

      The platform compares the outputs of a run with the hashes and generations of the store. Then it copies the outputs to a location where runs cannot write, and signs them. It makes download links only after it verifies the signature.

    • Integrations that cannot be turned against you

      Webhooks are HMAC-signed. They go through an SSRF guard that pins the checked address. Embed links show only platform recipes and have no credential. You can revoke them. Snippets never contain a secret.

    • Compute you can see and cap

      Quotas are in vCPU-seconds for each token, tenant and platform. Each token that calls an endpoint has a budget. Each run shows a cost. There is a global spend cap and an audited kill switch.

    • No pickle, anywhere

      Bundles are single zarr zips plus JSON sidecars. Native models are skops (allow-listed types) or xgboost JSON. Network weights are safetensors files. Each file has CRC32C, MD5 and SHA-256 values. The platform verifies them when it reads the file.

    Run it for many teams¶

    One deployment serves many organisations. Users sign up, or sign in with their own identity provider. They work in the projects where they have a role, and they see the cost of their compute. Operators manage the platform, but they never read the data of a tenant.
