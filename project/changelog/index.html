    [Unreleased]¶

    [0.5.0] — M3.5: Workflows, governance, explorers, mmm-framework — 2026-10-16¶

    Analyses can now be automated and models held to written rules before anyone relies on them. A workflow chains statistical tests, data processing, train/test plans, searches and model fits into a versioned, scheduled pipeline; a governance policy says which checks a model must pass (including null tests that show it beats noise) and whether a second person must approve it; and the Data and Model Explorers show what is in the data and in the fit. mmm-framework is now the only marketing-mix engine, with budget optimisation built on its planning module, and twelve statsmodels time-series models join the catalog. Everything was verified on a laptop against a live local stack (the GCS shim, embedded Postgres, the local-process executor); real Google Cloud, Docker and human testers are still to come (see Known gaps). In summary:

    • workflows (mapi-workflows, migration 0011): a declarative WorkflowSpec (a DAG of 51 typed nodes: statistical tests, transforms, splitters, searches, model fit, backtest, evaluate, compare, select, governance, report, branch.if with a safe expression language and plain-language explanations, sub-workflows) run by the server's orchestrator with per-node child runs in the sandbox, server-sent events, caching of unchanged nodes, cost roll-up, cron schedules and new-dataset-version triggers. A gallery of templates: time-series readiness to ARIMAX (seasonal and ordinary differencing decided by ADF, KPSS, Phillips-Perron and Zivot-Andrews with an over-differencing guard, an AIC search of the AR and MA orders, an expanding-window backtest against naive benchmarks, selection and governance), VAR or VECM by the Johansen rank, the governed marketing mix and a forecast bake-off. The web app has a visual workflow builder (React Flow), a live run monitor and Guided recipes.
    • governance (migration 0012): tenant- and project-scoped, versioned policies over 12 checks (shuffled-driver permutation test, noise-placebo drivers, time-shifted drivers, beats naive, holdout accuracy, residual whiteness, rolling parameter stability, sign constraints, prior sensitivity, parameter recovery, convergence, data quality); a validation state machine; second-person approval by a member with the reviewer capability (never the submitter); a promotion gate (NOT_VALIDATED) that checks the validation covered every gating policy as it stands now; HTML and JSON evidence packs; policy editor and review queue in the web app.
    • explorers: the Data Explorer (13 sections: profile, distributions, time plots, missingness, outliers, correlations, prewhitened cross-correlation with the KPI by lag, ACF/PACF, stationarity, STL and seasonal strength, VIF, group comparisons, data-quality warnings) and the Model Explorer (parameters, diagnostics, fit, residual tests, contributions, response curves, IRF/FEVD, forecasts, backtests, side-by-side comparison, governance evidence, lineage), computed in the sandbox (explore run kind).
    • models: mmm.bayesian and mmm.frequentist on mmm-framework==1.5.0 (national and geo/product panels, MFF ingest with mmm-framework's semantics, business priors, lift-test calibration, response grids, counterfactuals, scorecard) and budget plans through POST …:optimize (the optimize run kind: allocation, efficient frontier, chance of beating the current plan) in Expert and Guided mode. mapi-plugin-statsmodels: ts.sarimax, arima, var, vecm, varmax, ecm, ardl, ets, unobserved_components, dynamic_factor, markov_switching and theta, with future exogenous drivers, quantile intervals, IRF/FEVD and cointegration rank selection.
    • About cards and Help me choose: every model, step, split, template, workflow node, governance check and dataset carries a plain-language About card (the catalog refuses items without one); a chooser asks a few questions and ranks what fits.
    • client, CLI and docs: client calls and mapi workflows, mapi governance, mapi validations, mapi explore, mapi optimize, mapi choose and mapi about; the v0.5 documentation site (workflows, governance, null tests, explorers, mmm-framework, the workflow cookbook, generated node and check references); a generated THIRD-PARTY-NOTICES.md shipped in every image.
    • removed (breaking): Atlas (mapi_client.atlas), BayesInsight (importer, plugin, ingest preset, route), mmm.hierarchical_geo and the pymc-marketing adapter; see Removed below.

    The M3.5 review found 46 defects (conformance and UX, security, statistics, reliability); all were fixed before the release, each with a regression test (the Fixed sections below).

    Added¶

    • spec: the M3.5 contracts for workflows, governance, explorers, budget optimisation and About cards, shared by the server, runner, plugin, web and client components. The contract version is now 0.2 (the removals below are breaking).
    • mapi_spec.about and mapi_spec.abouts: the plain-language About card (summary, use and avoid when, data needs, assumptions, outputs, difficulty, typical runtime, example, related items, expert notes) on model manifests, step, split and plot catalog entries, guided and workflow templates, workflow node kinds and implementations, governance checks, and DatasetAbout for datasets (the owner's description plus a summary generated from the schema); the catalog rule (ABOUT_INCOMPLETE) and cards for every built-in step, split, model (including the mmm-framework and statsmodels ids of v0.5) and template; the "Help me choose" questions and the deterministic recommend ranking.
    • mapi_spec.workflow, .workflow_nodes, .workflow_templates: versioned WorkflowSpec DAGs of typed nodes (test, transform, branch, split, search, model, evaluate, compare, select, governance, report, subworkflow) with typed ports, parameters, alternatives and branch gating; static validation with JSON pointers (types, references, parameters, cycles, unreachable nodes); the node catalog (51 implementations with parameter schemas, result fields and About cards); runs, node runs, branch decisions, cache keys, cron schedules, dataset triggers and events; four gallery templates including the canonical readiness-to-ARIMAX workflow.
    • mapi_spec.expr: the safe condition language of branches (a hand-written parser and an evaluator over JSON with hard limits; never eval). mapi_spec.cron: schedules.
    • mapi_spec.splitplan: multi-fold split plans (holdout, rolling origin, expanding window, blocked and purged k-fold, geo holdout, nested) with pure fold computation that matches scikit-learn's splitters. mapi_spec.stattests: test results and decisions.
    • mapi_spec.governance: versioned tenant and project policies, the twelve-check catalog (null tests against shuffled targets, noise drivers and time-shifted placebos, naive benchmarks, residual whiteness, stability, signs, prior sensitivity, simulated recovery, convergence, holdout accuracy, data quality), evidence, the pure validation state machine, approvals by a second person with the reviewer capability, and the evidence pack. The promotion gate refuses unvalidated versions when a policy says so (NOT_VALIDATED).
    • Data Explorer and Model Explorer views (mapi_spec.views) and their requests (mapi_spec.explore); OptimizeRequest/OptimizeResult for POST …:optimize mapped onto mmm-framework planning (mapi_spec.optimize).
    • RunKind workflow (a parent), workflow_node and explore; M35_ENDPOINTS (60 operations) merged into ENDPOINTS, with access rules; resources workflow, policy, tenant_policy, actions validate and approve, the reviewer capability on memberships; scopes workflows:write, workflows:run, models:validate, policies:manage (no token can approve); audit actions, webhook events and problem codes for all of it.
    • sdk: Step.about and CustomModel.about/family, and the contract kit's About check (check_about, and an about check in check_step/check_model).
    • plugins: mapi-plugin-statsmodels (Apache-2.0; statsmodels is BSD-3-Clause), twelve ts.* models: ts.sarimax (ARIMAX/SARIMAX), ts.arima, ts.unobserved_components, ts.ets, ts.theta, ts.ardl, ts.ecm (UECM with the Pesaran-Shin-Smith bounds test), ts.var, ts.vecm (Johansen rank selection), ts.varmax (VARX), ts.dynamic_factor and ts.markov_switching. Panels loop over settings.series_dims; outputs are prediction-interval quantiles; forecasts need future drivers (MISSING_FUTURE_COVARIATE). Bundles hold parameters and data only - no pickle - and scoring rebuilds the results (Kalman filter/smoother with the stored parameters, or deterministic re-estimation checked against them). Fits store parameter tables with standard errors and p-values, fit statistics, residual tests, impulse responses with bands, variance decompositions, Granger tests, the Johansen table, ECM bounds tests, smoothed components, factors and regime probabilities; explorer_views() turns them into Model Explorer sections. Reference-value tests against direct statsmodels calls and the statsmodels VAR documentation; conformance fixtures sm_arimax and sm_vecm_macro. The plugin ships in mapi/base-forecast.
    • docs: Workflows, Governance and About cards concept pages; the v0.5 section of the HTTP API reference; the statsmodels time-series models page.
    • plugins/mmm: mmm-framework (mmm-framework==1.5.0) is the MMM engine. mmm.bayesian (mmm-framework's BayesianMMM: national, or partially pooled over geos and products; NUTS on nutpie, PyMC or NumPyro, or MAP/ADVI/Pathfinder/Laplace/SMC) and mmm.frequentist (its ridge estimator with bootstrap intervals). Both own scaling, carry-over and units, score by replaying the fitted model per draw in NumPy (checked against mmm-framework's forecaster), prepend the fitted history so carry-over reaches scored periods, follow new_levels (pooled, hyperprior, zero, error) for unseen geos/products, and cache contributions, response curves and marginal costs. Business priors translate in closed form into log-normal ROI priors (and an intercept prior solved against mmm-framework's own baseline prior); lift tests become mmm-framework experiment likelihoods (marginal ROAS or contribution). MFF panels are handed over in the layout MFFLoader builds.
    • runner, server, sdk: the optimize run kind and POST /v1/models/{model_id}/versions/{version}:optimize with GET /v1/optimizations/{run_id} (Prefer: wait, Idempotency-Key, an optimize.completed webhook): budgets split across channels (or geo x channel) by mmm-framework's planning module from the posterior's response curves, with bounds, groups, risk objectives, a horizon and the efficient frontier; the mmm.budget_plans plot. CustomModel.optimize and mapi_sdk.models.BudgetPlan are the plugin hook.
    • conformance: e33 and guided_mmm fit mmm.bayesian; the mmm_frequentist fixture.
    • docs: "Marketing-mix models on mmm-framework" (data contract, how the spec maps onto mmm-framework, priors, lift tests, optimisation, limits), the rewritten marketing-mix guide and the "Optimise a budget" tutorial.
    • workflows (new distribution mapi-workflows): the workflow engine and its nodes.
    • A JSON-only engine (mapi_workflows.engine) that both the control plane and a local runner drive: topological scheduling with max_parallel, branches evaluated with the safe expression language, input alternatives, skips, retries, on_failure: continue, cancellation, deadlines, cache keys and an event log; orchestrator nodes (compare.models, select.best, select.threshold, report.summary, report.evidence_pack) computed on JSON results only.
    • The data nodes (mapi_workflows.runtime, extra runtime): 17 statistical tests checked against statsmodels, scipy and arch reference values (Phillips-Perron included), transforms, the seven train/test plans, ARMA/SARIMA/VAR-lag/cointegration-rank searches, grid searches, backtests (window plans, masked k-fold, geo hold-outs), forecasts, benchmarks, metrics, residual diagnostics, Diebold-Mariano with the HLN correction and governance nodes over pluggable check runners (mapi.governance_checks).
    • LocalRunner: runs a workflow in-process (threads, timeouts, cancellation, an in-memory cache, sub-workflows); the canonical ts_readiness_arimax template runs end to end.
    • The generated node reference (docs/reference/workflow-nodes.md).
    • runner: the workflow_node run kind executes one node in the sandbox, with model inputs loaded from their bundles.
    • server: workflows (migration 0011_workflows, seven tables under forced row-level security): documents and revisions validated at every save, runs as workflow parent runs driven by the orchestrator's workflow loop, nodes as workflow_node, fit and child workflow runs, derived datasets registered as wf-<workflow>-<node> versions, cache reuse across runs, cancellation through the run state machine, SSE events, output links, cost roll-up, cron schedules, dataset.version.created triggers with debounce, webhooks and audit; the dispatcher and reconciler skip parent runs.
    • docs: the workflows guide (docs/guides/workflows.md) with the canonical document and a cookbook whose fragments are validated by a test.
    • Governance (server, runner): policies, validations and approvals end to end.
    • Every check of the catalog runs in a sandboxed governance run (new run kind, GovernanceJob → governance.json), model-family aware (Bayesian, frequentist, machine learning) under a refit budget: block-permutation null test, placebo noise drivers (new channels or variables, measured by ablation through the score path), time-shift placebos, naive and seasonal-naive benchmarks out of sample, Ljung-Box whiteness, rolling-window stability, effect signs, prior sensitivity, parametric-bootstrap recovery, convergence, holdout accuracy and data quality, each with message_plain, a suggested_action (new on CheckResult) and evidence.
    • Migration 0012_governance: versioned governance_policies, model_validations and validation_approvals (forced row-level security) and memberships.capabilities.
    • Policy CRUD for projects and tenants with versions and retirement; the platform's default policies per model family (DEFAULT_POLICIES, seeded on a tenant's first use; they never gate promotion by themselves); validation requests, resubmission, cancel and deprecation; second-person approval with the reviewer capability (never the submitter, never an API token); the promotion gate refuses unvalidated versions with NOT_VALIDATED when a policy requires it (audited as endpoint.promote_not_validated); evidence packs as JSON and self-contained HTML; audit rows and webhook events for every step.
    • Explorers (runner, plots-core, server): the 13 Data Explorer sections (overview, distributions, time series, missingness, outliers, correlation, cross-correlation, ACF/PACF, stationarity, STL, VIF, group comparisons, quality warnings) and the 11 Model Explorer sections (parameters, diagnostics, fit vs actual, residual tests, decomposition, response curves, IRF, FEVD, forecasts, backtests, comparisons) computed in the sandbox: the quick data sections at every ingest, the model sections at every fit, the rest in explore runs (POST …/explore, cached per request). POST /v1/models:compare compares several versions with Diebold-Mariano tests. Vega-Lite recipes for every view in mapi_plots.explorer (JSON-only). Dataset About (GET/PATCH …/about). Statistical helpers are validated against statsmodels/scipy reference values.
    • docs: guides "Validate models with governance policies", "Explore a dataset" and "Explore a model".
    • integration (M3.5 parts working together):
    • Workflow model nodes fit the real models: mapi_workflows.testing.test_registry() registers the statsmodels plugin (extra mapi-workflows[testing]), and the canonical readiness -> ARIMAX workflow runs end to end on the real ts.sarimax (in-process, through the server and on the real runner).     • Checks and explorers on every family (statsmodels, mmm-framework Bayesian and frequentist, PyMC time series, tabular, scikit-learn, choice), tested on every conformance fixture: the Model Explorer prefers a plugin's own views (explorer_views, e.g. the statsmodels IRF/FEVD and test tables); predictions are compared with the observed target at the model's stage (pipelines that resample or convert currencies); score requests name the spec's supplied side tables.

About cards for the five scikit-learn models; a test holds every selectable item of the installed catalog (models, steps, splits, guided and workflow templates, workflow node kinds and nodes, governance checks) to a complete card.

    • About cards (plain language first, expert notes and references collapsed) in the catalog's new Browse tab (every selectable item, filtered by kind, difficulty and text), the model and step details, the spec editor (an About tab, a button on every pipeline step) and the Guided template cards; dataset About (the owner's description, editable, next to the generated summary) on the dataset page and the Data Explorer.

    • Mock-mode fixtures computed by the real runner and plots-core (apps/web/scripts/gen_explorer_fixtures.py, --check in CI) and generated TypeScript types of the explorer views; the guides' screenshots (make docs-screenshots-explorers).

    • Workflows: the list and the template gallery with About cards; a "use this template" wizard (name, parameter defaults, bound data); a Guided "run this recipe on my data" flow. Problems are pinned to nodes by their JSON pointers; revisions are saved with expected_revision and compared side by side.

A node drawer shows test verdicts, cached-vs-ran, outputs (tables, scores, folds, reports, evidence, charts in the plot sandbox, file downloads), child runs and logs. Schedules use a cron editor with presets and a preview of the next firing times that matches mapi_spec.cron; triggers fire on new dataset versions.
    • Governance: the policy editor (project and tenant-wide; covers, checks with About cards, severity, limits checked like the server, parameters; approval and promotion switches; versions with a diff; retire), the check catalog, validations with the status path and history, per-check evidence with plain messages, what to do and the shuffled-result distribution, approve/reject (never the submitter; hidden without the reviewer capability), resubmit, cancel, deprecate and the evidence-pack export.     • web: the M3.5 screens work as one app.
    • Navigation per persona: Guided mode lists Guided, Help me choose and Recipes (the workflow gallery as recipes) first, as does a Guided-locked project; Expert mode has Workflows, Governance and Help me choose (G O).

    • A finished workflow run links each model it fitted to the Model Explorer and the version's validations (run summary, fit step, outputs); a workflow run's run page opens its monitor, and lineage links the workflow run that fitted a version.

Explorer and governance screens share one validation cache and badge.
    • The Data Explorer offers the readiness workflow with the data bound (?data= on the recipe and template wizard pages).

Folds step periods apart only overlap up to ceil(h / step) - 1 folds; the node now reads the spacing from the folds (backtest and benchmark metrics carry each fold's origin, origins) or a step parameter, and uses that many autocovariances with the matching correction (details.variance_lags).

It now counts ARMA terms only (ar.L*, ma.L*, seasonal terms, ARDL/ECM lags of the target), stored per series as model_df, which residuals.whiteness also uses (it previously ignored seasonal AR/MA terms).

It shuffled blocks of the result's levels (which keeps the series' own persistence and adds a level jump at every block edge, including the train/test boundary) and compared raw holdout errors, whose spread came from which levels landed in the test periods: in simulation it rejected 35% of random walks and 33% of real AR alternatives, and a marketing mix model with no media signal passed.     Known gaps¶

    • No human testers yet. No non-technical user has tried the Guided recipes, Help me choose or the About cards, and no reviewer has used the approval screens on real models. The M3 tester protocol applies, with the readiness recipe as an extra task.
    • Real Google Cloud and Docker are unverified. Every workflow node, validation, exploration and optimisation ran on the local-process executor against the GCS shim. The images (in particular base-bayes with mmm-framework, JAX and nutpie, and base-forecast with statsmodels and the workflow runtime), the docker and docker-gvisor executors and Cloud Run were never run. Routing a workflow node to the image of its model's plugin is tested with fakes only, and a node whose models live in different images is not refused. The licence files and notices the images copy are checked statically.
    • mmm-framework's extensions are not exposed: mmm.nested (nested and mediated effects) and mmm.multivariate (several outcomes, cross-product effects) are not in the catalog. Partial spend-cut lift tests are skipped with the reason, because mmm-framework's marginal ROAS estimand only takes spend increases.
    • Plotly static rendering still needs kaleido and a system Chrome and has not run in an image (MAPI_RENDER_PLOTLY_ENABLED); Vega-Lite renders out of the box.
    • The null tests' size and power were simulated on statsmodels, regression and a small PyMC channel model, not on mmm.bayesian or mmm.frequentist (minutes per refit); they share the same code paths. The noise-regressor share is now measured against the real drivers' effect, so existing 2%/5% limits are stricter for models with a small media share; tuned policies may want a review.
    • The Data Explorer's prewhitened cross-correlation (the new default) hides a driver whose spend follows a fixed periodic flighting pattern; the raw view is one switch away.
    • Child runs a workflow's orchestrator starts are bounded by the active-run limit and the dispatcher's per-tenant concurrency and vCPU budgets, but not by the per-token admission quotas, which need a request. Schedules and triggers re-check their creator only when they fire (they pause themselves then); the reason is in the audit log, not in their API representation.
    • mapi workflows run --watch and the engine's skip reasons still say "took the then arm"; the web monitor and reports use the plain explanations.
    • Help me choose ranks ts.hsgp_trend first for a beginner forecasting one series with drivers, although it does not use them (ts.sarimax comes first for other experience levels).
    • The licences of a few Python packages with ambiguous metadata come from a hand-kept table in scripts/third_party_notices.py; re-check it when the lock bumps one of them.
    • The documentation's captured terminal outputs are kept in step by hand, and the Model Explorer comparison screenshot still shows a Diebold-Mariano verdict for forecasters.
    • Timing-sensitive tests can fail once on a fully loaded laptop (the canvas drag test of the workflow editor, the runner's checkpointed-chain test) and pass when run again.

    Fixed (M2 review: spec, server and auth)¶

    • server: an API token can no longer administer its tenant. Tokens are bound to one project, so tenant members, project create and delete, the tenant audit log and tenant usage now need a signed-in session (403 for any token). A token may still read its own tenant and list its own project (mapi_spec.api.TOKEN_TENANT_ROUTES).
    • server: signing in again no longer re-activates a disabled account. /auth/callback refuses it with the generic 401 and audits auth.login_failed; only an invitation becomes active at its first sign-in.
    • server: operator status is decided on every request from MAPI_OPERATOR_EMAILS (and the dev profile's first account). Before, a demoted operator kept operator powers through mapi login ID tokens indefinitely and through browser sessions until they expired.
    • spec/server: an API token can no longer mint tokens, whatever its scopes (mapi_spec.tokens.TOKEN_NEVER). A child token dropped its parent's expiry, vCPU budget and rate limit, and outlived its revocation. POST /v1/tokens needs a signed-in session.
    • spec/server: score:<target> tokens can score. They authorized nothing, because :score checks run on the model and the scope covered only endpoints, so integrations fell back to broader runs:create tokens. score:<model id> now covers :score on that model and score:* on every model of the project (RouteAccess.name_param). The web tokens page, the CLI help and the docs say so.
    • server: concurrent uploads can no longer overrun the storage quota. Storage admission now locks the tenant row like run admission does, so six concurrent 800-byte intents against a 1000-byte quota admit exactly one.
    • server: abandoned upload intents no longer hold storage quota forever. Usage counts a pending intent only while its signed PUT is valid, and a new housekeeper loop in the worker (MAPI_HOUSEKEEPING_INTERVAL_S, default 300 s) marks expired intents expired and deletes whatever reached quarantine.
    • server: expired browser sessions are deleted. The delete in load_session was rolled back with the request's 401, and nothing else removed web_sessions rows. The row is now deleted in its own transaction after the 401, and the housekeeper sweeps expired sessions and abandoned sign-ins.
    • server: a FINALIZING run no longer counts its vCPU estimate on top of its metered attempt. Quota usage counts an active run's estimate only while its current attempt has no actual ledger entry, so runs near a daily or monthly limit are not refused by mistake.
    • server: concurrent submissions from different tenants can no longer exceed a global concurrent_runs or vCPU limit. Run admission takes a transaction-scoped advisory lock after the tenant row when the global policy sets such a limit.
    • server: the global spend cap counts work in flight. The ledger only grows when runs finish, so every queued run used to be admitted and dispatched against the same figure. Admission now adds the estimates of admitted, unmetered runs, and the dispatcher adds the estimates of started runs and of each run it leases in the same pass.
    • server: held runs can no longer fill the dispatcher's window of queued runs and stall fair share for every tenant. Runs of suspended tenants, uploaded code paused by the kill switch and non-internal work past the spend cap are left out in SQL, and each tenant takes at most MAPI_LEASE_CANDIDATES_PER_TENANT (50) of the window.
    • server: a retry resumes from the newest checkpoints of any earlier attempt. Before, it only looked at the attempt just before it, so an attempt that died before its first segment threw away all earlier progress. Automatic infra retries are also capped by cost (MAPI_AUTO_RETRY_COST_FACTOR, default 2× the estimate), as plan §8.3 asks, and no longer by count alone.
    • server: an unknown token prefix and a wrong secret for a known prefix get the same answer (the API token is invalid), so the API no longer tells which prefixes exist. Unauthenticated failures that anyone can cause (token.auth_failed, auth.login_failed) are audited at most five times per token prefix or client and minute, so they can no longer flood a tenant's audit log. The housekeeper sweeps old rate counters.
    • server/web: run event streams re-check the caller's credential every MAPI_SSE_REAUTH_S (60 s). A revoked token, an ended session or a lost membership no longer keeps receiving a 24-hour run's progress and logs: the stream closes and the reconnect is refused. The web client stops on 401 (and raises the session-expired prompt) or 403, where it used to retry forever.
    • server: the audit log and the cost ledger are append-only (migration 0004_append_only_records). Both runtime roles lose UPDATE and DELETE on them, and a trigger refuses any change to an existing row, so a request-path bug or injection can no longer rewrite a tenant's audit trail or billing history.
    • server/infra: the default data residency follows the deployment. It used to be us everywhere, so on the documented EU deployment every run of the platform tenant and of tenants created with defaults failed as INFRA_ERROR. MAPI_DEFAULT_RESIDENCY defaults to the multi-region of the Cloud Run region, and Terraform sets it from the dispatch pool's region (default_residency overrides it). It applies to the platform tenant, to rows the tenancy migration adopts and to POST /v1/admin/tenants without data_residency. Submissions that no reporting executor can place are refused at admission with a clear 403 instead of being queued, and the worker warns at start-up about such tenants.
    • server/infra: the API and events services no longer hold the RLS-bypassing database role, which plan §9 reserves for the dispatcher, reconciler and finalizer. Their platform lookups (sign-in, memberships, operator metadata, routing pushed events) now run as a new mapi_gateway role (migration 0005_gateway_role, MAPI_DATABASE_GATEWAY_URL, MAPI_DB_GATEWAY_ROLE). It has no BYPASSRLS, gets explicit policies on identity tables and column privileges on a few run and ledger metadata columns, and cannot read datasets, specs, models, plots, attempts, events or logs. Every API request uses it automatically. Pushed events are written through tenant sessions. Terraform adds the mapi_gateway login and its db-url-gateway secret, and only the orchestrator can read db-url-orchestrator.
