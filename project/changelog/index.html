    [Unreleased]¶

    [0.4.0] — M3: Guided mode and integrations — 2026-10-16¶

    Analysts who do not write code can now build a model from a spreadsheet, read it and try scenarios on it, and teams can wire a model they trust into the tools they already use. Everything was verified on a laptop against a live local stack (the GCS shim, embedded Postgres, the local-process executor). The real Google Cloud, Docker and the five non-technical testers are still to come (see Known gaps). In summary:

    • Guided mode: a task flow for non-technical analysts. Pick a template (geo marketing mix, weekly forecast, demand by store, customer choice), upload a CSV, Parquet, MFF or Meridian table, confirm the detected column roles, state business beliefs (ROI or contribution-share ranges, a baseline) and lift tests, fit, and read a plain-language report with a scorecard. What-if sliders answer at once from a per-draw response grid (a TypeScript port of the model's own maths), and "Run exact" checks a scenario, a forecast or a counterfactual with a real score run.
    • modelling: business priors translated into model priors (translate_priors runs and a preview chart) and lift tests as calibration in mmm.hierarchical_geo and mmm.pymc_marketing; the mmm.bayesinsight built-in and a BayesInsight importer; a scorecard per version and a promotion gate that needs an audited admin override for a failing or unevaluated version.
    • endpoints and integrations: endpoints with aliases, promotion, history and rollback; generated snippets (Python, TypeScript, curl, R, Apps Script, notebook, Atlas); score answers with the summary inline; webhooks signed with HMAC, behind an SSRF guard, with an outbox, a delivery log and replays; saved plots, static PNG/SVG/PDF rendering with vl-convert and expiring embed links served by the plot sandbox; the Integrations hub in the web app.
    • trust and data lifecycle: self-service sign-up with e-mail verification, identity verification and Sybil flags with a review queue, trusted-proxy client addresses, per-tier draw and egress caps, GDPR export and tenant deletion with a grace period, and a Cloud Armor policy in Terraform.
    • client and CLI: the v0.4 Python client (endpoints, webhooks, plots, Guided, tenants) and Atlas RemoteModel, which lets Atlas optimise a budget against an endpoint; mapi endpoints, webhooks, plots, guided, priors, signup and tenant.
    • docs: a new landing page, Why modeling-api, use cases, a Tutorials section (Google Sheets, embeds, BayesInsight, webhook receivers, a first Guided analysis, Atlas), Guided and Integrations guides, the security model for v0.4, and the M3 verification report.

    Every workspace package and both web apps are versioned 0.4.0. Contract v0.1 gains only additive changes. Upgrading from 0.3 runs migrations 0007 to 0010 (Guided drafts, endpoints and webhooks, saved plots and embeds, the trust lifecycle). Multi-tenant deployments must now set MAPI_TRUSTED_PROXIES (none when clients connect directly), or the server refuses to start.

    • docs: Guided mode and Integrations concept pages; the v0.4 section of the HTTP API reference.
    • server: the Guided data path. GET /v1/guided/templates (paged) and /{template_id}; POST /v1/guided/detect-roles from browser profiles or a stored dataset version; POST /v1/guided/drafts and POST /v1/guided/import/bayesinsight, validated statically against the catalog with the schema the draft's mapping promises. Every operation documents its RFC 7807 problems in the OpenAPI document.
    • Migration 0007_guided: projects.guided_locked and dataset_versions.columns.
    • The persona lock is persisted, audited (project.guided_lock) and enforced: in a locked project, members below admin store Guided specs only, and only their basic fields may change (403 FORBIDDEN with the pointers otherwise).
    • The finalizer validates and stores an ingest's columns.json, which detection reads and …/artifacts/columns.json serves.
    • runner: sandboxed ingest for Guided mode: wide variables (one column per channel or product), the Meridian preset, MFF tables mapped like a CSV after the pivot, MffOptions.combine, and the BayesInsight preset (allowed_* values, period range, necessary variables). Caps on rows, columns, cell and name length, and decompression (gzip CSV streamed under a budget, Parquet, zip and netCDF by their declared sizes) are checked before a parser allocates; every refusal is a plain message with a suggested action. Ingest writes columns.json, the profile of every uploaded column.

    • spec: mapi_spec.bayesinsight.import_bayesinsight maps model_def.json onto mmm.hierarchical_geo - adstock, Hill saturation and pooling with BayesInsight's own priors where they have equivalents, controls, seasonality, trends - and reports every feature without one as an IMPORT_UNSUPPORTED warning (BayesInsightImport.target keeps the mmm.bayesinsight draft). Role detection gains ColumnProfile.monotonic and origin, profiles_from_dataset, draft_schema and guided_lock_issues; GuidedAnswers.format accepts mff; IngestJob gains the ingest caps.

    • docs: the "From a spreadsheet to a Guided draft" guide; the Guided mode concept page, the built-in models and the conformance guide describe the served parts.

    • mmm: mmm.hierarchical_geo declares business_priors and lift_tests calibration.

    • Business priors (ROI or contribution-share ranges at a credibility, a baseline share) become per-channel LogNormal beta_channel priors (and an intercept prior) through a vectorised location/scale bisection over Monte Carlo draws of the other priors, with a prior-predictive preview in business units and the prior mass inside each stated range (mapi_plugin_mmm.calibration; property tests check the round trip).
    • Lift tests add kpi_delta ~ Normal(implied lift, se) over the test window; the extra spend is carried over through the lag tensor and the implied lift is kept as lift_tests__model.
    • response_curves carries the baseline (intercepts and controls), closing the expected KPI.
    • mmm.pymc_marketing takes lift tests through pymc-marketing's add_lift_test_measurements.
    • runner: translate_priors runs (priors.json and the mmm.prior_beliefs / core.prior_predictive plots); every fit writes scorecard.json (the whole check catalog, or the guided template's, each measured or skipped with a reason) and the what-if grid view ui/grids/response_curves.json; forecast and counterfactual score runs write ui/guided/forecast.json and ui/guided/counterfactual.json, and a forecast's fan chart shows the fitted history with the split line. Lift tests are checked against the raw data before a fit.
    • server: POST /v1/guided/prior-translations and GET …/{run_id} (static checks of the beliefs and lift tests against the dataset summary, a pinned translate_priors run, its verified priors.json). The finalizer stores the runner's scorecard on the model version and validates priors.json; spec validation checks a spec's lift tests against the dataset.
    • sdk: FitContext.calibration and FitContext.to_original (the fitted scales); prepare_model_stage for runs that build but do not fit a model; the optional translate_priors plugin hook. sdk-pymc: PyMCModel.prior_overlap_vars keeps cheap prior draws for the scorecard's new plausibility.prior_overlap check.
    • sdk/runner/server: forecasts extend the covariates their payload lacks (ScoreRequest.future_covariates: carry_last, seasonal_naive, zero) from the fitted history (mapi_sdk.future); the server passes the fit dataset as the score run's history input. mapi_server.services.scorecards.promotion_decision derives the promotion gate from a stored model version.
    • plots: mmm.prior_beliefs (each channel's prior ROI or share against the stated range).
    • docs: Guided modelling (the translation math, the lift-test likelihood, how each scorecard check is measured, the what-if, forecast and counterfactual views).
    • server: endpoints and aliases (/v1/endpoints, migration 0008_endpoints_webhooks).
    • PUT /v1/endpoints/{alias} promotes a model version through the promotion gate: the sanity scorecard, the endpoint's evaluation policy (evaluate_then_refit by default, so endpoints serve versions refitted on all data after their holdout evaluation) and input-schema breaks. A warn needs a signed-in project admin's override with a reason (audited endpoint.promote_override; no API token can override); a fail blocks. expected_revision guards concurrent promotions.
    • History, rollback (audited with its reason) and delete; GET …/schema with an example payload, POST …/validate, and GET …/snippets rendered with the server's base URL.
    • POST /v1/endpoints/{alias}/score: inline XrJSON payloads are checked against the endpoint's input contract and the CoordPlan rules, stored as run inputs and decoded only in the sandbox; Prefer: wait, Idempotency-Key (repeat the call to collect a result), score:<alias> tokens, and the per-token rate limit and vCPU budget. Bodies are capped (413) and depth-checked before parsing.
    • server: webhooks (/v1/webhooks).
    • CRUD with the signing secret shown once and stored sealed (AES-GCM under a key derived from the server secret); rotation keeps the old secret signing for 24 hours.
    • A transactional outbox: run.succeeded, run.failed, model.version.ready, score.completed and endpoint.promoted are written in the transaction of the change; emit_tenant_event serves tenant.deletion.completed.
    • Deliveries from the worker on a webhooks procrastinate queue: signed (Mapi-Signature), retried with exponential backoff and jitter, auto-disabled after MAPI_WEBHOOK_AUTO_DISABLE_AFTER consecutive failed events or a 410 (audited), with a delivery log and replays.
    • The SSRF guard: static URL checks, one resolution with every address checked, a pinned connection with the original name as SNI and Host, no redirects, time and size caps; MAPI_WEBHOOK_ALLOW_HTTP and MAPI_WEBHOOK_DEV_ALLOWLIST for development only.
    • Metrics for promotions, endpoint calls, events, delivery tries, SSRF refusals and disabled webhooks; every new operation documents its RFC 7807 problems in OpenAPI.
    • docs: the Endpoints and webhooks guide and the webhook settings.
    • server: saved plots, static rendering and embed links (plan §10.3 items 4-5).
    • POST/GET/DELETE /v1/plots[/{plot_id}]: a model version's plot (after its signed manifest verifies) or a user-authored PlotSpec, sanitized on save and on every read. User-authored plots are recorded with author provenance whatever they claim.
    • POST /v1/plots:render (Prefer: wait, Idempotency-Key) and GET /v1/plots/renders/{run_id}: a render run of one sanitized plot. The API writes its plots.json input and pins each bundle dataset as a plotdata.<n> input. Plotly is refused with MODE_NOT_SUPPORTED unless MAPI_RENDER_PLOTLY_ENABLED.
    • POST/GET/DELETE /v1/plots/{plot_id}/embeds[/{embed_id}]: tokenised links for platform recipes only (EMBED_NOT_ALLOWED otherwise), stored as keyed hashes, with expiry, revocation, view counts and audit events. A PNG fallback is rendered when the caller may start render runs, and copied write-once into the bundles bucket on first use.
    • The public GET /v1/embeds/{token}: no credential is read (cookies and Authorization are dropped), CORS for the plot-sandbox origin only, rate limits per link and per address, every dataset inlined from the verified bundle without decoding it.
    • Migration 0009_plots_embeds: saved_plots and plot_embeds with forced row-level security; the gateway role may read only the embed lookup columns.
    • Every new operation documents its RFC 7807 problems in the OpenAPI document.
    • runner: render runs draw PNG, SVG and PDF with vl-convert (pinned in the new mapi-plots[render] extra) with network access off, refuse anything that could fetch a resource, read plotdata.<n> inputs, apply width/height and cap images at 32 MiB. Plotly needs kaleido and a system Chrome (MODE_NOT_SUPPORTED otherwise; no browser is ever downloaded).
    • plot-sandbox: the embed page /embed/<token>. It fetches the embed view with no credentials under its own CSP (connect-src adds only the API's /v1/embeds/ path), validates and decodes it, honours the link's allowed origins and offers the PNG fallback. The mapi/web image serves it with the API origin filled in at start-up.
    • docs: the "Sharing plots" guide and the new settings in the configuration reference.
    • spec: the sign-up review queue (SignupReview, SignupReviewDecision, the SYBIL_FLAGS catalog), GET /v1/admin/signups, POST /v1/admin/signups/{signup_id}/review and POST /v1/admin/tenants/{tenant_id}/deletion/retry; the auth.signup_flagged, auth.signup_review and tenant.deletion_retry audit actions; the deletion record and platform logs in RETAINED_RECORDS.
    • server: the trust lifecycle (migration 0010_trust_lifecycle).
    • Self-service sign-up (POST /auth/signup, POST /auth/verify-email): single-use e-mail tokens stored as HMACs (24 h), the same answer for new and known addresses, a mailer protocol (SMTP with required TLS, a file outbox read at GET /dev/outbox in the dev profile, console), the disposable-domain blocklist plus configured domains and files, per-address, per-domain and platform-wide sign-up limits, and Sybil heuristics (same address, browser cookie, e-mail, domain burst) that flag sign-ups for the operators' review queue. Verification creates a public tenant, its default project and the admin grant.
    • Identity verification (GET /v1/tenants/{id}/verification, operators' PUT /v1/admin/tenants/{id}/verification, an IdentityVerifier provider protocol with a fake) and cut line A at run admission: uploaded code needs a trusted tier or identity verification (IDENTITY_VERIFICATION_REQUIRED); public tenants run built-ins and declarative specs only.
    • Tenant deletion: a confirmed request suspends the tenant and cancels its runs; after the grace period the orchestrator makes it deleting (tokens revoked, sessions ended, revoker hooks) and a procrastinate job purges the queue, every tenant table, every t/{tenant}/ object prefix (resuming after retention locks), then notifies and writes the tenant.purged tombstone; progress per store; automatic and operator retries.
    • GDPR export: a zip of every tenant record (credentials redacted), dataset objects and bundle manifests, with a short-lived signed link.
    • infra: a Cloud Armor policy on every load-balancer backend (OWASP CRS sqli, xss, lfi, rce and scanner rules in preview-then-enforce, per-IP rate bans on sign-up, /auth/*, embeds and endpoint scoring, Adaptive Protection), and an explicit retention for the control project's _Default log bucket (tenant deletion does not purge logs).
    • docs: Sign-up and abuse controls, Deleting and exporting data, and a Cloud Armor section in Security hardening.
    • integration: the M3 parts work together.
    • Tenant deletion revokes the tenant's embed links and disables its webhooks when it starts, purges every M3 table (endpoints and their history, webhooks, events and deliveries, saved plots, embeds, column profiles) and then delivers a signed tenant.deletion.completed to the webhooks that subscribed to it, through the same SSRF-guarded sender as every delivery (mapi_server.services.tenant_hooks).
    • Webhook events come from the finalizer's terminal transitions (run.*, model.version.ready with the runner's scorecard), promotions and rollbacks (endpoint.promoted), score runs (score.completed) and deletions.
    • Endpoint promotion gates on the scorecard the runner measured at fit (services.scorecards.promotion_decision, the single gate derivation).
    • Sign-up workspaces are public tier: built-ins and declarative specs only, on executors with enforced egress and DNS (cut line A).
    • server: POST /v1/guided/requests:compile turns a what-if scenario, a forecast or an intervention preset into its ScoreRequest, checked against the model version's score metadata ("Run exact").
    • runner: score runs read an endpoint call's inline XrJSON payloads (inline.data, inline.scenario) with the wire-format caps and the model's dim types.
    • mmm: mmm.bayesinsight, a BayesInsight model_def.json as a built-in model (Q8): Normal, log-normal, Poisson, negative binomial and zero-inflated likelihoods; coefficient and intercept priors in the KPI's own units; Hill, linear and S-shaped curves before delayed, geometric, Weibull or no carry-over; enforced sign constraints; fixed and partially pooled effects per row id (new levels pooled); Fourier seasons and local spline trends. Contributions sum to the expected KPI (a log-mean Divisia split for log links); lift tests observe the incremental KPI under the model's own likelihood. It passes the contract kit; mapi_plugin_mmm.bayesinsight_examples simulates a project with known parameters.
    • spec: mapi_spec.bayesinsight_model types model_def.json as the plugin runs it (the mmm.bayesinsight settings); import_bayesinsight(target="mmm.bayesinsight") now drafts a runnable spec - every row id a panel dim, the KPI bound to y, lagged media - falling back to BayesInsight's defaults with IMPORT_UNSUPPORTED warnings (and info issues for faithful but surprising behaviour).
    • mmm: business-prior translation for mmm.pymc_marketing (1.1.0): ROI and share ranges become per-channel log-normal saturation_beta priors and a baseline share an intercept prior (narrowing the control and seasonality priors when needed), solved on prior draws of pymc-marketing's own model; settings.priors hands them to pymc-marketing's model_config; a translate_priors hook previews them and a fit without a translation run translates them itself.
    • sdk: categorical holdout metrics - accuracy, accuracy_naive, accuracy_lift, log_score and brier - for a text target scored as one probability per category.
    • spec/runner: the holdout.hit_rate scorecard check (the holdout hit rate against always guessing the most popular product, in plain words) for the customer_choice template.
    • conformance: the guided_mmm fixture (the geo_mmm Guided draft with business priors and a lift test, true to its simulation); e84_lite evaluates the categorical metrics; the dedicated BayesInsight import ingests, validates and fits end to end.
    • docs: the built-in models reference covers mmm.bayesinsight and every plugin's calibration; Guided modelling covers business priors for the pymc-marketing adapter and the BayesInsight lift likelihood.
    • docs: the v0.4 site. A new landing page (both personas, how it works, the Guided quick path, the v0.4 feature grid and the numbers measured in the M3 verification), "Why modeling-api?" (compared with notebooks and ad-hoc apps, MMM vendors and libraries, and generic model serving, with when to use something else) and "Use cases"; a Tutorials section with new tutorials "Connect Google Sheets" (an Apps Script that writes an endpoint's forecast into a sheet, run in the tests against stand-ins for Apps Script), "Embed a chart in Notion, Slack or BI" and "Import a BayesInsight model" (import, check and a local fit that recovers the simulated parameters), and "Receive webhooks" as a tutorial with a tested Flask receiver; the roadmap with v0.4 released and v0.5 (expert plugins, MCP, optimise jobs) next; the security model and architecture pages for v0.4; make docs-screenshots-tutorials.
    • cli: mapi tokens create --scope lists the endpoint, endpoints:promote and webhooks:manage scopes.
    • dev: make outbox (dev.py outbox) prints the dev mailer's newest e-mails and verification links; make dev sets MAPI_OUTBOX_DIR and the plot sandbox's VITE_API_URL; compose keeps the outbox on a volume. make api-types and make snapshots regenerate the web API types and the snapshots.
    • web: Guided mode, the task flow for non-technical analysts (plan §11 Guided 1-7), replacing the placeholder page.

    Fixed (M2 review: spec, server and auth)¶

    • server: an API token can no longer administer its tenant. Tokens are bound to one project, so tenant members, project create and delete, the tenant audit log and tenant usage now need a signed-in session (403 for any token). A token may still read its own tenant and list its own project (mapi_spec.api.TOKEN_TENANT_ROUTES).
    • server: signing in again no longer re-activates a disabled account. /auth/callback refuses it with the generic 401 and audits auth.login_failed; only an invitation becomes active at its first sign-in.
    • server: operator status is decided on every request from MAPI_OPERATOR_EMAILS (and the dev profile's first account). Before, a demoted operator kept operator powers through mapi login ID tokens indefinitely and through browser sessions until they expired.
    • spec/server: an API token can no longer mint tokens, whatever its scopes (mapi_spec.tokens.TOKEN_NEVER). A child token dropped its parent's expiry, vCPU budget and rate limit, and outlived its revocation. POST /v1/tokens needs a signed-in session.
    • spec/server: score:<target> tokens can score. They authorized nothing, because :score checks run on the model and the scope covered only endpoints, so integrations fell back to broader runs:create tokens. score:<model id> now covers :score on that model and score:* on every model of the project (RouteAccess.name_param). The web tokens page, the CLI help and the docs say so.
    • server: concurrent uploads can no longer overrun the storage quota. Storage admission now locks the tenant row like run admission does, so six concurrent 800-byte intents against a 1000-byte quota admit exactly one.
    • server: abandoned upload intents no longer hold storage quota forever. Usage counts a pending intent only while its signed PUT is valid, and a new housekeeper loop in the worker (MAPI_HOUSEKEEPING_INTERVAL_S, default 300 s) marks expired intents expired and deletes whatever reached quarantine.
    • server: expired browser sessions are deleted. The delete in load_session was rolled back with the request's 401, and nothing else removed web_sessions rows. The row is now deleted in its own transaction after the 401, and the housekeeper sweeps expired sessions and abandoned sign-ins.
    • server: a FINALIZING run no longer counts its vCPU estimate on top of its metered attempt. Quota usage counts an active run's estimate only while its current attempt has no actual ledger entry, so runs near a daily or monthly limit are not refused by mistake.
    • server: concurrent submissions from different tenants can no longer exceed a global concurrent_runs or vCPU limit. Run admission takes a transaction-scoped advisory lock after the tenant row when the global policy sets such a limit.
    • server: the global spend cap counts work in flight. The ledger only grows when runs finish, so every queued run used to be admitted and dispatched against the same figure. Admission now adds the estimates of admitted, unmetered runs, and the dispatcher adds the estimates of started runs and of each run it leases in the same pass.
    • server: held runs can no longer fill the dispatcher's window of queued runs and stall fair share for every tenant. Runs of suspended tenants, uploaded code paused by the kill switch and non-internal work past the spend cap are left out in SQL, and each tenant takes at most MAPI_LEASE_CANDIDATES_PER_TENANT (50) of the window.
    • server: a retry resumes from the newest checkpoints of any earlier attempt. Before, it only looked at the attempt just before it, so an attempt that died before its first segment threw away all earlier progress. Automatic infra retries are also capped by cost (MAPI_AUTO_RETRY_COST_FACTOR, default 2× the estimate), as plan §8.3 asks, and no longer by count alone.
    • server: an unknown token prefix and a wrong secret for a known prefix get the same answer (the API token is invalid), so the API no longer tells which prefixes exist. Unauthenticated failures that anyone can cause (token.auth_failed, auth.login_failed) are audited at most five times per token prefix or client and minute, so they can no longer flood a tenant's audit log. The housekeeper sweeps old rate counters.
    • server/web: run event streams re-check the caller's credential every MAPI_SSE_REAUTH_S (60 s). A revoked token, an ended session or a lost membership no longer keeps receiving a 24-hour run's progress and logs: the stream closes and the reconnect is refused. The web client stops on 401 (and raises the session-expired prompt) or 403, where it used to retry forever.
    • server: the audit log and the cost ledger are append-only (migration 0004_append_only_records). Both runtime roles lose UPDATE and DELETE on them, and a trigger refuses any change to an existing row, so a request-path bug or injection can no longer rewrite a tenant's audit trail or billing history.
    • server/infra: the default data residency follows the deployment. It used to be us everywhere, so on the documented EU deployment every run of the platform tenant and of tenants created with defaults failed as INFRA_ERROR. MAPI_DEFAULT_RESIDENCY defaults to the multi-region of the Cloud Run region, and Terraform sets it from the dispatch pool's region (default_residency overrides it). It applies to the platform tenant, to rows the tenancy migration adopts and to POST /v1/admin/tenants without data_residency. Submissions that no reporting executor can place are refused at admission with a clear 403 instead of being queued, and the worker warns at start-up about such tenants.
    • server/infra: the API and events services no longer hold the RLS-bypassing database role, which plan §9 reserves for the dispatcher, reconciler and finalizer. Their platform lookups (sign-in, memberships, operator metadata, routing pushed events) now run as a new mapi_gateway role (migration 0005_gateway_role, MAPI_DATABASE_GATEWAY_URL, MAPI_DB_GATEWAY_ROLE).     • Contract kit, check_model: new horizon_exceeds_fit, missing_future_covariate, recursive_unsupported, fast_score_matches_exact (plugin check_fast_score hook, provided by PyMCModel), plots_sanitize and outputs_match_manifest checks; extend_typed_errors covers integer extend dims; output_space_and_units covers outputs that inherit the target implicitly.
    • OutputDecl.dims_of (additive) lets a manifest declare settings-dependent data dims; the sklearn models (and so tabular.regressor) and mmm.pymc_marketing use it, so their static output dims match what score returns.
