    HTTP API (v1) v0.2¶

    The platform API that ships with v0.2 (milestone M1, the local vertical slice). Every request and response body is a Pydantic model in mapi_spec.api. The server serves an OpenAPI 3.1 document generated from those models, and each model carries examples. The endpoint table on this page matches mapi_spec.api.M1_ENDPOINTS, and a test fails if the two drift apart.

    See also
    OpenAPI explorer The OpenAPI 3.1 document, browsable, with every schema and example (full screen)
    HTTP API guide The main flow with curl and jq: upload, validate, fit, follow, score
    Python client The same flow with mapi_client

    M1 is single-tenant

    A local install has one tenant and one project, both called default. Every resource still carries tenant_id and project_id, and every storage key starts with t/{tenant}/, so multi-tenancy in v0.3 adds row-level security without changing the schema. There is no authentication in M1. The API listens on 127.0.0.1 only. The tenants, sign-in, tokens and quotas that v0.3 adds are described in Multi-tenant API.

    Conventions¶

    Topic Rule
    Base URL http://127.0.0.1:8000 locally. Resource paths start with /v1.
    Bodies application/json (UTF-8). Spec text travels as a string field (yaml) inside JSON.
    Unknown fields Request bodies reject unknown fields (SCHEMA_INVALID). Clients ignore unknown response fields, so the server can add fields without a new version.
    Timestamps RFC 3339, timezone-aware, UTC (2026-10-15T09:30:00Z).
    Ids <prefix>_<26 lowercase Crockford base32>, ULID layout, sortable by creation time (run_01jaf3q2x8m9v7k5h4g3f2e1d0). Prefixes: ds, upl, spc, run, mdl, mv. Projects and tenants use slugs (default).
    Durations "45m", "1h30m", "90s".
    Actions Non-CRUD actions use a colon suffix: POST /v1/runs/{run_id}:cancel.
    Untrusted text Log lines, tracebacks and plugin messages only ever appear in untrusted_text or LogLine.line. Render them as text, never as HTML or markdown.

    Errors¶

    Every error is an RFC 7807 problem document (application/problem+json, model mapi_spec.Problem) with a stable code:

    {
  "type": "urn:mapi:error:LEAKAGE_RISK",
  "title": "A stateful step runs before the split",
  "status": 422,
  "code": "LEAKAGE_RISK",
  "detail": "validation failed with 1 error; first at /pipeline/2: …",
  "errors": [
    {"code": "LEAKAGE_RISK", "severity": "error", "pointer": "/pipeline/2",
     "message": "stateful step 'scale_y' runs before the split"}
  ]
}
    • Malformed request bodies, path parameters and query parameters return 422 SCHEMA_INVALID. Each problem goes in errors[] with an RFC 6901 pointer into the request (/body/kind, /query/limit).
    • Every endpoint can also return RATE_LIMITED (429), INTERNAL_ERROR (500) and INFRA_ERROR (503). These are not repeated in the table.
    • The full list of codes and their HTTP statuses is in Error codes.

    Pagination¶

    List endpoints return Page[T]:

    {"items": [ … ], "next_cursor": "eyJpZCI6InJ1bl8wMWphZiJ9"}
    • Pass ?limit= (default 50, maximum 200) and ?cursor=<next_cursor> to fetch the next page. A null cursor means the current page is the last one.
    • Cursors are opaque and only valid for the same list and filters.
    • Items are ordered newest first by id.

    Idempotency¶

    POST /v1/runs, …:score, …:retry, …:dry-run and POST …/versions (ingest) accept an Idempotency-Key header (1–255 printable ASCII characters, scoped to the project and kept for 24 hours):

    Situation Response
    First request with the key The normal response, for example 201 Created with the Run
    Same key, same body (byte-equal after canonical JSON) 200 OK with the originally created resource. No second run is created.
    Same key, different body 409 IDEMPOTENCY_CONFLICT
    Same key while the first request is still in flight 409 CONFLICT. Retry later.

    Clients should generate one key per user intent, for example a UUIDv4 when the user clicks Fit, and reuse it on every network retry.

    Long-running work and Prefer: wait¶

    Runs are asynchronous. Creating one returns the Run at once in state created or queued. POST /v1/models/{model_id}/versions/{version}:score also honours RFC 7240 Prefer: wait=N, with N capped at 60 seconds:

    • If the score run reaches a terminal state within N seconds, the response is 200 with ScoreCallResult{done: true, run, outputs: [ArtifactLink…]}.
    • Otherwise the response is 202 with done: false and the run. Follow the run with GET /v1/runs/{run_id} or its event stream.
    • The Preference-Applied: wait=N response header echoes the wait the server actually used.

    Run events (server-sent events)¶

    GET /v1/runs/{run_id}/events has two representations:

    • Accept: text/event-stream: a live SSE stream.
    • Any other Accept: a JSON Page[RunEventView] of persisted events. Pass ?after=<id> to read events after a given id.

    The stream sends these frames, in this order:

    1. event: snapshot with the full Run JSON. It is the first frame on every connection and has no id:.
    2. A replay of the persisted events whose id is greater than the Last-Event-ID request header. Without the header the replay starts from the beginning. Every replayed frame carries id: <RunEventView.id>. The ids increase per run, so a reconnecting client resumes exactly where it stopped, including across the 60-minute request cut on Cloud Run.
    3. Live frames as events arrive: state, progress, log, diagnostic, warning, checkpoint, metric, complete and error. The data: of each frame is one line of compact JSON (RunEventView).
    4. event: end once the run is terminal (data: the final Run). The server then closes the stream. A client that sees end must not reconnect.

    The server also sends a fresh event: snapshot (no id:) whenever the run's state changes, so a client can re-render from the latest Run without reassembling it from events. progress and log frames are not persisted: they are sent live without an id: (data: {run_id, attempt, seq, ts, type, payload}) and are never replayed; Last-Event-ID only covers persisted events.

    Between events the server writes a heartbeat comment (: keepalive) every 15 seconds. The first frame also carries retry: 3000.

    An open stream checks its caller's credential again every minute (MAPI_SSE_REAUTH_S). Once the token is revoked or expired, the session has ended, or the caller has lost access to the project, the server closes the stream without end. The reconnect then answers 401 or 403, and clients should stop there rather than retry.

    Progress frames are coalesced to at most one every 2–5 seconds. Only state changes, warnings, diagnostics, checkpoints, metrics and terminal events are persisted and replayable. A reconnecting client gets the latest progress from the snapshot frame. Log lines are paged from GET /v1/runs/{run_id}/logs.

    retry: 3000
event: snapshot
data: {"id":"run_01jaf3q2x8m9v7k5h4g3f2e1d0","state":"running", …}

id: 17
event: state
data: {"id":17,"run_id":"run_01jaf3q2x8m9v7k5h4g3f2e1d0","attempt":1,"seq":3,"type":"state", …}

: keepalive

    Datasets¶

    Data reaches the platform in three steps:

    1. Create the dataset.
    2. PUT the file to the signed URL from an upload session. The URL points into the quarantine bucket and the API never sees the bytes.
    3. Create a version. A sandboxed ingest run parses the upload, validates it, and writes the content-addressed data.zarr.zip with its schema, profile and preview.

    POST /v1/datasets Create a dataset DatasetCreate Dataset 201 CONFLICT (name taken)

    POST /v1/datasets/{dataset_id}/uploads Signed PUT URL into quarantine UploadCreate UploadSession 201 NOT_FOUND, PAYLOAD_TOO_LARGE, QUOTA_EXCEEDED
    POST /v1/datasets/{dataset_id}/versions Ingest an upload as a new version; starts an ingest run. Accepts Idempotency-Key. DatasetVersionCreate DatasetVersion (status ingesting) 202 NOT_FOUND, CONFLICT (upload not finished or already consumed)

    GET /v1/datasets/{dataset_id}/versions/{version} Schema, summary, profile and preview refs — DatasetVersion 200 NOT_FOUND

    How validation reports results:

    • POST /v1/specs:validate returns 200 even when the document is invalid. The verdict is in ValidateResponse.valid and issues.
    • The non-2xx statuses are kept for requests that cannot be validated at all: unparseable YAML, an oversized document, or a malformed request body.
    • Creating a spec or a revision stores invalid revisions too, with valid: false and their issues, so the editor can save work in progress.
    • POST /v1/runs refuses invalid revisions with the first error's code. Examples: LEAKAGE_RISK, UNSEEN_LEVELS.

    Multi-tenant API v0.3¶

    v0.3 (milestone M2) adds tenants, projects, members, API tokens, quotas, cost and an operator console. The models are in mapi_spec.api, mapi_spec.tenancy, mapi_spec.tokens, mapi_spec.quotas, mapi_spec.cost, mapi_spec.audit, mapi_spec.admin and mapi_spec.auth. The endpoint table below matches mapi_spec.api.M2_ENDPOINTS, and mapi_spec.api.ROUTE_ACCESS gives every operation (v0.2 ones included) its scope and the permission it checks. Tests fail if the code, this page and the server drift apart. Roles, tokens and scopes are explained in Tenancy and authentication, limits and prices in Quotas and cost.

    Authentication¶

    Caller Credential Notes
    Browser (the web app) Session cookie __Host-mapi_session (HttpOnly; Secure; SameSite=Strict; Path=/), set by GET /auth/callback OpenID Connect Authorization Code flow with PKCE (S256) and a nonce, run by the API as a backend-for-frontend. The browser never holds an OAuth token.
    Programs, SDKs, CLI, Atlas Authorization: Bearer mapi_<prefix>_<secret><checksum> An API token. It acts as its owner, narrowed by its scopes, in the one project it is bound to.
    Google Pub/Sub A Google-signed OIDC ID token on POST /internal/events Audience, issuer and the push service account are checked. Nothing in the body authenticates.

    Responses for authentication and authorization:

    Situation Response
    No credential, or an expired session, on a non-public route 401 UNAUTHENTICATED
    A malformed token, or one whose checksum fails 401 UNAUTHENTICATED. The presented value is never echoed.
    A revoked or expired token 401 UNAUTHENTICATED
    A resource in a project or tenant the caller cannot see 404 NOT_FOUND, the same as a missing one, so ids cannot be probed
    A visible resource, but the role or the token's scopes do not allow the action 403 FORBIDDEN
    A token used outside the project it is bound to 403 FORBIDDEN
    The tenant is suspended Reads work. Everything else returns 403 FORBIDDEN.

    Selecting the project¶

    Every v0.2 resource (datasets, specs, runs, models, plots) belongs to a project. From v0.3 a request names its project in one of these ways, in this order of precedence:

    1. Path parameters, on routes under /v1/tenants/{tenant_id}/projects/{project_id}.
    2. The X-Mapi-Project header: X-Mapi-Project: <tenant_id>/<project_id>, for example X-Mapi-Project: acme/growth. A bare X-Mapi-Project: growth is accepted when the tenant is unambiguous: the caller belongs to one tenant, or uses a token.
    3. The token's binding. A token always acts in its own project, so token clients may omit the header. A header that names another project returns 403 FORBIDDEN.
    4. The deployment default, in the single-tenant local profile only (default/default, as in v0.2).

    If none applies, or path and header disagree, the request fails with 422 SCHEMA_INVALID. mapi_spec.tenancy.resolve_project_scope implements these rules.

    The scope of each v0.2 endpoint (by operation id) and the permission checked:

    Scope Operations Permission
    Public health, ready, get_schema None
    Authenticated list_projects, get_catalog, list_catalog_models, get_catalog_model, list_catalog_steps, list_catalog_plots Any signed-in caller. Lists are filtered to what the caller can see.
    Project get_project read project
    Project create_dataset / create_upload, create_dataset_version create / update dataset (editor)
    Project list_datasets, get_dataset, list_dataset_versions, get_dataset_version, get_dataset_artifact read dataset
    Project validate_spec, list_specs, get_spec, list_spec_revisions, get_spec_revision read spec
    Project create_spec / create_spec_revision create / update spec (editor)
    Project create_run, dry_run_spec, resume_run, retry_run create run (runner). Runs on a model version also need run model.
    Project cancel_run cancel run (runner)
    Project list_runs, get_run, run_events, run_logs, list_run_plots read run
    Project list_models, get_model, list_model_versions, get_model_version, get_model_artifact read model
    Project score_model run model (runner)
    Project list_plots, get_plot, validate_plot read plot

    Storage keys and rows were already tenant- and project-qualified in v0.2 (t/{tenant}/…), so the switch needs no data migration. Postgres enforces the boundary with row-level security on tenant_id in every table.

    Members¶

    A membership grants one role. A tenant-wide membership grants it on the tenant and on every project in it; a project membership grants it on that project only. The effective role in a project is the higher of the two. Add a member by principal_id, or by email to invite someone who has not signed in yet (the invitation is claimed at first sign-in with that verified e-mail). Removing or demoting the last admin returns 409 CONFLICT.

    Browser session (backend-for-frontend)¶

    These routes are not versioned and live at the root, next to the web app.

    Endpoint Purpose Request Response Success Errors
    GET /auth/login Start sign-in. Redirects to the identity provider with response_type=code, a PKCE code_challenge (S256), state and nonce. ?return_to= must be a same-origin path; anything else becomes /. — — 302 —
    GET /auth/callback Check state, exchange the code with the PKCE verifier, verify the ID token (issuer, audience, nonce, expiry), set the session cookie and redirect to return_to — — 302 UNAUTHENTICATED
    POST /auth/logout End the session and clear the cookies. Works without a valid session; with one it needs X-CSRF-Token. — — 204 —
    GET /auth/session Whether the browser is signed in, as whom and until when. authenticated: false is a 200, not a 401. — SessionInfo 200 —

    The login transaction (state, nonce, PKCE verifier) is held by the server for 10 minutes and referenced by a __Host-mapi_login cookie with SameSite=Lax, because the identity provider's redirect back is a cross-site navigation that would drop a Strict cookie. Sessions expire after 2 hours idle or 12 hours in total. Every state-changing API route takes JSON, which a cross-site form cannot send without a CORS preflight, and the session cookie is SameSite=Strict, so cross-site requests never carry it.

    On top of that, every cookie-authenticated POST, PUT, PATCH and DELETE (including POST /auth/logout when a session is live) must echo the session's CSRF token in an X-CSRF-Token header, and is refused (403 FORBIDDEN) when its Origin is neither the web app nor the API or it says Sec-Fetch-Site: cross-site. The web app reads the token from the __Host-mapi_csrf cookie (readable, SameSite=Strict) or from the X-CSRF-Token header of GET /auth/session. Requests with an API token need no CSRF token.

    Internal¶

    Endpoint Purpose Request Response Success Errors
    POST /internal/events Pub/Sub push of run events from the Cloud Logging sink PubSubPushEnvelope Ingest result 200 UNAUTHENTICATED, SCHEMA_INVALID

    The push envelope is {message: {data, attributes, messageId, publishTime}, subscription, deliveryAttempt}. message.data is a base64 Cloud Logging entry whose jsonPayload.mapi_event is one HMAC-signed run event (see Run protocol). The request must carry Authorization: Bearer <Google-signed ID token>; after verifying the signature, the server checks the claims with mapi_spec.auth.check_push_claims: issuer https://accounts.google.com, the configured audience, the push service account's verified e-mail, and expiry. Events that fail their HMAC are acknowledged with 200 (redelivery would not help) and audited as event.rejected.

    Quotas and rate limits on every endpoint¶

    Requests and submissions are checked against three levels of quota: token, tenant and global (see Quotas and cost).

    • A request over a requests-per-minute limit returns 429 RATE_LIMITED with a Retry-After header. Retry after that many seconds.
    • A submission that would exceed a compute, concurrency, fan-out, resource-class, storage or egress limit returns 429 QUOTA_EXCEEDED. Retry-After is set when the limit resets with a window (the UTC day or month). The problem's detail names the level and the limit.
    • The platform kill switches (uploaded code paused, global spend cap reached) also return QUOTA_EXCEEDED, at the global level.

    Guided mode and integrations v0.4¶

    v0.4 (milestone M3) adds the contracts for Guided mode and for connecting other applications: guided templates and drafts, business priors and lift tests, what-if scenarios, endpoints and aliases, code snippets, webhooks, saved and rendered plots with embed links, and the trust lifecycle (sign-up, verification, tenant deletion and export). The endpoint table matches mapi_spec.api.M3_ENDPOINTS; mapi_spec.api.ROUTE_ACCESS gives each operation its scope and permission, and mapi_spec.api.ENDPOINTS is the whole v0.4 surface (M1, M2 and M3; the server's route-table test checks that it serves every row). The ideas behind them are explained in Guided mode and Integrations.

    Project-scoped M3 routes take the project from X-Mapi-Project, like every v0.3 route.

    Guided mode¶

    GET /v1/guided/templates lists the built-in templates (GuidedTemplate): plain-language questions, the built-in plugin they target, a ModelSpec template with {{placeholder}} strings, default settings, the scorecard checks that apply and x-ui-level hints. Role detection (POST /v1/guided/detect-roles) ranks the columns of an upload for every question from ColumnProfiles computed in the browser (or from a stored dataset version: its ingest's columns.json, else its schema and summary) and returns RoleSuggestions, each candidate with a confidence and a reason_plain. A draft (POST /v1/guided/drafts) turns GuidedAnswers into an IngestMapping for the upload, a ModelSpec document and its YAML ("View as YAML") without storing anything, with the static validator's findings in issues; save it with POST /v1/specs. POST /v1/guided/import/bayesinsight does the same for a BayesInsight model_def.json and metadata.json (BayesInsightImport), for the built-in geo MMM unless target says mmm.bayesinsight (the dedicated BayesInsight model). Business priors become model-space priors in a sandboxed translate_priors run (PriorTranslationRequest → PriorTranslation, whose result is a PriorTranslationResult with a prior-predictive preview in business units). POST /v1/guided/requests:compile turns a what-if scenario, a forecast or an intervention preset (GuidedCompile) into the ScoreRequest it stands for, so "Run exact" submits a real score run. The persona lock is Project.guided_locked, changed with PATCH /v1/tenants/{tenant_id}/projects/{project_id} (ProjectUpdate.guided_locked); in a locked project, POST /v1/specs and POST /v1/specs/{spec_id}/revisions by members below admin answer 403 FORBIDDEN for anything but Guided specs that keep their template's advanced and hidden fields. Served in this release: the templates, role detection, drafts, the BayesInsight import and the lock (see From a spreadsheet to a Guided draft).

    Endpoints and aliases¶

    An endpoint is a stable alias (endpoint://<project>/<alias>) for one model version. PUT promotes a version: the promotion gate (PromotionGateDecision) allows a passing scorecard, asks for override: true with a reason from a signed-in project admin when it warns (409 OVERRIDE_REQUIRED; the override is audited as endpoint.promote_override), and blocks a failing one (409 PROMOTION_BLOCKED). The endpoint's EvaluationPolicy requires evaluate_then_refit fits by default and blocks input-schema changes that would break callers. POST …/score takes an EndpointScoreCall (a score request without model, whose data and scenario may be inline XrJSON datasets up to 5 MB) and answers like …:score on a model version: Prefer: wait=60 gives 200 with the result when it is done in time, otherwise 202 with the run. A score:<alias> token may read the endpoint, its schema, history and snippets, and score it; endpoints:promote tokens may promote and roll back but never override the gate.

    Sign-up, verification, deletion and export¶

    Self-service sign-up (SignupRequest → SignupAccepted) answers the same for new and known addresses. Verifying the e-mail (EmailVerify → VerificationResult) creates a public-tier tenant. VerificationStatus says whether the tenant may upload code: never for public tenants before cut line B, and only after identity verification (operators record it with VerificationUpdate). Deletion is scheduled with a grace period during which the tenant is suspended and can cancel (TenantDeletionRequest → TenantDeletion, with progress per store); a GDPR export (GdprExportRequest → GdprExport) packages everything the tenant stored.
