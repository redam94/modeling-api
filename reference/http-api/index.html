    HTTP API (v1) v0.2¶

    This page describes the platform API of v0.2 (milestone M1, the local vertical slice). Each request body and each response body is a Pydantic model in mapi_spec.api. The server serves an OpenAPI 3.1 document that it makes from those models. Each model has examples. The endpoint table on this page agrees with mapi_spec.api.M1_ENDPOINTS. If the two are different, a test fails.

    See also
    OpenAPI explorer The OpenAPI 3.1 document, which you can browse, with all schemas and examples (full screen)
    HTTP API guide The main flow with curl and jq: upload, validate, fit, follow, score
    Python client The same flow with mapi_client

    M1 is single-tenant

    A local installation has one tenant and one project. Their names are default. Each resource has a tenant_id and a project_id, and each storage key starts with t/{tenant}/. Thus, the multi-tenancy of v0.3 adds row-level security and does not change the schema. M1 has no authentication. The API listens only on 127.0.0.1. Multi-tenant API describes the tenants, sign-in, tokens and quotas that v0.3 adds.

    Conventions¶

    Topic Rule
    Base URL http://127.0.0.1:8000 locally. Resource paths start with /v1.
    Bodies application/json (UTF-8). The spec text is a string field (yaml) in the JSON.
    Unknown fields Request bodies reject unknown fields (SCHEMA_INVALID). Clients ignore unknown response fields. Thus, the server can add fields and not make a new version.
    Timestamps RFC 3339, with a timezone, in UTC (2026-10-15T09:30:00Z).
    Ids <prefix>_<26 lowercase Crockford base32>, with the ULID layout. You can sort them by the time of creation (run_01jaf3q2x8m9v7k5h4g3f2e1d0). The prefixes are ds, upl, spc, run, mdl and mv. Projects and tenants use slugs (default).
    Durations "45m", "1h30m", "90s".
    Actions Actions that are not CRUD use a colon suffix: POST /v1/runs/{run_id}:cancel.
    Untrusted text Log lines, tracebacks and plugin messages occur only in untrusted_text or LogLine.line. Render them as text. Do not render them as HTML or markdown.

    Errors¶

    Each error is an RFC 7807 problem document (application/problem+json, model mapi_spec.Problem). It has a stable code:

    {
  "type": "urn:mapi:error:LEAKAGE_RISK",
  "title": "A stateful step runs before the split",
  "status": 422,
  "code": "LEAKAGE_RISK",
  "detail": "validation failed with 1 error; first at /pipeline/2: …",
  "errors": [
    {"code": "LEAKAGE_RISK", "severity": "error", "pointer": "/pipeline/2",
     "message": "stateful step 'scale_y' runs before the split"}
  ]
}
    • Incorrect request bodies, path parameters and query parameters return 422 SCHEMA_INVALID. Each problem goes in errors[], with an RFC 6901 pointer into the request (/body/kind, /query/limit).
    • All endpoints can also return RATE_LIMITED (429), INTERNAL_ERROR (500) and INFRA_ERROR (503). The table does not show these codes again.
    • Error codes has the full list of codes and their HTTP statuses.

    Pagination¶

    List endpoints return Page[T]:

    {"items": [ … ], "next_cursor": "eyJpZCI6InJ1bl8wMWphZiJ9"}
    • To get the next page, send ?limit= (default 50, maximum 200) and ?cursor=<next_cursor>. A null cursor tells you that the current page is the last page.
    • Cursors are opaque. A cursor is valid only for the same list and the same filters.
    • The items are in order of id, with the newest item first.

    Idempotency¶

    POST /v1/runs, …:score, …:retry, …:dry-run and POST …/versions (ingest) accept an Idempotency-Key header. The key has 1–255 printable ASCII characters. Its scope is the project, and the server keeps it for 24 hours:

    Situation Response
    First request with the key The usual response, for example 201 Created with the Run
    Same key, same body (the bytes are equal after canonical JSON) 200 OK with the resource that the first request made. The server does not make a second run.
    Same key, different body 409 IDEMPOTENCY_CONFLICT
    Same key while the first request is in progress 409 CONFLICT. Try again later.

    Clients must make one key for each user intent, for example a UUIDv4 when the user clicks Fit. They must use that key again on each network retry.

    Long-running work and Prefer: wait¶

    Runs are asynchronous. When you make a run, the response gives the Run immediately, in the state created or queued. POST /v1/models/{model_id}/versions/{version}:score also obeys the RFC 7240 header Prefer: wait=N. The maximum value of N is 60 seconds:

    • If the score run gets to a terminal state in N seconds, the response is 200 with ScoreCallResult{done: true, run, outputs: [ArtifactLink…]}.
    • If not, the response is 202 with done: false and the run. Follow the run with GET /v1/runs/{run_id} or with its event stream.
    • The response header Preference-Applied: wait=N gives the wait time that the server used.

    Forecasts with actuals¶

    A forecast request (on a model version or on an endpoint) can send actuals. Actuals are target values for periods after the fit, or new values for the last periods of the fit. The request can also send the periods to forecast, with an empty target. The model uses its fitted parameters to update its state with the actuals. Then it forecasts from the last actual. The model does not estimate its parameters again. Forecasts with actuals gives the rules, the plugin hook and examples.

    • The model forecasts exactly the periods after the last actual that have an empty target. When the payload ends with an actual, the model adds horizon.periods periods after it.
    • ScoreCallResult.summary.conditioning (ForecastConditioning) tells what the model used to condition each forecast. It has fit_end, conditioned, n_actuals, actuals_through, revised, horizon_source (rows or horizon), details for each series and a plain message.
    • A model without capabilities.conditions_on_actuals refuses actuals with 422 ACTUALS_NOT_SUPPORTED. The suggested action is to fit again with the new data, or to keep the target empty.
    • Gaps that the model cannot filter, and actuals without their drivers, give 422 ACTUALS_INVALID.
    • EndpointSchema.actuals_example is a forecast call that you can use immediately. It has inline data for the periods after the fit, and all values are empty. Endpoints have this example only when their model conditions on actuals.

    Run events (server-sent events)¶

    GET /v1/runs/{run_id}/events has two representations:

    • Accept: text/event-stream: a live SSE stream.
    • All other Accept values: a JSON Page[RunEventView] of the persisted events. To read the events after a given id, send ?after=<id>.

    The stream sends these frames, in this order:

    1. event: snapshot with the full Run JSON. It is the first frame on each connection. It has no id:.
    2. A replay of the persisted events that have an id greater than the request header Last-Event-ID. If the request has no header, the replay starts from the start. Each replayed frame has id: <RunEventView.id>. The ids increase for each run. Thus, a client that connects again continues exactly where it stopped. This is also true after the 60-minute request limit on Cloud Run.
    3. Live frames when the events occur: state, progress, log, diagnostic, warning, checkpoint, metric, complete and error. The data: of each frame is one line of compact JSON (RunEventView). From v0.11, the stream also sends tracking frames (see Run tracking).
    4. event: end when the run is terminal (data: the final Run). Then the server closes the stream. A client that gets end must not connect again.

    When the state, the name or the note of the run changes, the server also sends a new event: snapshot (no id:). Thus, a client can show the latest Run again and does not have to assemble it from events. The server does not persist progress and log frames. It sends them live without an id: (data: {run_id, attempt, seq, ts, type, payload}) and does not replay them. Last-Event-ID applies only to persisted events. From v0.11, the payload of a log frame also has level and fields when the line has stream user.

    Between events, the server writes a heartbeat comment (: keepalive) each 15 seconds. The first frame also has retry: 3000.

    An open stream does a check of the credential of its caller again each minute (MAPI_SSE_REAUTH_S). The server closes the stream without end in these conditions:

    • The token is revoked or expired.
    • The session has ended.
    • The caller does not have access to the project now.

    Then the new connection gets 401 or 403. Clients must stop at that point and not try again.

    The server combines progress frames into a maximum of one frame each 2–5 seconds. The server persists only state changes, warnings, diagnostics, checkpoints, metrics and terminal events. Only these events can replay. A client that connects again gets the latest progress from the snapshot frame. To get the log lines in pages, use GET /v1/runs/{run_id}/logs.

    retry: 3000
event: snapshot
data: {"id":"run_01jaf3q2x8m9v7k5h4g3f2e1d0","state":"running", …}

id: 17
event: state
data: {"id":17,"run_id":"run_01jaf3q2x8m9v7k5h4g3f2e1d0","attempt":1,"seq":3,"type":"state", …}

: keepalive

    How validation gives its results:

    • POST /v1/specs:validate returns 200 also when the document is not valid. The result is in ValidateResponse.valid and issues.
    • The API uses the statuses that are not 2xx only for requests that it cannot validate. These are YAML that it cannot parse, a document that is too large, and a request body that is not correct.
    • When you create a spec or a revision, the API also stores revisions that are not valid. They have valid: false and their issues. Thus, the editor can save work that is not complete.
    • POST /v1/runs refuses revisions that are not valid. It uses the code of the first error. Examples: LEAKAGE_RISK, UNSEEN_LEVELS.

    Score summaries. When a score run succeeds, ScoreCallResult.summary (ScoreSummary) holds the requested summary as plain tables (the summary.json of the run). Each ScoreSummaryTable has the coordinate columns (one for each dim), then one column for each statistic. dims names the coordinate columns, and time_dim names the dim that is time when there is one. A server that predates these two fields leaves them out. The tables are in the order of their size. If the summary has more than 100 000 cells, truncated is true. Use the score.zarr.zip output for all the values. From v0.9, the table of a circular output (OutputDecl.circular, for example a direction) has the field period (one turn, in the units of the output). The statistics are then on the circle:

    • mean is the circular mean, and the intervals are centred on it.
    • The mean, the median, the quantiles and the interval bounds are in [0, period). An interval with lower more than upper crosses the seam (from 350 to 10 degrees).
    • sd is the circular standard deviation.

    Other tables do not have the field. Refer to Circular outputs.

    Selecting the project¶

    Each v0.2 resource (datasets, specs, runs, models, plots) is part of a project. From v0.3, a request identifies its project in one of these ways. The list order is the order of precedence:

    1. Path parameters, on routes under /v1/tenants/{tenant_id}/projects/{project_id}.
    2. The X-Mapi-Project header: X-Mapi-Project: <tenant_id>/<project_id>, for example X-Mapi-Project: acme/growth. The API also accepts only the project, for example X-Mapi-Project: growth, when the tenant is clear. This is when the caller is a member of one tenant, or uses a token.
    3. The token binding. A token always acts in its own project. Thus, token clients do not have to send the header. A header that identifies a different project returns 403 FORBIDDEN.
    4. The deployment default, only in the single-tenant local profile (default/default, as in v0.2).

    These routes have no version. They are at the root, next to the web app.

    The server keeps the login transaction (state, nonce, PKCE verifier) for 10 minutes. A __Host-mapi_login cookie with SameSite=Lax refers to it.     • Its Origin is not the web app or the API.
    • It has Sec-Fetch-Site: cross-site.

    Endpoint Purpose Request Response Success Errors

    The push envelope is {message: {data, attributes, messageId, publishTime}, subscription, deliveryAttempt}. message.data is a base64 Cloud Logging entry.     • The audience is the configured audience.

    Quotas and rate limits on every endpoint¶

    The platform does a check of requests and submissions against three levels of quota: token, tenant and global (see Quotas and cost).

    • If a request goes above a requests-per-minute limit, the API returns 429 RATE_LIMITED with a Retry-After header. Try again after that number of seconds.
    • If a submission goes above a compute, concurrency, fan-out, resource-class, storage or egress limit, the API returns 429 QUOTA_EXCEEDED. The API sets Retry-After when the limit resets with a window (the UTC day or month). The detail of the problem gives the level and the limit.
    • The platform kill switches (uploaded code paused, global spend cap reached) also return QUOTA_EXCEEDED, at the global level.

    Endpoints and aliases¶

    An endpoint is a stable alias (endpoint://<project>/<alias>) for one model version. PUT promotes a version. The promotion gate (PromotionGateDecision) does a check of the scorecard:

    • If the scorecard passes, the gate permits the promotion.
    • If the scorecard has a warning, the gate asks for override: true with a reason from a signed-in project admin (409 OVERRIDE_REQUIRED). The audit log records the override as endpoint.promote_override.

    Tree datasets and multi-file versions v0.8¶

    A dataset version can hold an xr.DataTree (layout tree) instead of one xr.Dataset (layout dataset, the default). DatasetVersion then has layout: "tree", the tree_schema (a TreeSchema: one DataSchema per node such as / or /instrument/psf) and the sources it was built from, and data_schema is the schema of the root node.

    • Several files in one version. DatasetVersionCreate takes either upload_id + mapping (one file, as before) or assembly (an IngestAssembly): each source names its upload, its own IngestMapping, the node it goes to and how it joins the other sources of that node: node (the only source), concat (along concat_dim, one concat_label per file) or merge (variables on shared coords, aligned per join).
    • Raw HDF5. Format hdf5 needs mapping.hdf5 (an Hdf5Mapping): which HDF5 dataset becomes which variable of which node, with its dims (Hdf5Var) and coords (Hdf5Coord). To see what is in a file first, inspect the upload (below). NetCDF and xarray-written HDF5 files keep format netcdf; their groups become nodes.
    • Inspection. An inspect run reads only the metadata of an upload (after the HDF5 safety checks) and lists its groups and arrays. It is idempotent per upload: while an inspection runs, or after it succeeded, the server returns that run. If the run failed or was cancelled, a new request starts a new run. The run has the resource class that an ingest of the upload would get (the smallest class that holds the upload, so S, M or L), interactive priority and the timeout MAPI_INSPECT_TIMEOUT_S (300 s).
    • Assemblies. The server checks every upload of an assembly before it uses any of them: each upload belongs to the dataset, is complete, is used one time and is not in another version. Otherwise it answers 409 CONFLICT with a pointer to the source (/body/assembly/sources/<i>/upload_id), and all the uploads stay available. The uploads of one version are a maximum of 5 GB together (413 PAYLOAD_TOO_LARGE). One ingest run reads them all.
    • Unsafe files. If the HDF5 guard refuses a file, the ingest or inspect run fails with INGEST_UNSAFE_FILE (422) in its problem, and the version becomes failed.

    Run tracking v0.11¶

    A run keeps a log of what happened in it. The log has these parts:

    • Metrics. A metric is a series of points. A series has a key (for example loss) and labels (for example {"chain": "0"}). A point has a value, a time and, if it is part of a curve, a step. A point without a step is a scalar. For a scalar, the newest value is kept.
    • Params. A param is a key and a value that does not change: the first value is kept. The runner logs the params of the spec (model, fit.*, settings.*) automatically.
    • Tags. A tag is a key and a text value that you can change at any time. Tag keys that start with mapi. are for the platform only.
    • The name and the note. A run can have a display name (a maximum of 200 characters) and a note (free text, a maximum of 20 000 characters).
    • Structured log lines. Model code can write log lines with a level (debug, info, warning or error) and fields. These lines have stream user in LogLine.

    Metric keys must match ^[a-z][a-z0-9_]{0,63}$. Do not write qualifiers such as train/loss in the key. Use labels: key loss with labels={"split": "train"}. Label keys match ^[a-z][a-z0-9_]{0,31}$, label values match ^[A-Za-z0-9_.\-]{1,63}$, and a series has a maximum of 8 labels. Param keys and tag keys can have ., - and /. The guide Track metrics, params and tags shows how to log from model code, workflow nodes and notebooks.

    Search runs¶

    GET /v1/runs has these query parameters for search (v0.11):

    Parameter Value
    parent_run_id Only the child runs of this run (for example, the node runs of a workflow run).
    experiment_id v0.14: only the runs of this experiment.
    name The runs whose name contains this text (case-insensitive).
    tag key (the run has the tag) or key:value (exact value). Repeatable: all must match.
    filter A comparison, for example metric.rmse < 0.5. Repeatable, a maximum of 8: all must match.
    order_by One ref. A - before the ref gives descending order. The default is -created_at.
    column A ref whose value the server adds to Run.columns. Repeatable, a maximum of 16.

    A ref has one of these forms:

    metric.KEY[{label=value,...}][.AGG]     AGG: last (default), min, max, count
param.KEY
tag.KEY
name
created_at                              (only in order_by and column)

    A filter is ref OP value. The operators are <, <=, >, >=, =, != and ~. ~ finds text that contains the value (case-insensitive).

    Ref Operators Value
    metric.… < <= > >= = != A number. The server compares it with the summary of that exact series. metric.loss is the series without labels. metric.loss{split=val} is the series with exactly that label.
    param.… = != ~ Text, compared with the text form of the param.
    param.… < <= > >= A number, compared with the numeric value of the param.
    tag.… = != ~ Text.
    name = ~ Text.

    A run that does not have the series, the param or the tag does not match the filter. This is also true for !=. Runs that do not have the value of order_by come last. Equal values sort by run id (descending). When order_by is a param, the server sorts by the numeric value of the param first, then by its text. Run.columns uses the canonical text of each ref as its key (labels in key order, .last left out), for example metric.loss{chain=0,split=val}. The server returns 422 SCHEMA_INVALID for a value that does not have this grammar. mapi_spec.tracking.parse_run_filter, parse_run_order and parse_run_ref implement the grammar. The Python client and the CLI use them to do a check of the values before they send the request.

    curl -G "$MAPI/v1/runs" -H "Authorization: Bearer $MAPI_TOKEN" \
  --data-urlencode 'filter=metric.rmse < 12' \
  --data-urlencode 'filter=param.fit.engine = nutpie' \
  --data-urlencode 'order_by=metric.rmse' \
  --data-urlencode 'column=metric.rmse' --data-urlencode 'column=param.settings.adstock.l_max'

    Log levels¶

    GET /v1/runs/{run_id}/logs?level=warning returns the lines with the level warning or error. The order of the levels is debug, info, warning, error. A line without a level (stdout, stderr and system lines) counts as info. LogLine has level and fields only for stream user.

    The server sends the lines of stream user only when the request has stream=user or include_user=true. A client before v0.11 knows only the streams stdout, stderr and system, thus it continues to read the logs of all runs. The v0.11 Python client, the CLI and the web app send include_user=true.

    The tracking frame¶

    The event stream (GET /v1/runs/{run_id}/events, SSE) sends event: tracking when the metrics, the params or the tags of the run change. The data: is a TrackingFrame:

    • series: the MetricSeries summaries that changed after the last frame (a maximum of 200).
    • params and tags: true if the params or the tags changed. Get them again.
    • media (v0.14): true if the run logged images or tables. Get them again from GET /v1/runs/{run_id}/media-keys.

    A tracking frame has no id:, and the server does not replay it. A client that connects again gets the current values from the endpoints above. The run events metrics, params and tags (see Run protocol) are not persisted as events. Thus, they are not in Page[RunEventView] and have no frame name of their own.

    event: tracking
data: {"run_id":"run_01jaf3q2x8m9v7k5h4g3f2e1d0","series":[{"key":"step_size","labels":{"chain":"0"},"attempt":1,"count":1400,"last":0.31,"last_step":1400, …}],"params":false,"tags":false}

    Retention¶

    The setting MAPI_TRACKING_RETENTION_DAYS (no default: keep all) deletes the metric points and the user log lines of runs that finished more days ago than the setting. The server keeps the summaries, the params, the tags, the name and the note. Thus, search and comparison of old runs continue to work. See Configuration. The setting does not delete media (v0.14).

    Media, comparison, experiments and saved views v0.14¶

    v0.14 adds these parts to run tracking:

    • Media. A run can log images (PNG or JPEG) and small tables (JSON). The runner uploads them during the run (see Run protocol: Media). You can also log them through the API, also after the run finished.
    • Comparison. One request gets the summaries, the metric histories, the params and the media of 2 to 10 runs.
    • Experiments. An experiment is a named group of runs. A run is in a maximum of one experiment.
    • Saved views. A saved view is a list_runs query with a name, shared in the project.

    Resumable uploads and image collections v0.15¶

    v0.15 adds these parts to the dataset API:

    • Resumable uploads. get_upload tells you if the file of an upload arrived. renew_upload signs a fresh PUT URL for an upload whose URL expired. An upload whose file arrived has the status uploaded. You can use it in a version also after its PUT URL expired. If no version uses it, the server deletes it 7 days after its PUT URL expired. When you renew an expired upload, the server does a check of the storage quota again.
    • Image collections. A collection version is made from a manifest upload and image part uploads (DatasetVersionCreate.collection). find_missing_images tells you which images a base version does not have, so you upload only these images.

    The guide Image data: collections shows the CLI, the client and the web app.

    Endpoints¶

    Endpoint Purpose Request Response Success Errors
    GET /v1/datasets/{dataset_id}/uploads/{upload_id} An upload and whether its file arrived (received). upload is the current signed PUT. — UploadSession 200 NOT_FOUND
    POST /v1/datasets/{dataset_id}/uploads/{upload_id}/renew Sign a fresh PUT URL (TTL 1 h) for an upload whose file did not arrive. received is false. — UploadSession 200 NOT_FOUND, CONFLICT (a version used the upload, or the file arrived)
    POST /v1/datasets/{dataset_id}/blobs/missing Which images (by SHA-256) the base version does not have BlobQuery BlobMissing 200 NOT_FOUND (the base version), SCHEMA_INVALID, CONFLICT (the base version is not a ready collection)

    All three need the X-Mapi-Project header (or a project in the token). find_missing_images needs read on dataset, as get_dataset. get_upload and renew_upload need update on dataset, as create_upload, because their answer holds a signed PUT URL. A user who can only read the dataset cannot write its uploads.

    POST /v1/datasets/{dataset_id}/versions takes collection (a CollectionSource) in place of upload_id + mapping or assembly. The server:

    • makes sure that the manifest upload has a maximum of 256 MB and each part a maximum of 2 GB − 64 MB, and that each part has an MD5 (else 409, pointer /body/collection/part_upload_ids/<i>);
    • finds the base version: with base_version set, the version must exist, be ready and have the layout collection (else 409); with null, the latest ready collection version (or none); with 0, no base;
    • starts a collection ingest run of class M. The run reads the parts in ranges, so the class does not depend on the size of the upload.

    get_dataset_artifact also gives manifest.parquet and collection.json of a collection version.

    The DTOs¶

    • UploadSession gains received (only in the answers of get_upload and renew_upload).
    • DatasetVersionCreate gains collection (a CollectionSource). Give exactly one of upload_id + mapping, assembly or collection. upload_ids is the manifest, then the parts.
    • CollectionSource (mapi_spec.collection): manifest_upload_id, part_upload_ids (a maximum of 64, unique, not the manifest), base_version (null: the latest ready collection version; 0: none) and options (a CollectionOptions).
    • CollectionOptions (mapi_spec.collection): sha256_column (default sha256), id_column, path_column (default path), label_column, split_column, columns (a maximum of 64; not the reserved names of manifest.parquet), var (pixels), dim (image), mode (auto, gray or rgb), size (height, width), resize (stretch, crop or pad) and max_images (default 100 000, a maximum of 1 000 000).
    • DatasetVersion.layout can be collection. DatasetVersion.collection is then a CollectionInfo (mapi_spec.collection): n_images, dim, var, label, split, classes (a maximum of 1000 ClassCount, by count), other_classes, splits, mode, size, min_size, max_size, formats, total_bytes, packs (PackInfo: digest, size, crc32c, md5, entries, images, source (upload or base) and input), new_images, reused_images, base_version, columns and manifest_sha256.
    • BlobQuery: sha256 (1 to 5000 unique lowercase hex digests) and base_version (null: the latest ready collection version; 0: none, so all images are missing).
    • BlobMissing: base_version (the version compared with, or null), missing (in the order of the query) and present (the number of the other digests).

  -H "X-Mapi-Project: growth" -H "Content-Type: application/json" \
  -d '{"sha256": ["'"$(sha256sum photo.jpg | cut -c1-64)"'"]}'
