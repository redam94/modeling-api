    Roles¶

    Roles are ordered viewer < editor < runner < admin; each includes the one before it. tenant-wide means only a tenant-wide membership grants it; otherwise the effective role in the project counts (the higher of the tenant-wide and the project grant).     Operators¶

    Platform operators (verified e-mails in MAPI_OPERATOR_EMAILS, signed in; never through an API token) hold exactly these permissions, on every tenant: audit read, billing read, catalog read, catalog update, executor read, executor update, kill_switch read, kill_switch update, member read, project read, quota delete, quota read, quota update, run read, tenant_deletion manage, tenant_deletion read, tenant_member read, tenant create, tenant delete, tenant manage, tenant read, token read, usage read. None of them reads tenant content: datasets, specs, models or plots.

    Capabilities¶

    A capability is granted on top of a role, per project membership; project admins hold every capability implicitly. A rule that needs one says so in the roles table ("✓ with reviewer").

    Capability Needed for What it allows
    reviewer model approve Approve or reject model validations that wait for a second person (POST /v1/validations/{id}/approvals), never the member's own submissions (SELF_APPROVAL_FORBIDDEN) and never through an API token. Granted per project membership (capabilities on the membership, or the Reviewer column of Members); viewers cannot hold it.

    Token scopes¶

    A token acts as its owner, narrowed by its scopes: both the owner's role and a scope must allow an action. admin covers everything the owner's role allows; score:<alias> covers one endpoint (score:* every endpoint of the project). dashboard:<id> is the scope of a dashboard read token: it reads that one dashboard through MCP and nothing else.

    self-hosted-trusted isolation ≥ process — — — — — — — —
