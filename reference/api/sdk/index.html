    mapi_sdk¶

    The xarray runtime. Runs in notebooks and runner images, never in the control plane.

    Fit and score¶

    The fit/score harness: the platform side of every run (plan §4.2).

    :func:fit_spec implements fit.mode:

    • bind the data, validate it, fit the stateless prefix on all data up to the split stage;
    • split; fit the remaining step states and the model on train (the evaluation fit);
    • evaluate the holdout through the score path (context from train) - never a separate code path - and compute the spec's metrics;
    • evaluate_then_refit: refit states and model on train ∪ holdout so the context tails and terminal state come from the full data; the production bundle links the evaluation bundle and its metrics. train_only keeps the train fit as the result.
    • derived quantities the spec requests (outputs.derived) whose manifest declaration says cache: fit are computed on the production fit by the plugin's derive hook, over the first outputs.ui_draws draws of the thinning index, with ScoreContext.to_original mapping them to the output space.

    :func:score_bundle implements scoring: CoordPlan checks, binding, interventions, entry at inputs_stage, context replay, canonical coords, model.score, context removal, selection, inverse transforms to the output space, aggregation, summaries, thinned draws and reverse binding. It returns an xr.DataTree.

    score_bundle ¶

    score_bundle(
    bundle: Bundle,
    request: ScoreRequest | str,
    data: Dataset | None = None,
    *,
    scenario: Dataset | None = None,
    side_tables: Mapping[str, Dataset] | None = None,
    registry: Registry | None = None,
    max_draws: int | None = None,
    return_full: bool = False,
    metrics: Sequence[str] | None = None,
    metric_mask: DataArray | None = None,
    hooks: FitHooks | None = None,
    observed: Dataset | None = None,
    history: Dataset | None = None,
) -> DataTree

    Score a fitted bundle; returns a DataTree.

    data is the request's data payload and scenario its scenario payload. Outside counterfactuals a scenario simply is the payload. A counterfactual scores the scenario (or the data, when no scenario is given) with the interventions applied against the baseline data; a scenario without baseline data is rejected.

    Groups: summary (stats along a stat dim), draws (when requested; joint, from the bundle thinning index), predictions (full representation, when return_full), and for counterfactuals baseline/... and delta/.... Root attrs carry the representation, output kind, units/output space, retransformation labels, non-error issues and - in evaluate mode - the metrics. observed (evaluation of cell-level splits) gives the observed targets for metrics when data has them masked. history (M3) is the fitted dataset (dataset names): forecasts whose future_covariates policy is carry_last or seasonal_naive extend the covariates the payload lacks from it (:mod:mapi_sdk.future).

    Steps¶

    The preprocessing step contract: Step, StepState and StepContext.

    A step is a class with static metadata (id, version, kind, a Pydantic Settings model, an optional State model) and four methods::

    fit(ds, settings, ctx) -> State           # learn on train data only
transform(ds, settings, state, ctx) -> ds # never learns; must tolerate an absent target
inverse(ds, settings, state, ctx) -> ds   # invertible VALUE steps only

    Rules the contract kit (:mod:mapi_sdk.testing) enforces:

    • transform(train, fit(train)) equals the fit-time output exactly, and transform is deterministic and does not mutate its input;
    • reductions name the dims they reduce over; the state stays labelled by the rest;
    • group-local operations take along/within and declare a :class:ContextNeed;
    • unseen levels go through :meth:StepContext.align_state;
    • the static :class:~mapi_spec.effects.SchemaEffect (effect_template) matches the real output schema.

    The static metadata is exported as a :class:~mapi_spec.catalog.StepCatalogEntry, so the control plane validates specs without importing step code.

    Models¶

    The model plugin contract (plan §5).

    A plugin turns a model-stage xr.Dataset into a :class:FitOutput and, later, scores a canonicalised dataset into an xr.DataTree whose predictions group holds the declared outputs in the plugin's :class:~mapi_spec.capabilities.Representation::

    draws      (chain, draw, *dims)
quantiles  (quantile, *dims)       quantile coords in (0, 1)
interval   (bound, *dims)          bound coords include "lower", "upper" (+ "point")
point      (*dims)
moments    (moment, *dims)         moment coords ["mean", "sd"]

    The platform owns everything around that: binding, CoordPlan, context, canonical coords, inverse transforms, reverse binding and summaries. :class:CustomModel is the base class for hand-written plugins; mapi_pymc.PyMCModel and mapi_sklearn.SklearnModel build on the same protocol.

    PREDICTIONS ¶

    PREDICTIONS = 'predictions'

    Name of the DataTree group a plugin's score must fill.

    CustomModel ¶

    Base class for hand-written plugins: declare metadata, implement fit/score.

    Optional hooks: :meth:diagnostics, :meth:postprocess, :meth:derive, :meth:objective, :meth:recommend, :meth:translate_priors, :meth:optimize. Set pad_extend = False if the model does not index time positionally (scoring then skips padding extend dims to the fit range).

    FitContext ¶

    FitContext(
    seed: int = 0,
    schema: DataSchema | None = None,
    policies: Mapping[str, DimPolicy] = dict(),
    coords: Mapping[str, ndarray] = dict(),
    workdir: Path | None = None,
    log: Callable[[str], None] | None = None,
    on_progress: ProgressFn | None = None,
    cancel: CancelToken | None = None,
    checkpoint_sink: Any | None = None,
    stage_schema: DataSchema | None = None,
    calibration: Calibration | None = None,
    to_original: Callable[[DataArray, str], DataArray]
    | None = None,
)

    Everything a plugin's fit may use besides data, settings and fit config.

    schema is the model's resolved input schema (its template); stage_schema is the schema of the pipeline stage the data comes from, with every variable and its role.

    checkpoint_sink is an engine-specific sink for segmented fits (for example mapi_pymc.CheckpointSink); the runner supplies one that writes to the run prefix. None disables checkpointing.

    calibration (M3) is the spec's calibration block - business priors and lift tests - for plugins whose capabilities declare them (Capabilities.calibration). to_original (M3) maps a model-stage array in the units of input variable src back to the output space with the fitted preprocessing state (as :attr:ScoreContext.to_original does for derived quantities), so a plugin can turn business-unit calibration data into model units. Both are None outside the harness.

    ScoreContext ¶

    ScoreContext(
    mode: ScoreMode = "predict",
    kind: Literal["expected", "predictive"] = "expected",
    seed: int = 0,
    schema: DataSchema | None = None,

    Everything a plugin's score may use besides the fitted model and data.

    The dataset handed to score is canonicalised: fixed and new-level dims are in fit order (padded to the full fit set), new levels are appended and flagged by the bool coordinate <dim>__is_new, and <dim>__requested marks real (non-padding) labels.

    Pipelines¶

    The pipeline engine: stages, fitting, score-time replay and the inverse chain (plan §4.2).

    A stage is the dataset after a named step (raw is the bound input before any step). :meth:Pipeline.fit fits and transforms a range of stages, recording each step's state and its per-group context tail at the step's input stage. :meth:Pipeline.transform replays stored states over a range of stages, prepending each step's context before it runs (:mod:mapi_sdk.context). :meth:Pipeline.inverse_outputs maps model outputs back through invertible VALUE steps up to the last RESHAPE step and labels the output space.

    inverse_outputs(
    ds: Dataset,

    Map output variables back to their output space.

    var_sources maps each output variable to the input variable whose transforms it inherits (y_hat -> y). Inversion stops at to_stage (default: the last RESHAPE stage) or at the first non-invertible step that touched the variable. Point outputs through a non-linear inverse are labelled median (plain inverse) or use Duan's smearing over stored model-space residuals; moments use the first-order delta method (g(mu), |g'(mu)| sd with a central difference).

    decompositions name additive decompositions (contributions(component, ...)). They are inverted component by component only through additive steps (Step.additive); through any other inverse (expm1, x * sd + mean) the components would no longer sum to the inverted prediction, so inversion stops right after that step and :attr:InverseResult.kept says why.

    Bundles¶

    Fitted-model bundles: one bundle.zarr.zip DataTree plus JSON sidecars (plan §8.6).

    Layout of bundle.zarr.zip::

    /                       attrs: format, bundle_id, role
/spec                   attrs: spec (canonical JSON), resolved (ResolvedSpec JSON)
/schema/raw             attrs: json (dataset-named raw DataSchema)
/schema/model           attrs: json (model input schema, effective policies)
/binding                attrs: json
/preprocess/<step_id>   attrs: state (JSON); children: arrays, context
/model                  attrs: manifest, settings, fit_config, learned (JSON)
/model/<group>          ArviZ-named groups (posterior, sample_stats, log_likelihood ...)
/terminal_state         plugin-owned state for sequential models
/native                 uint8 arrays of safe native artifacts (skops, xgb json, ...)
/derived/<name>         derived quantities cached at fit
/fit_coords/<stage>     coordinates of the fitted data at every stage
/side_tables/<name>     pinned side tables used at fit
/residuals              model-space residuals (point models, smearing)
/thin                   the bundle-wide draw thinning index

    Sidecars: manifest.json (content hashes of every file: size, CRC32C and MD5 in the GCS base64 form, SHA-256), diagnostics.json, plots.json and metrics.json. An evaluate_then_refit bundle keeps its train-only evaluation bundle under evaluation/. Pickle is never written and is rejected on read.

    Summaries¶

    Representation-aware summaries, aggregation and draw thinning (plan §5).

    Outputs come in one of five representations (see :mod:mapi_sdk.models). Which summaries and aggregations are valid depends on the representation; the rules live in :data:mapi_spec.capabilities.REPRESENTATION_RULES and are enforced here:

    • draws: every summary; any aggregation (applied per draw);
    • quantiles: median/quantiles/ETI (interpolated on the stored quantile grid, never extrapolated); no aggregation;
    • interval: the interval and its point; no aggregation;
    • point: mean/point; linear aggregation only, flagged;
    • moments: mean/sd and normal ETIs; no aggregation.

    Summaries are returned as one variable per output with a leading stat dim whose labels read like mean, hdi_90_lower, hdi_90_upper, q5 ... HDIs are computed in numpy (narrowest window over sorted draws).

    In-process executor¶

    In-process executor (isolation NONE) for notebooks, tests and mapi fit on own code.

    Implements the :class:mapi_spec.executor.Executor protocol: submit starts the run in a worker thread, status is the source of truth, cancel is cooperative (checked between pipeline phases) and event_source yields :class:~mapi_spec.executor.RunEvent objects. Payloads are JSON only; dataset references are resolved by a resolver.

    Supported run kinds: fit (payload spec, data, optional side_tables and raw_schema) and score/evaluate (payload request, bundle - a bundle directory or a key registered with :meth:InprocExecutor.put_bundle - and optional data/scenario/side_tables; otherwise the request's data/scenario refs are used). A counterfactual resolves data as the baseline and scenario as the scenario.

    Never use this executor for untrusted code: it runs plugins in the caller's process.

    Wire formats¶

    Wire formats: XrJSON, single-object zarr v3 zips, DataTree zips, stacking and Arrow IPC.

    Encoding rules (plan §3.2), applied by every writer here:

    • any pandas.MultiIndex is reset before persisting (and recorded so readers restore it);
    • string coords and variables are zarr v3 vlen-utf8 (data type string);
    • datetimes are int64 nanoseconds with explicit units and calendar attrs;
    • only the zstd and blosc compressors are written or accepted;
    • :func:stack_rows drops empty rows and records a row mask so :func:unstack_rows restores them.

    Pickle (and joblib/cloudpickle) is never used for anything. Readers treat every payload as hostile: zip entries, zarr metadata, codecs, dtypes and sizes are checked before any array is decoded.

    Contract kit¶

    Contract-kit checks for step and model authors (plan §13).

    :func:check_step and :func:check_model run every contract check that is possible without a sandbox and return a :class:ContractReport (raising :class:ContractViolation by default when any check fails). Each check is independent: one failure never hides the others.

    M3.5: both also check the item's plain-language About card (about): an incomplete card always fails; a missing one fails with require_about=True (what the catalog requires) and is skipped otherwise. :func:check_about checks cards on their own.
