    mapi_spec¶

    Pure-Pydantic contracts. No numpy, xarray or pandas: the control plane depends on this package.

    Data schema¶

    Data contract primitives: dims, variables, ragged structure and dataset schemas.

    A :class:DataSchema describes an xr.Dataset without any arrays: its dims (each with a :class:DimPolicy saying what may happen to it at score time), its variables (with a :class:Role, dtype, units and missingness) and its ragged structure.

    A :class:DataSchemaTemplate is a static JSON function of enumerated settings: plugins export one per model so the control plane can compute the required input schema for given settings without running plugin code.

    Bases: StrEnum

    FIXED ¶

    FIXED = 'fixed'

    Score coords must be a subset of fit coords (channel, state, product).

    EXTEND ¶

    EXTEND = 'extend'

    New coords may be appended after the fit range, contiguously (time, obs).

    NEW_LEVELS ¶

    NEW_LEVELS = 'new_levels'

    Unseen levels are allowed through a declared strategy (market, county).

    Loading and hashing¶

    Strict YAML 1.2 / JSON loading, apiVersion upgrades, canonical JSON and spec hashing.

    The loader is safe for hostile input:

    • size ≤ 256 KB, nesting depth ≤ 32, ≤ 10 000 nodes (all configurable via :class:Limits);
    • YAML anchors, aliases, explicit tags (!foo, !!python/...), %TAG directives and multiple documents are rejected;
    • plain scalars are resolved with the YAML 1.2 core schema (yes/on/0777/dates stay strings), NaN/Infinity are rejected, duplicate keys are rejected and every mapping key must be a string;
    • JSON input is parsed with the same limits.

    :func:load_document returns a typed document (discriminated on kind) after running the apiVersion upgrade chain (the API accepts N and N-1). :func:canonical_json and :func:spec_hash give a normalised, deterministic serialisation for immutable revisions.

    Capabilities, manifests and outputs¶

    Model capabilities, uncertainty representations and the model manifest.

    The :class:Representation of a model's output decides which aggregations and summaries are statistically valid. Those rules live here as data (:data:REPRESENTATION_RULES) and small functions (:func:can_aggregate, :func:summary_allowed) so the control plane, the runner summariser and the UI all agree.

    Representation ¶

    Bases: StrEnum

    How a model encodes uncertainty in its outputs.

    DRAWS ¶

    DRAWS = 'draws'

    (chain, draw, *dims) joint samples — any aggregation is valid.

    QUANTILES ¶

    QUANTILES = 'quantiles'

    (quantile, *dims) marginal quantiles — no cross-cell aggregation.

    INTERVAL ¶

    INTERVAL = 'interval'

    (bound, *dims) + alpha, e.g. conformal — no aggregation.

    Static validation¶

    Static (JSON-only) validation of ModelSpecs and ScoreRequests.

    :func:validate_spec checks a :class:~mapi_spec.spec.ModelSpec against a :class:~mapi_spec.catalog.Catalog and the dataset's raw :class:DataSchema:

    1. binding references exist and do not collide;
    2. every use: resolves to a non-yanked version (semver range);
    3. step and model settings validate against their JSON Schemas;
    4. side-table references exist;
    5. the schema is propagated through every step's SchemaEffect, with per-step input checks;
    6. the split stage is resolved (default: end of the stateless prefix), its dims exist there, and LEAKAGE_RISK is raised if a stateful step precedes it;
    7. the model's schema template is resolved and compared with the final stage; spec dim policies may only tighten the plugin's;
    8. recursive forecasting (a target-dependent lag feeding a longer holdout) is rejected unless the model owns recursion; outputs, plots, metrics and resource class are checked.

    :func:validate_score_request runs the static CoordPlan checks for a ScoreRequest from metadata only (resolved spec + fit coordinate summaries + dim policies).

    Every finding is an :class:~mapi_spec.errors.Issue with a JSON pointer into the document.

    Run protocol¶

    See Run protocol for the narrative specification.

    The run protocol (plan §8.1, §8.3–§8.7): state machine, bootstrap, events, manifests.

    Everything a control plane, an executor and a runner must agree on lives here, as pure Pydantic / stdlib code:

    • :class:RunState, :class:RunTrigger and the transition table :data:TRANSITIONS, with the pure function :func:transition used by the API, dispatcher, events service, reconciler, finalizer and tests;
    • :class:RunSpec — the bootstrap object written to bootstrap/<nonce> before an execution starts (signed URLs, a per-run HMAC key, limits, deadline);
    • :class:~mapi_spec.executor.RunEvent payload models, canonical HMAC-SHA256 signing and verification, and the stdout JSONL wire format ({"mapi_event": {...}} per line);
    • :class:OutputManifest (the runner's claim), metadata-only verification against server-computed hashes, and the platform-signed :class:BundleManifest;
    • the runner invocation contract: environment (:class:RunnerEnv) and exit codes (:class:RunnerExit).

    Executor-facing shapes (:class:Isolation, :class:ExecutorCaps, :class:Handle, :class:ExecStatus, :class:RunKind, :class:RunEvent, ...) are defined in :mod:mapi_spec.executor and re-exported here unchanged, so both import paths name the same classes.

    Object storage¶

    Object storage contracts (plan §8.6): metadata, the ObjectStore protocol, signed URLs, integrity hashes and the bucket/key naming scheme.

    The control plane talks to object storage only through :class:ObjectStore. Two implementations exist outside this package: ShimObjectStore (the local GCS emulator in mapi_gcs_shim) and GcsObjectStore (google-cloud-storage). Both expose GCS semantics:

    • every write creates a new generation; if_generation_match=0 means "only if the object does not exist" (write-once);
    • the server computes CRC32C (base64 of the big-endian 4-byte value) and MD5 (base64 of the 16-byte digest) — uploader-supplied hashes are never evidence;
    • signed GET URLs are pinned to a generation and honour HTTP Range; signed PUT URLs and V4 POST policies (key prefix + content-length-range) are how sandboxes write, so the executor never holds storage credentials.

    Object keys are always built server-side from validated IDs with the helpers at the bottom of this module (never from user-supplied paths).

    ObjectStore ¶

    Bases: Protocol

    Async object-store driver used by the control plane (GCS semantics).

    Conventions shared by every method:

    • generation pins the source generation to read (None = live generation);
    • if_generation_match is a precondition on the target: 0 means "must not exist", n means "live generation must be n"; a failed precondition raises :class:PreconditionFailed;
    • missing buckets/objects raise :class:NotFound; denied operations raise :class:AccessDenied.

    PostPolicy ¶

    REST DTOs¶

    See HTTP API (v1) for the endpoint table and conventions.

    REST DTOs for the M1 HTTP API (/v1; plan §8.2 subset).

    Conventions shared by every endpoint (see docs/reference/http-api.md):

    • Requests reject unknown fields (extra="forbid"); responses ignore unknown fields when parsed by a client, so older clients keep working when the server adds fields.
    • Every resource carries tenant_id and project_id. M1 is single-tenant: both are :data:DEFAULT_TENANT_ID / :data:DEFAULT_PROJECT_ID, but the identity is in every row and key so M2 can add row-level security without migrations churn.
    • Lists return :class:Page (items + opaque next_cursor); errors are RFC 7807 :class:~mapi_spec.errors.Problem documents with stable codes.
    • Timestamps are timezone-aware RFC 3339 strings in UTC.

    :data:M1_ENDPOINTS is the machine-readable endpoint table; the server's route table and the reference docs are tested against it.
