    mapi_client¶

    The Python client for the /v1 HTTP API (see the Python client guide for tested walkthroughs and CLI and Python client for a summary of every resource). Generated from the docstrings; AsyncClient has the same resources, awaited.

    Clients¶

    Python client for the modeling-api /v1 HTTP API.

    • :class:Client / :class:AsyncClient - typed with the mapi_spec.api DTOs; resources projects, catalog, datasets, specs, runs, models and plots, and from v0.3 tenants, tokens, usage and admin (plus :meth:Client.me);
    • credentials: an API token (MAPI_TOKEN, config profile) or the OIDC sign-in stored by mapi login (:mod:mapi_client.oidc), renewed automatically;
    • project selection: Client(project="acme/growth") / MAPI_PROJECT / the profile's project is sent as X-Mapi-Project on project-scoped requests;
    • 429 handling: RATE_LIMITED is waited out (Retry-After) and resent; QUOTA_EXCEEDED raises :class:~mapi_spec.errors.QuotaExceeded with :func:retry_after_of (see :class:RetryPolicy);
    • errors are :class:mapi_spec.errors.MapiError subclasses rebuilt from RFC 7807 problems (see :mod:mapi_client.errors);
    • list endpoints return lazy :class:Paginator / :class:AsyncPaginator iterators;
    • runs.stream_events follows the SSE stream and resumes with Last-Event-ID;
    • datasets.upload and models.score handle signed URLs, waiting and CRC32C checks; xr.Dataset uploads and xr.DataTree results need the xarray extra;
    • from v0.4 guided, endpoints (and Client.endpoint(alias), a :class:RemoteEndpoint whose score(ds) returns an xr.Dataset), webhooks, saved plots, renders and embeds on plots, sign-up (:meth:Client.signup) and the trust lifecycle on tenants/admin; :mod:mapi_client.webhooks verifies deliveries and :mod:mapi_client.xrjson encodes inline payloads;
    • from v0.5 workflows (documents, revisions, runs with :meth:stream_events - an SSE iterator of :class:WorkflowSnapshot, :class:WorkflowEventFrame and :class:WorkflowEnd - node outputs, schedules, triggers, the template gallery), governance (check catalog, project and tenant policies), validations (requests, the review queue, approvals, evidence packs), explorations and the Data/Model Explorer, comparison and budget optimisation (models.optimize) methods, and About cards with Help me choose on catalog (abouts, chooser, recommend).

    from mapi_client import Client # doctest: +SKIP with Client("http://127.0.0.1:8000") as api: ... version = api.datasets.upload("eu_media.zarr.zip", dataset="eu_media_daily")

    RetryPolicy ¶

    RetryPolicy(
    max_retries: int = 2,
    base_delay: float = 0.5,
    max_delay: float = 30.0,
    rate_limit_retries: int = 4,
    max_rate_limit_wait: float = 120.0,
    max_quota_wait: float = 0.0,
    jitter: float = 0.1,
)

    When and how long to wait before resending a request.

    • Transport errors and 502/503/504: idempotent calls only (safe methods, Idempotency-Key, or by definition), max_retries times, exponential backoff with full jitter, honouring Retry-After (capped at max_delay).
    • 429 RATE_LIMITED: the server refused the request before acting on it (:mod:mapi_spec.quotas runs before any handler), so every method is resent, up to rate_limit_retries times, after max(Retry-After, base·2^n) plus a little jitter. A Retry-After longer than max_rate_limit_wait is not waited out: the error is raised with :func:~mapi_client.errors.retry_after_of set.
    • 429 QUOTA_EXCEEDED: raised at once, unless the quota resets within max_quota_wait seconds (default 0: never wait for a quota window).
    • A bare 429 without a problem document (a proxy) is treated like RATE_LIMITED for idempotent calls only.

    jitter ¶

    jitter: float = 0.1

    Fraction of a throttle delay added as random jitter (at most one second).

    Workflow run events (v0.5)¶

    Server-sent events: a WHATWG-conformant line decoder and typed run-stream items.

    GET /v1/runs/{run_id}/events (Accept: text/event-stream) sends snapshot (the full :class:~mapi_spec.api.Run, no id) first on every connection, then the persisted run events (id: = :attr:RunEventView.id) after Last-Event-ID, then live events, and finally end (the final run) before closing. : keepalive comments are heartbeats. progress and log frames are live and unpersisted: they carry no id: and are never replayed after a reconnect (:class:RunLiveFrame).

    GET /v1/workflow-runs/{run_id}/events follows the same pattern for workflow runs (v0.5): snapshot (the :class:~mapi_spec.workflow.WorkflowRun with every node), one frame per :class:~mapi_spec.workflow.WorkflowEvent (event: is its type, id: its seq) and end (the run id and its final status), decoded by :func:to_workflow_stream_item.
