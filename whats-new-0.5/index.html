    What's new in 0.5 v0.5¶

    v0.4 made one model easy to fit, read and share. v0.5 makes the full analysis around the model repeatable and trustworthy. A weekly forecast is not "fit an ARIMA and hope" now. It is a versioned workflow. The workflow does these steps:

    1. It tests the series for unit roots.
    2. It decides the differencing.
    3. It searches the AR and MA orders.
    4. It backtests the model on rolling origins against naive forecasts.
    5. It keeps the model only if the model wins.
    6. It checks the model against shuffled data and fake drivers.
    7. It records the evidence.
    8. It waits for the sign-off of a colleague.

    The workflow also runs again each Monday morning automatically.

    • Workflows

      A workflow is a versioned YAML graph. It can contain statistical tests, transforms, branches, train/test plans, order searches, model fits, evaluations, governance checks and reports. You get live node status, a cache for unchanged steps, schedules and dataset triggers.

      Workflow cookbook

    • Governance and null tests

      Policies tell which checks a model must pass and who must approve. For example, the model must be better than the same model fitted on shuffled results. It must give no credit to fake noise drivers, and it must be better than naive forecasts. Promotion refuses models that are not validated. Evidence packs are available for auditors.

      Can you trust this model?

    • Data and Model Explorers

      The Data Explorer has thirteen sections, for example profiles, stationarity, cross-correlation with the KPI, STL, VIF and quality warnings. The Model Explorer has eleven sections, for example parameters, residual tests, IRF/FEVD, forecasts, backtests and side-by-side comparisons with Diebold-Mariano tests.

      Explore a dataset · Explore a model

    • mmm-framework marketing-mix models

      mmm.bayesian is national or pooled over geos and products. mmm.frequentist is a ridge model with bootstrap ranges. You also get business priors, lift tests, response curves and budget optimisation with risk objectives and an efficient frontier.

      Marketing-mix models

    • Twelve statsmodels time-series models

      The models are SARIMAX, ARIMA, ETS, Theta, unobserved components, ARDL, error correction, VAR, VECM, VARMAX, dynamic factors and Markov switching. They support future drivers, prediction intervals, impulse responses, Granger and cointegration tests, and panels for each series.

      statsmodels models

    • About cards and Help me choose

      Each model, step, node, check and template has an About card in plain words. The card tells what the item does, when to use it and when not to use it. It also tells what the item needs and what it gives. Help me choose changes eight answers into a ranked shortlist with the reasons.

      Choosing a model

    For analysts: answers you can defend¶

    • Help me choose. Possibly you do not know if you need an ARIMAX, an exponential smoothing model or a marketing-mix model. Answer a maximum of eight questions, for example "What do you want to do?", "What does your data look like?" and "Do you need a range?". You get the best fits. Each fit has the reasons, the cautions and its About card. You can use Help me choose in the web app, in the terminal (mapi choose) or in Python.
    • Templates that think like a statistician. Start a workflow from the gallery, for example Is my weekly KPI ready to forecast?, Do these series move together?, A governed marketing-mix model or Forecast bake-off. Read the result as a report. Each test has a plain verdict ("The series wanders: consider differencing it."). Each decision shows the numbers that it read. Each comparison says "is possibly luck" or "It is not luck".
    • A model must earn its place. Before a person uses a model, the platform shuffles the results that the model was fitted on. Then it fits the model again, many times. A model that learned something real must be clearly better on the real data. The platform also adds drivers that are pure noise. These drivers must get almost no credit. The null tests explained page shows why this is important, without formulas.
    • Explore before you model. The Data Explorer shows gaps, constant columns, outliers, collinear drivers and series that wander. It also shows which drivers move with the KPI, and at which lag.

    For data scientists: the statistics, end to end¶

    • A DAG with typed ports. The port types are dataset, test_result, split_plan, model_version, metrics, table, evidence and report. The server validates the DAG statically with JSON pointers before a run starts. Branches use a safe expression language (never eval) and record the values that they read. Alternatives ([diff.data, inputs.data]) take the first input that exists.
    • Seventeen statistical tests. We checked these tests against statsmodels/scipy/arch reference values. The tests are:
      • ADF, KPSS, Phillips-Perron, Zivot-Andrews, Johansen and Engle-Granger
      • Ljung-Box, Jarque-Bera, Breusch-Pagan, White and ARCH-LM
      • Granger, ACF/PACF, seasonal strength, VIF, CUSUM and Chow.
    • Split plans and searches. There are seven split plans: holdout, rolling origin, expanding window, blocked k-fold, purged k-fold, geo holdout and nested. There are ARMA/SARIMA/VAR-lag/cointegration-rank searches and grid searches on backtests. There is also Diebold-Mariano with the Harvey-Leybourne-Newbold correction.
    • Honest backtests. Each candidate and each naive benchmark use the same folds. A gap allows for late data. The backtest scores each horizon separately.
    • Governance with real statistics. Each check gives the value, the threshold and the evidence. The checks change for Bayesian, frequentist and machine-learning models. The checks are:
      • block-permutation tests of the target
      • placebo noise regressors, measured by ablation, and time-shifted placebos
      • out-of-sample skill against naive and seasonal-naive forecasts
      • Ljung-Box whiteness and rolling-window stability
      • prior sensitivity, parametric-bootstrap recovery, R-hat and holdout accuracy.
    • All of it from Python and the terminal. The Python client has api.workflows, api.governance, api.validations, api.explorations, api.models.optimize and api.catalog.recommend. The CLI has mapi workflows run --watch, mapi validate model, mapi approve, mapi explore, mapi optimize and mapi choose.

    The canonical example, three ways¶

    The cookbook shows each node of the example. This is a short version:

    from mapi_client import WorkflowEnd, WorkflowEventFrame, WorkflowSnapshot

# create the workflow, or save the file as its next revision when it changed
workflow, revision = api.workflows.upsert(Path("weekly-readiness.yaml"))
run = api.workflows.run(
    workflow.id,
    inputs={"data": "dataset://growth/weekly_sales@latest"},  # pinned to a version at start
    params={"drivers": ["price"], "window": 80, "max_p": 2, "max_q": 2},
)
for item in api.workflows.stream_events(run.run_id):  # server-sent events, resumable
    match item:
        case WorkflowSnapshot(run=now):
            print(f"{len(now.nodes)} nodes, {now.status.value}")
        case WorkflowEventFrame(event=e) if e.type.value == "workflow.branch.decided":
            print(f"  {e.node_id}: took the {e.data['arm']} arm")
        case WorkflowEventFrame(event=e) if e.node_id is not None:
            print(f"  {e.node_id}: {e.type.value.rsplit('.', 1)[-1]}")
        case WorkflowEnd(status=status):
            print("run", status.value if status else "ended")

    mapi workflows templates                      # the gallery, in plain words
mapi workflows init ts_readiness_arimax --name weekly-readiness   # writes weekly-readiness.yaml
mapi workflows validate weekly-readiness.yaml # checked by the server: pointers to every problem
mapi workflows apply weekly-readiness.yaml -m "first version"     # create, or save a revision
mapi workflows run weekly-readiness \
  --input data=dataset://growth/weekly_sales@latest \
  --param 'drivers=["price"]' --param window=104 \
  --watch                                     # live node status; exit 1 if the run fails

    api POST /v1/workflows -d "$(jq -Rs '{text: .}' weekly-readiness.yaml)"
api POST "/v1/workflows/$WF/runs" -H "Idempotency-Key: $(uuidgen)" -d '{
  "inputs": {"data": "dataset://growth/weekly_sales@latest"},
  "params": {"drivers": ["price"]}}'
curl -N -H "Accept: text/event-stream" "$API/v1/workflow-runs/$RUN/events"

    This output shows that the platform is honest. It does not flatter the model:

    • All four unit-root tests agree that the series wanders. Thus the workflow differences the series one time.
    • On weeks that it did not see, ARIMAX is 25% better than "same as last week".
    • ARIMAX forecasts better than all twenty fits with the price driver shuffled in time. Thus the driver has real information.
    • But Diebold-Mariano says that the one-week-ahead advantage over naive is possibly luck.
    • The AR coefficient changes across windows of history.

    The default forecasting policy uses stability as information only. Thus the version is validated, and the failure stays on the record for the reviewer. A stricter policy makes the failure blocking. Each validation makes its own random shuffles. Thus the p-value of the shuffled-driver test changes a little between validations.

    The tests of the documentation run this walkthrough, without changes, against a real server.

    Upgrading from 0.4¶

    • mmm-framework is the only marketing-mix engine. We removed the earlier marketing-mix plugins. Specs move to mmm.bayesian@^1. They do not have their own scaling and lag steps now, because the model controls scaling, carry-over and units. For budget optimisation, use POST …:optimize (api.models.optimize, mapi optimize). See Marketing-mix models and the Removed section of the CHANGELOG.

    • Contract version 0.2. This version adds:

      • resources: workflow, policy and tenant_policy
      • actions: validate and approve
      • scopes: workflows:write, workflows:run, models:validate and policies:manage
      • the reviewer capability on memberships.

      An API token cannot approve. - Migrations 0011_workflows and 0012_governance. These migrations add workflow and governance tables under forced row-level security. - Promotion can now need validation. If a policy has require_validated_for_promotion, endpoints refuse unvalidated versions with 409 NOT_VALIDATED. The default policies that the platform seeds on first use do not gate promotion. You must turn on this gate yourself. - Client and CLI. All of the items above are new API surface. No existing signature changed. mapi_client exports WorkflowSnapshot, WorkflowEventFrame and WorkflowEnd for the workflow event stream.

    What is not in 0.5 yet¶

    • mmm.nested and mmm.multivariate (the extensions of mmm-framework) have About cards but no plugin. The multiplicative specification, time-varying effects and price/promotion levers are not available.
    • statsmodels models do not have the counterfactual, simulate or filter score modes. A what-if is a forecast with changed future drivers.
    • evaluate.residuals and model.forecast nodes make tables, not plots.
    • We did not run 0.5 on real Google Cloud or in Docker. See the release notes.
