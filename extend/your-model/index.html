    A model recipe is a model that you describe instead of program. There are two kinds:

    • A declarative model. You say what to explain, which drivers move it, what you believe about each driver (a prior and a sign) and which groups have their own level. The platform fits it with the trusted built-in model tabular.declarative_glm.
    • A preset over a catalog model. You fix the settings of any model in the catalog and pick the few settings that others may change when they use it. Use it to share "the way our team fits weekly forecasts".

    You make both in the app, under Make your own › Models. Each recipe is a JSON document with revisions. This page shows the same document as YAML, which is what the builder's YAML tab shows.

    A declarative model¶

    # A declarative model recipe (docs/extend/your-model.md). `make docs-test` compiles it
# (docs/snippets/extend_library.py and conformance/tests/test_docs_extend.py).
apiVersion: mapi/v1
kind: ModelRecipe
metadata: {name: store-sales, title: "Store sales with promo lift", tags: [retail]}
base: declarative
declarative:
  outcome: {var: sales, family: negative_binomial}
  terms:
    - {var: price, transform: [{use: log1p}, {use: standardize, with: {over: [obs]}}], prior: {dist: normal, sigma: 0.5}, sign: negative}
    - {var: promo, prior: {dist: normal, sigma: 1}, sign: positive, varies_by: store}
  groups: [{dim: store}]
plots: [core.ppc]

    In the builder, this is:

    1. Data. Pick a dataset. The builder lists its columns and their roles.
    2. Outcome. sales is "A count that varies a lot", so the family is negative_binomial. Each plain label maps to one of the ten families: "A number" (normal), "A number with outliers" (student_t), "A positive amount" (gamma), "A count" (poisson), "A count with many zeros" (zero_inflated_poisson), "Yes / no" (bernoulli), "A share between 0 and 1" (beta), "A rating" (ordinal) and two more for counts. The extension points reference lists them all.
    3. Terms. One row for each driver:
      • Transform chips apply built-in steps to the driver first: log1p, standardize, max_abs_scale, mean_scale, adstock, saturation, impute.
      • Prior is one of normal, student_t, laplace, half_normal, exponential or lognormal, with numbers for its parameters. The small curve next to it shows which values the prior thinks are likely.
      • Sign is any, positive or negative. A sign cuts the prior at zero, so the model can never give a driver the wrong direction.
      • Varies by gives a driver its own slope in each level of a group.
    4. Groups. Each group (up to three) gets its own intercept, partly pooled toward the others.
    5. Review. A summary in words and the YAML. Then Save, Use in Build or Fit now.

    There are no expressions in a declarative model: every choice comes from a closed list. This is why anybody may make one, on any tier.

    What it compiles to¶

    When you use the recipe, the platform compiles it to normal spec parts. This is the code the server runs (mapi_spec.model_recipes), here with the catalog of this checkout and the schema of a weekly table with one row for each week and store:

    from mapi_sdk import default_registry
from mapi_spec.library import parse_library_text

catalog = default_registry().catalog()  # what `describe` publishes for this checkout


def load(name: str):  # noqa: ANN201 - a library document of any kind
    return parse_library_text((HERE / name).read_text("utf-8"))

    from mapi_spec.schema import DataSchema

# the dataset you pick when you use the recipe: weekly sales of each store
schema = DataSchema.model_validate(
    {
        "dims": {
            "week": {"kind": "time", "freq": "W-SUN"},
            "store": {"kind": "categorical"},
        },
        "vars": {
            "sales": {"dims": ["week", "store"], "dtype": "float64", "role": "target"},
            "price": {"dims": ["week", "store"], "dtype": "float64"},
            "promo": {"dims": ["week", "store"], "dtype": "float64"},
        },
    }
)

    from mapi_spec.model_recipes import compile_model_recipe

recipe = load("extend_model_recipe.yaml")
compiled = compile_model_recipe(
    recipe, catalog, schema=schema, item_ref="lib_01jaf3q2x8m9v7k5h4g3f2e1d0-r1"
)
assert compiled.ok, [(i.pointer, i.message) for i in compiled.issues]
fragment = compiled.spec_fragment()
print(fragment["model"]["use"])  # tabular.declarative_glm@^1
print([s["use"] for s in fragment["pipeline"]])  # shape to long rows, then the transforms
print(fragment["metadata"]["labels"])  # {'mapi.library/model': 'lib_...-r1'}

    The pipeline first turns the week × store table into one row for each observation (core.to_long), then applies the transforms of each term. The model block uses tabular.declarative_glm@^1. The label mapi.library/model records which recipe and which revision made the spec. A later revision of the recipe never changes a spec that you made before.

    If your data has the wrong shape

    The builder checks the shape when you pick a dataset. If the platform cannot make one row for each observation (for example, the outcome and a driver have different dims), you get LIBRARY_DATA_SHAPE with a hint of what to change.

    A preset over a catalog model¶

    # A preset over a catalog model (docs/extend/your-model.md): fixed settings plus the two
# keys the person who uses it may change. `make docs-test` compiles it.
apiVersion: mapi/v1
kind: ModelRecipe
metadata:
  name: weekly-ets
  title: "Weekly sales forecast (damped trend)"
  summary: "Exponential smoothing with a damped trend and a yearly season."
  tags: [forecast, weekly]
base: ts.ets@^1
settings:
  trend: add
  damped_trend: true
  seasonal: add
  seasonal_periods: 52
exposed: [seasonal_periods, damped_trend]

    base names any catalog model with a version range. settings are fixed. exposed lists the settings that a person who uses the preset may change. The Use form shows only these settings, made from the base model's settings schema:

    from mapi_spec.model_recipes import exposed_settings_schema

preset = load("extend_model_preset.yaml")
form = exposed_settings_schema(preset, catalog)  # the "Use" form: only the exposed keys
assert form is not None
print(sorted(form["properties"]))  # ['damped_trend', 'seasonal_periods']
used = compile_model_recipe(preset, catalog, exposed={"seasonal_periods": 13})
assert used.ok, [(i.pointer, i.message) for i in used.issues]
print(used.model.use, used.model.settings["seasonal_periods"])  # ts.ets@^1 13

    In the app, you can also save a preset from the model panel of the spec editor: Save as preset.

    Use a recipe¶

    • Build: the palette lists your recipes under "From your team". Pick one, then pick a dataset.
    • Make your own › Models: open a recipe, then Use in Build (a new draft spec) or Fit now.
    • Catalog › Yours: "From your team" lists every recipe of your project and your tenant.

    Share a recipe¶

    A new recipe belongs to your project. Every member of the project can use it. A tenant admin can promote it: the latest revision is copied into a tenant item that every project of the tenant can use. Items are never deleted, only archived, so a spec that used one still says where it came from.

    Who Can do
    Viewer Use project and tenant items
    Editor Make, revise and archive project items
    Tenant admin All of that, plus make and promote tenant items

    The HTTP API¶

    The app uses these routes; you can use them too (see the OpenAPI explorer):

    Route What it does
    GET /v1/library?kind=model_recipe List items
    POST /v1/library Make an item ({"document": {...}} or {"text": "<YAML>"}, scope)
    POST /v1/library/{item_id}/revisions Add a revision (If-Match: "r<n>")
    POST /v1/library:validate Check a document, optionally against a dataset
    POST /v1/library/{item_id}:use Compile an item: a spec fragment for a model recipe
    POST /v1/library/{item_id}:promote · :archive Promote to the tenant, archive
